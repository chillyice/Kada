| 文件 | 改动 |
|---|---|
| `AGENTS.md` | 「归档流程」重写为两档：日常只追加日更（+ 代码地图）；明确说「归档」才全量梳理。Git 例外条改成「日更自动提交」，交付范围 = 代码 + 当日日更 |
| `.agents/skills/archive/SKILL.md` | 技能重写：`一、日常日更（默认动作）` / `二、全量归档（只在明确口令下）` + 分流规则表；`.zcode/skills/archive` 是指向它的符号链接，一处改完即两处生效 |
| `docs/README.md` | 索引表加 `docs/归档/日更/` 一行；「文档维护规矩」第一条改成两档节奏，真机验收项日常先写日更 |
| `docs/变更归档.md` | 抬头声明：本表只收全量归档沉淀过的条目，日常原记在 `日更/` |
| `scripts/check-docs.mjs` | 新增 `[daily]` 检查：日更只许 `YYYY-MM/YYYY-MM-DD.md` 形状（防目录漂移） |
| `docs/归档/日更/2026-11/2026-11-07.md` | 本文件（日更目录首个记录） |

**规则/决策**：
- **日常不再动大文档**：`docs/需求设计说明书.md`（~1.5MB）、`docs/变更归档.md`（149KB）、`docs/人工验证清单.md`（367KB）、四个分卷，每次改动都要 Read + Edit，读写成本远大于收益；改为只往当日日更追加（小文件、只 append）。
- **代码地图例外**：它是定位入口、每次只加一两行，且 AI 一开工就靠它 —— 改了代码就顺手加/改路由行，不受「等归档」约束。
- **日更 = 原始记录，只追加不改写**：全量归档时靠它回填说明书的「功能现状」和变更归档的索引 / 分卷；因此条目必须写清功能现状怎么变，不能只写「改了 xx 文件」。
- **全量归档只在明确口令下**：用户说「归档 / 整理文档 / 更新文档 / 归档推送」才把日更沉淀进正式文档；日更原件保留（不改不删），审计链不断。
- **提交策略不放宽**：日常仍要 `git commit` + `git push`（多会话并行 + OneDrive 同步下未提交改动会被回退），只是提交范围变成「代码 + 当日日更」。
- **新铁律仍可即时进 AGENTS.md**：只有「确实是新铁律 / 新约定」才写，且守 20KB（CRLF）上限；本次改完余量只有几十字节，要加内容得先外移描述性细节。

**验证**：`node scripts/check-docs.mjs` 通过（AGENTS.md 20,4xx B / CRLF 上限 20,480 B，新增 `[daily]` 检查对当日文件通过）。
**遗留**：说明书与变更归档自 V2.62 之后未沉淀的条目，等用户明确说「归档」时统一梳理。

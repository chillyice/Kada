**决策 / 结论**：

1. **没有「先吞下、凑不齐再回放」的窗口**——`onKeyEvent` 必须同步回答吞不吞，桌面 `Engine` 的吞键语义在安卓上不成立。
2. **只能吞不能注入**：吞错的键补不回来，和弦必须选「成员键被吞也无所谓」的组合。
3. **软键盘打字不产生 `KeyEvent`**：手机档「打字触发」只能走面板 / 粘贴（规划 §4 定案未变）。
4. **自动化必须用 `sendevent`**：`adb shell input keyevent` 的注入事件不进无障碍过滤，用它测吞键是假阴性。
5. **音量键可收可吞**（系统音量不跟着变），但系统侧流水线约 160 ms。

**验证**：模拟器 `emulator-5554` / `ihomy34`（Android 14）S0 段全过（收键 / 吞键 / tap-hold / 和弦 / 音量键 / 前台服务 / `GLOBAL_ACTION_*`）；探针自身判据 32 项见下一节汇总。`sendevent` 需要 `adb root`（重启后丢，脚本开跑先补）。

**决策**：

1. **吞键策略定成非破坏式**：`shortcuts` 只吞「凑齐的那一下」，和弦成员 / 序列前缀一律放行；`remaps` 与层**永不吞**（无 root 注入不了，吞了就是白吞），只在报告里标 `unsupported`。这是对规划 §5.2「先吞后回放」的**有意偏离**——安卓没有回放通道，只能少吞。
2. **判定在 Rust，Kotlin 只搬运**：决策顺序、等待窗、前台过滤全在 `crates/kada-android/src/engine.rs`；Kotlin 只做 keycode → core 键名映射 + 动作执行，避免两套规则漂移。
3. **动作支持表只有一份**：`action_support.rs` 的 `SUPPORTED`（`open_url` / `text` / `clipboard` / `pause_ms` / `group` / `disabled`）；Kotlin 不许再维护第二张表，报告里的 `unsupported_actions` 也由它产出。
4. **共享层搬 core 而不是复制**：`decide` / `config_io` 搬进 `kada-core`，桌面壳改成重导出——桌面行为零变化，安卓直接用。
5. **`text` 动作先按「写剪贴板 + `ACTION_PASTE`」落地**（规划 §4 方案 ③ 的底座），已知会覆盖用户剪贴板，方案本身仍待决策。

**决策**：

1. **S1 段以 `resetConfig` 起跑**：上一轮的合并导入会把 `F6` 留在设备上，「示例 5 条」「合并后 6 条」这类断言就随残留漂移。删配置 + 重新 `init` 比「导出→替换导入」干净（不依赖上一轮导出的文件）。
2. **前台切换是「丢键」的头号原因**：`open_url` 拉起 Chrome、通知栏 / 快捷设置抢焦点，都会让无障碍重建输入连接，窗口里的按键直接丢。所以每段按键前统一 `Restore-App`，而不是逐条补 `am start`。
3. **时序必须一次发完**：每次 `adb shell` 在 Windows 上有 50~200ms 抖动，偶发卡 1~2 秒；分开发会把和弦成员间隔拖过 `chord_timeout_ms`（1000ms）。`Send-Sequence` 把 `睡 60ms` 这类间隔也交给**设备侧** `sleep`，脚本自身延迟不再影响按键时序。
4. **重试一次不掩盖回归**：`Test-KeyFlow` 失败会重发并重判，两次都失败才判 FAIL；重试成功时打 `[warn]` 留痕，方便区分「脚本抖了」和「功能坏了」。
5. **主线程是共享预算**：`onKeyEvent` 与节点动作 / 报告序列化同在主线程，连续 binder 调用会吃掉输入过滤的 500ms 预算（超时即 fail-open 放行）。所以音量键检查前移到节点动作之前。
6. **Gradle 输出不接管道**：一次 `powershell verify.ps1 | Tee-Object …` 全量跑挂了 30 分钟超时，日志其实在跑完那刻就写完了（含汇总），是 Gradle daemon（空闲 3 小时才退）继承了父进程 stdout 句柄，管道等不到 EOF。改成「Gradle 输出落临时文件 → `FileShare.ReadWrite` 读回回显」；用户手动留日志也一律 `> 文件`。

- 首轮复跑 30/32（`F&J` 和弦、导入 `F6` 两条偶发 FAIL）；`adb` 直连逐条复现均为 PASS，确认是投递时序而非判定逻辑 → 才有上面的四件去抖改动。

## ControlReceiver 加 DUMP 门控（0.2.0-s2）

| 文件 | 改动 |
|---|---|
| `android/app/src/main/AndroidManifest.xml` | `ControlReceiver` 加 `android:permission="android.permission.DUMP"`（`exported` 保持 `true`）；注释改成「门控代替『出货前记得删』」 |
| `android/app/src/main/java/com/kada/spike/ControlReceiver.kt` | 类注释同步：DUMP 只有 shell / system 持有，非 shell 身份被拦是预期 |
| `android/app/build.gradle.kts` | `versionCode` 2 → 3、`versionName` `0.2.0-s1` → `0.2.0-s2` |
| `android/README.md` | 目录树与「坑」两处口径更新（不再是「出货前删」，而是 DUMP 门控） |
| `docs/安卓版规划.md` §8 | 补一条分发纪律：调试入口要门控，别靠口头约定 |

**决策**：

1. **门控用 `android.permission.DUMP`，不是自定义 signature 权限**：signature 权限要求调用方与接收方同签名，而 `adb shell`（uid 2000）拿不到，验收脚本会全废；DUMP 的保护级别是 `signature|privileged|development`，shell / system 天然持有，第三方应用只能靠用户手动 `pm grant`（要物理接触），刚好卡住「公开发出去就被同机应用控制」这条风险。
2. 保留 `exported="true"`：`am broadcast` 即便显式指定组件，非导出组件 shell 也发不进去。
3. 不删 receiver：`verify.ps1` 的 32 项全靠它（导出报告 / 开关状态 / 重置配置），删了就得另造一条控制通道。
4. 旧包 s1 **从服务器删掉**：它仍是裸 receiver，留在公开地址等于白加固。

**验证**：

- manifest 落盘：`aapt2 dump xmltree` 的 `E: receiver` 下能看到 `permission="android.permission.DUMP"` + `exported=true`；`aapt2 dump badging` → `versionCode='3' versionName='0.2.0-s2'`。
- 平台侧：`dumpsys package android` → `Permission [android.permission.DUMP] ... prot=signature|privileged|development`；`dumpsys package com.android.shell` → `android.permission.DUMP: granted=true`。
- shell 侧仍可驱动：`adb shell am broadcast ... --es op export` → `Broadcast completed: result=0`，日志出现 `ctrl op=export` + `report written`，报告仍 5 条。
- **反面测试本身有坑**：用 `run-as com.kada.spike am broadcast` 从同 uid 发**照样送达**（AMS 对同 uid 组件放行），而且权限不足时命令仍回 `result=0`（只写日志）。所以「拒绝」得换另一个应用 uid 才测得出来，判定送达要看副作用（日志 / 落盘）而不是返回码。
- 发布链路：s2 上传 `/opt/ihomy/uploads/kada/`（8,015,865 B，远端 `stat` 一致），直链 `200`、计数接口 `302`、旧 s1 `404`；ihomy 落地页 `androidVersion` 改 `0.2.0-s2` 后重新发 dist，线上 `assets/Kada-BazPZxE5.js` 与本地构建 **SHA256 一致**。
- 验收脚本：`powershell android\tools\verify.ps1 -SkipBuild` → **32/32 PASS**（DUMP 门控没有破坏 adb 驱动）。

| 文件 | 改动 |
|------|------|
| `Cargo.toml` | workspace 定义：members `crates/kada-core`/`crates/kada-hook`/`src-tauri`；release profile `lto=true`/`strip=true`/`codegen-units=1` |
| `src-tauri/` | Tauri 2 壳脚手架（`Cargo.toml` crate `kada`、`build.rs`、`tauri.conf.json`、`src/main.rs`、图标） |

**规则/决策**：workspace 三成员职责切分——`kada-core` 只做纯逻辑（可独立测试、无平台依赖）、`kada-hook` 只做平台钩子、`src-tauri` 只做壳与命令层；平台相关代码用 `#[cfg]` 门控，保证非目标平台仍可编译。

##### M1 核心键模型 + Windows 钩子引擎

| 文件 | 改动 |
|------|------|
| `crates/kada-core/src/lib.rs` | `Key`/`Modifier`/`RawEvent`/`Shortcut` 类型；`parse::shortcut`/`parse::key`（`"Ctrl+Alt+K"`）；`format_shortcut`/`key_name`；`matches`（主键一致 + 修饰键超集） |
| `crates/kada-hook/src/win.rs` | `SetWindowsHookEx(WH_KEYBOARD_LL)` 全局低层钩子；`start`/`HookHandle`（Drop 发 WM_QUIT 回收）；`keyboard_proc`/`swallow` 状态机（`Block`/`Replace`/`SWALLOWED`/`REPLACED_DOWN`/`LAST_DOWN`）；`GetKeyState` 修饰键 + 250ms 自动重复识别；`LLKHF_INJECTED` 防回环；`key_to_vk`/`vk_to_key` 映射 |
| `crates/kada-hook/src/win/simulate.rs` | `SendInput` 注入 `down`/`up`/`tap`/`chord`；`type_text` 剪贴板 + `Ctrl+V` |
| `crates/kada-hook/examples/demo.rs` | M1 冒烟 demo：`Ctrl+Alt+K` 输文本、`Ctrl+Alt+M` 改键、`Ctrl+Alt+Q` 退出（仅 Windows） |
| `crates/kada-hook/tests/hook_smoke.rs` | 钩子安装 → 消息循环 → 卸载回收冒烟（仅 Windows） |

**规则/决策**：
- 处理函数直接跑在回调内（不做跨线程调度），保证顺序与低延迟；注入事件带 `LLKHF_INJECTED` 一律放行杜绝回环。
- `Block`/`Replace` 登记 `SWALLOWED`，后续 keyup 一并吞掉防幽灵按键；`Replace` 保持"按下-抬起"配对。
- 未吞掉的 keyup 以观察者身份回调 handler（录制宏用），返回值忽略、永远放行。
- `type_text` 用剪贴板粘贴（中文最稳），会短暂占用剪贴板。

##### M2 配置模型与动作/宏

| 文件 | 改动 |
|------|------|
| `crates/kada-core/src/lib.rs` | `Config`/`ShortcutItem`/`Remap`/`Action`（`Text`/`Sequence`）/`Step`（`Text`/`Tap`/`Keys`/`Down`/`Up`/`PauseMs`）；`Action::validate`（键名可解析校验）；`#[serde(tag="type", rename_all="snake_case")]` 序列化；`Default` 实现 |

- 手工编辑的配置允许缺字段、带未知字段（`#[serde(default)]`），配置缺失字段回落默认值（如 `enabled` 缺省 `false`）。

##### M3 Tauri 桌面壳 + 宏录制 + 配置界面

| 文件 | 改动 |
|------|------|
| `src-tauri/src/lib.rs` | `KadaState`/`Ev`/`Outcome`/`decide`（改键优先于快捷键）/`fire`/`run_action`/`Recorder`（转录 `Step` 时间线）/`load_config`/`save_config`/`validate`；Tauri 命令 `get_config`/`set_config`/`set_paused`/`start_record`/`stop_record`；`setup` 接钩子 + 托盘常驻（关窗隐藏） |
| `ui/src/main.ts` | 配置界面：快捷键列表（开关/编辑/删除/录入组合键）、动作类型切换（文本/宏）、宏录制（`start_record`/`stop_record`）、改键列表（from/to 下拉） |
| `ui/src/style.css` | 深色 UI 样式 |

**规则/决策**：
- 改键优先于快捷键（先消耗原生键，避免改键后键再触发快捷键）；命中动作在异步线程执行，避免阻塞钩子回调。
- 录制器中重复 down 折叠、事件间时差 ≥20ms 补 `PauseMs`；录制中快捷键/改键全暂停。
- 组合键录入时调 `set_paused(true)` 暂停触发，避免自触发；Esc 取消。
- 关窗 = 隐藏到托盘（`CloseRequested` 阻止关闭并 hide），应用继续跑。

##### M4 Linux 钩子引擎（evdev + uinput）

| 文件 | 改动 |
|------|------|
| `crates/kada-hook/src/linux.rs` | evdev + uinput 钩子：`start` 抓取键盘设备 + 建虚拟键盘 `kada-virtual-keyboard`；`poll_loop` 轮询；`handle`/`press`/`release` 状态机（`SWALLOWED`/`REPLACED_DOWN`/`MODS_DOWN`）；`key_to_code`/`code_to_key` 映射；`simulate` 子模块（`type_text` 剪贴板 + `Ctrl+V`） |
| `crates/kada-hook/src/lib.rs` | 增加 `#[cfg(target_os = "linux")] pub mod linux;` |
| `crates/kada-hook/Cargo.toml` | Linux 目标加 `evdev = "0.13"`；`arboard`/`windows` 依赖改为 `cfg(any(windows, target_os = "linux"))` |
| `Cargo.lock` | 新增 evdev 依赖树 |
| `src-tauri/src/lib.rs` | 增加 Linux `input` 模块（`kada_hook::linux`）+ `to_ev` 映射 |

**规则/决策**：
- 独占抓取（`EVIOCGRAB`）使被抓设备按键事件只到达我们，原事件不再进应用；用 uinput 虚拟键盘转发，天然无注入回环。
- 修饰键状态按事件流维护（`MODS_DOWN`），吞键/改键不影响真实状态位，与 Windows `GetKeyState` 语义对齐。
- 需要 root 或 `input` 组 + udev 放开 `/dev/uinput`；无权限时 `start` 报错，能读到的其它键盘静默跳过。
- 热插拔键盘不在监听列表（重启应用即可）。

| `ui/index.html` | 「消息」导航（红点徽标）+ 消息详情区（tab 条 + `‹ ›` + 清空）+ 结果弹窗模态 |
| `ui/src/main.ts` | `listen` 监听 `command-result`；消息页/tab/红点/弹窗渲染；Cmd/PowerShell 动作「弹窗显示结果」复选框；TS `Action` 类型加 `show_output` |
| `ui/src/style.css` | 红点徽标、消息 tab/卡片、结果弹窗、动作复选框样式 |

**规则/决策**：

- `show_output` 开 → 唤起主窗口 + 结果弹窗；关 → 托盘图标 + 应用内「消息」入口亮红点。两种情况都 `emit("command-result")`。
- 中文不乱码：Windows cmd 前缀 `chcp 65001>nul & `、PowerShell 前缀 `[Console]::OutputEncoding=...` 统一 UTF-8 解码；Linux 下 CMD 走 `sh -c`。
- 进入「消息」页即标记已读（`mark_results_read`），红点熄灭、托盘图标还原。

| 文件 | 改动 |
|------|------|

| `src-tauri/src/lib.rs` | `run_actions` 递归驱动（拦截 If 按条件分支执行）；`run_os`/`run_app`（文件动作走 std::fs、应用动作用 taskkill/tasklist/启动）；`close_program` 统一记入消息中心；`set_config`/`import_config` 改为清洗后返回 `Vec<String>` 忽略提示 |
| `ui/src/main.ts` | 动作类型新增「文件动作 / 应用动作 / 条件判断」；文件动作子操作下拉 + 文件/目录浏览、应用动作程序浏览 + 参数、条件判断递归渲染 then/otherwise 分支；TS 类型对齐 |
| `ui/src/style.css` | 条件判断分支样式（`.branch-label`/`.action-branch`/`.add-inline`） |

**规则/决策**：
- 变量作用域 = 单次触发内的动作序列：`GetFileProps`/`Status` 写入变量，后续动作（含 If 条件）用 `{变量名}`/`{变量名.字段}` 引用；复制/剪切记 `last_copied` 供「粘贴」用。
- 动作链不引入 `Sequence` 包装：`If` 的 `then`/`otherwise` 直接是 `Vec<Action>`，运行器递归展开，嵌套条件任意层。
- 保存语义从「校验失败整体拒绝」改为「逐条清洗 + 提示」：坏触发键/动作/改键单独忽略，硬冲突不再阻塞保存（仅 UI 提示），避免「一条坏配置拖垮整份保存」。
- 旧版 `Launch`/`CloseProgram` 保留为兜底变体（加载时已迁移到 `App`，正常不出现）。

| 文件 | 改动 |
|------|------|
| `src-tauri/capabilities/default.json` | `windows: ["main"]` → `["main", "toast"]`：把气泡窗口纳入 capability，修复「触发快捷键后右下角气泡无内容」（`toast` 窗口无 `core:default` 导致 `plugin:event|listen` 被 ACL 拒绝） |
| `src-tauri/tauri.conf.json` | `windows` 清空为 `[]`：纯托盘冷启动，启动时零 WebView |
| `src-tauri/src/lib.rs` | 新增 `ensure_toast()`（首次触发才建气泡窗口 + 点击穿透/定位）、`show_main_window()`（主窗口不存在则建 860×560 居中、已存在则 show+focus）；`KadaState` 增 `toast` 暂存载荷 + `get_toast_payload` 命令；`setup` 删启动时气泡创建，`launch_minimized`/托盘菜单/双击/`show_output` 三处改走 `show_main_window` |
| `ui/src/main.ts` | `bootstrapToast()` 加载后主动 `get_toast_payload` 拉取一次，兜底「事件早于监听器注册」的首触发竞态 |
| `ui/src/style.css` | `body:has(.toast-bubble) { background: transparent }`：transparent 窗口的 body 必须透明，否则显示成实心深色矩形 |

**规则/决策**：
- 冷启动零 WebView：主窗口与气泡窗口都不在启动时创建，首次用到才 `WebviewWindowBuilder` 建出；`default_window_icon` 来自 `bundle.icon`（非 `windows` 数组），清空 windows 不影响托盘图标。
- 气泡懒创建有首触发竞态（窗口刚建好、事件早于前端监听器注册）→ 后端 `KadaState.toast` 暂存载荷 + 前端加载后拉取兜底，保证第一次触发也有内容。
- 主窗口按需创建后「关窗」仍隐藏到托盘（`CloseRequested` 阻止关闭），不销毁 WebView，后续打开即时、状态保留。
- 已知边界：主窗口从未打开时若 `show_output` 结果触发，弹窗可能错过（主窗口刚建、`command-result` 监听器未注册），但结果仍进消息中心。

**规则/决策**：

**规则/决策**：

- 注入修饰分三类、释放时机各不同：`hold`（`from` 松开释放）、`sticky`（再次单击 `from` 解锁）、`oneshot`（下一个非修饰键释放）；`oneshot` 的 roll/长按复用 `activate_hold` 当普通 hold 修饰按下/释放。mods 补全 = `hold ∪ sticky ∪ oneshot`，让「长按 CapsLock=Ctrl」「粘滞 Shift」「单次 Ctrl」都能让后续组合键携带该修饰。

**规则/决策**：
- **吞键铁律**：被吞的键补不回来，「吞掉」只允许发生在「还在等下一个键凑齐」的窗口内；没组成快捷键的按键（和弦没凑齐/序列断链超时/tap-hold 两条无输出路径）必须按输入顺序原样回放，否则配置 `F&J`、`F9 J K` 或只设切层键后这些键永久变哑。
- **自动重复判定不能用时间窗**：同键 250ms 内两次 down 是正常输入（热串双写字母、双击连击），按时间窗会被误判成自动重复丢掉第二击；「按下未抬起集合」与真实语义一致。
- **keyup 一律观察者回调**：状态机靠抬起维护「按住集合」；被吞键的 keyup 若不同步回调，该键的抬起状态永久丢失、整个状态机卡死（键变哑）。
- **状态机拆 `engine.rs` 的动机**：这批时序逻辑互相纠缠且全是纯决策（输入事件 → 吞/放/回放/触发），与 Tauri 无耦合；拆出后用假注入单测覆盖（真实注入绝不进测试），`lib.rs` 从 ~2400 行瘦身到纯接线。
- **锁定切层 vs momentary**：`hold_layer` 按住生效（单组合场景快），`lock_layer` 长按切换保持生效（层内放和弦/序列唯一可行形态）；两者互斥、`sanitize` 裁决保留 `lock_layer`；层可达性检测同时认两种切层键，层内条目没有任何切层键指向时在冲突清单里直说「永远不会生效」。

**规则/决策**：
- **写入必须原子**：原 `fs::write` 先截断再写，崩溃 / 断电即留半截 JSON。改为「临时文件 → `fsync` → `rename` 覆盖」，任何时刻磁盘上的 `config.json` 要么是旧的完整内容、要么是新的完整内容。`fsync` 不可省——只写不刷时 `rename` 可能先落盘、数据后落盘，断电后留下空文件（「配置凭空消失」的另一条路径）。临时文件名带 pid + 序号（`create_new`），并发保存（连点保存、导入与保存同时进行）不会互踩同一份临时文件写出半截内容。
- **损坏绝不静默清空**（原行为：解析失败 `eprintln` 一句 + 回退空配置，用户随手一保存就把空配置写回磁盘 → 快捷键 / 改键 / 层 / 文本扩展「凭空消失」）：留档原文件（**改名**而非复制，后续保存盖不掉）→ 尝试 `.bak` 恢复 → **恢复成功即回写主文件**（否则下次启动还是同一个坏文件，且「主文件缺失」会被当成首次启动、告警消失）→ 都失败才空配置启动。原内容始终留在磁盘上可人工修回。
- **`.bak` 只存「上次良好副本」，损坏原件另名留档**：保存前写的 `.bak` 必须是可解析的配置——否则用户在主文件损坏期间保存一次，就把好备份的位置装进了坏内容、自愈就此断源；损坏原件用 `config.json.corrupt-<时间戳>`（带时间戳，不与上一次事故的留档互相覆盖）。这样 `.bak` 的语义始终是「从这里恢复」。（需求原文写「损坏时原名留档（`.bak`）」，实现按上述理由拆成两个名字。）
- **告警走消息中心、且必须在托盘建好之后推**：`commit_result` 会叠托盘红点，早于托盘就是 no-op；`show_output: false` 走红点而非弹窗（前端启动只 `get_command_results` + `get_unread`，此刻弹窗也不可靠，且开机自启场景不该被弹窗打断）。只 `eprintln` 到看不见的控制台等于没有告警。
- **加载路径仍只 `migrate()` 不 `sanitize_config()`**：加载时静默丢条目同样属于「悄悄改用户配置」，与本次「不静默丢数据」的原则一致；逐条清洗只留在保存 / 导入路径（原先审计把这一致性差异列为问题，现定为有意口径）。
- **`export_config` 保持 `fs::write`**：导出到用户指定路径的是导出文件、不是活配置，不加原子写、不产生 `.bak`。

**验证**：`cargo test --workspace` 全绿（壳 53，含新增 8 条：首次启动静默默认、保存-加载往返、损坏留档且原内容仍在盘上、损坏从 `.bak` 自愈并回写主文件、主文件缺失从备份恢复、损坏内容不污染 `.bak`、保存失败不留临时文件且不破坏原目标、并发保存各自独立临时文件）；`cargo check -p kada --no-default-features` 编译通过；clippy 无新增告警（仅剩 3 条既有）。**未跑 GUI**：改动是纯文件 I/O、单测覆盖全部路径；另核对本机真实配置 `%APPDATA%/com.kada/config.json` 为合法 JSON（10 条快捷键），加载不会误判损坏。实测路径：写坏 `config.json` 后重启 → 托盘红点 + 消息中心一条「配置 · 启动加载」。

**规则/决策**：
- **看门狗只「发现」，装钩子永远归钩子线程**：`SetWindowsHookEx` 装上的钩子其回调跑在**安装它的那个线程**上，所以重装也必须在那个线程做。看门狗线程只 `PostThreadMessageW` 一个自定义消息（`WM_APP + 1`），钩子线程的消息循环里识别它并落地——跨线程直接装会把回调挪到别的线程上（顺序与低延迟的前提就没了）。
- **必须「先卸旧再装新」**：钩子已被系统摘除时 `UnhookWindowsHookEx` 只是返回失败（无害）；但若旧钩子还活着而不卸就装新的，旧钩子会留在钩子链里**每个按键被处理两遍**（快捷键触发两次），比失效更难查。
- **重建时一并复位钩子层状态，并把被替换的目标键补一个 up**：重装意味着中间丢过事件，那些物理键的抬起不可能再经过我们。不复位的后果有两条且都很隐蔽：`HELD_KEYS` 里的键永远等不到抬起，自动重复判定会把它的后续**每次按下**都当成按住连发（该键彻底变哑）；`REPLACED_DOWN` 里已注入的目标键（常是 Ctrl 这类修饰键）永远收不到配对的 up，在系统看来一直按着。这一条也让 7.2-④ 的钩子层那半顺带落地。
- **装完必须把心跳重新起算**：否则「最后一次钩子事件」还停在很久以前，看门狗下一轮就把刚装好的钩子再判成失效，陷入每秒重装（每次重装都会短暂卸掉钩子、吃掉窗口里的按键）。
- **`HEARTBEAT_GRACE_MS` 必须大于 `WATCHDOG_INTERVAL_MS`**：判据里「输入够新」那一项只在输入发生在最近一个宽限内才成立，若宽限小于巡检间隔，两轮巡检之间的输入会整段落空、永远不被发现。
- **误判的方向是「多装一次」而非「漏判」**：所有阈值都取宽松侧（唤醒阈值 10s、连续的第二次触发才退避），一次多余的重装只值几毫秒的空窗，比漏掉一次真失效（快捷键全哑直到用户重启应用）便宜得多。看门狗在**闲置时一声不吭**是硬要求：判据只看「系统收下的输入」与「钩子心跳」的先后，不看绝对时间，所以没人碰键盘时两个时间戳一起停在原处、不构成失效。
- **以轮询替代原规划建议的事件订阅**：规划写的是订阅 `WM_POWERBROADCAST` / `WTSRegisterSessionNotification`。实现改为轮询，因为这两条都要在钩子线程上再建一个隐藏窗口（`WTSRegisterSessionNotification` 要 HWND；而**消息专用窗口收不到广播消息**，得建真实隐藏顶层窗口，还得引 `Win32_Graphics_Gdi`/`Win32_System_LibraryLoader` 等 feature 并管理窗口生命周期）。轮询同样能拿到「解锁」「唤醒」两个跃迁，且能在真机上验证（见下），代价是解锁最多迟 1s 被发现。
- **自愈不打扰用户**：只在 stderr 留痕 + `reinstall_count()` 计数，**不进消息中心**——用户此刻没有动作可做（已经自动修好了），弹窗/红点只会制造困惑。这与「命令结果一律记入消息中心」并不冲突：那条针对的是用户主动触发的动作。
- **已知局限写进代码注释与文档**：`GetLastInputInfo` 是键盘与鼠标**合并**的信号，「键盘钩子单独被摘除、鼠标钩子还活着」这种半边失效发现不了（心跳一直被鼠标事件喂着）。两个钩子装在同一线程、共用同一处理函数，把回调拖慢的成因对两者是同一个，通常一起被摘掉；真正的根因（把耗时操作移出回调）见 7.2-⑤，本看门狗只是兜底。

**规则/决策**：
- **复位口径：注入出去的东西收回来，缓冲里的东西一律丢弃不回放，锁定层保留**。三条各有反面教材：不收回注入的 `hold`/`sticky` → 系统层面 Ctrl 一直按着（后面敲什么都成组合键）；回放缓冲里的键 → 复位场景（钩子被摘 / 锁屏唤醒 / 切窗口）下前台目标**已经变了**，把旧按键注入到新窗口（可能是密码框、可能是别的程序）比丢掉它们更糟，用户会看到「一串莫名其妙的字符被打进当前窗口」；连锁定层一起清 → 用户显式切过去的层在 Alt-Tab 后莫名失效（锁定层与「按键抬起」无关，和 CapsLock 同理，跨前台切换应当继续生效）。
- **触发通道用轮询而不是回调（也不扩展 `HookHandle`）**：底座已经有单调递增的 `reinstall_count()`，壳层在**状态机定时器线程**上顺带看一眼就行（那个线程本来就每 60ms 跑一次、本来就要拿 `engine` 锁）。做成回调要动钩子 crate 的公开 API 并在钩子线程的消息循环里跑壳层代码，收益为零。代价是复位最多迟一个 tick（60ms），而复位本身是无声兜底，无体感。
- **前台切换必须「连续两轮看到同一个新窗口」才算**：`GetForegroundWindow` 会被瞬态窗口抖一下——我们自己的触发气泡、右键菜单、UAC 提示、桌面切换瞬间。误判的代价是**白复位一次**：用户手上正凑的和弦 / 刚按的序列 leader 会被丢掉。多等一个 tick 就能把这些只晃一轮的窗口全滤掉。另一条对称的坑是**读不到句柄时不能推进 `confirmed`**：锁屏瞬间读空、解锁回到同一个窗口，若把 `None` 当成「换了窗口」，用户每次解锁都要被白复位一次。
- **复位是无声兜底，不进消息中心**：用户此刻没有动作可做（已经自动好了），弹窗/红点只制造困惑。这与「命令结果一律记入消息中心」不冲突——那条针对用户主动触发的动作。只有真的丢了状态（`reset` 返回 `true`）才 `eprintln` 留痕，且复位原因写进日志（钩子重装 / 前台切换）。
- **Linux 两条路径恒不触发是已知受限、不是漏配**：evdev 层拿不到前台窗口（要接 X11/Wayland 协议，见 7.3-⑲），也不存在「被系统摘除后重装」。壳层照旧调用同一接口，占位实现返回 `None`/0，行为是「不复位」——比编造一个假窗口句柄安全。

**验证**：`cargo test --workspace` 159 项全绿（壳 66 / core 73 / 钩子单测 10 + 1 ignored / 钩子冒烟 1 / kada-actions 9）；`cargo check -p kada` 与 `cargo check -p kada --no-default-features` 两版通过；`cargo clippy --workspace --all-targets` 无新增告警（基线清单见下条 P1-⑦）。新增测试覆盖：按住切层键 roll 后复位要「补一个 up」且该键能重新判 hold（不卡在「已按住」）、sticky 锁定后复位也要收回、和弦待定期复位后既**不回放**又能重新凑成同一个和弦、序列待定期复位后 `tick()` 也不再回放而普通键照常放行、锁定层不被复位清掉而 momentary 层退出后回到锁定层、干净状态返回 `false`（不白刷日志）、热串缓冲被清空后不再展开。**未验证**：真实锁屏 → 解锁、真实 Alt-Tab 切换后的复位（需要真人操作 GUI 壳；`reinstall_count` 那条路径依赖看门狗判出「解锁」，其端到端验证现状见本文件 P0-① 条目）。可单测的部分（复位动作本身、前台切换判定）已全覆盖。**逐步操作（含前置配置、预期现象、判失败）见 `docs/人工验证清单.md` §1~§4。** **【2026-09-29 更新】人工验证：§1 / §2 / §3 已通过（前台切换的收回注入与热串不回放、锁屏解锁后的复位），**§4「休眠→唤醒」未执行**——见本节末「人工验证首轮」。**

##### 动作执行超时与中止（P1-⑦）

原 `run_cmd`/`run_script` 用 `Command::output()` **无限等待**：脚本挂住（等输入、死循环、弹了个看不见的确认框）就永久占住这条触发的执行线程——后续动作永不执行、线程也收不回来；同时没有任何「停止正在运行的宏」入口。

**规则/决策**：
- **中止用代数计数器，不用布尔量**：布尔量必须在「新一轮执行开始时清零」，而清零与用户按下停止之间存在竞态——停止请求落在清零之前会被下一轮吞掉（表现为「点了停止没反应」）；反过来不清零则一次停止会让之后**所有**触发一启动就自杀。改成只递增的代数、每轮开始时快照比对，两个问题同时消失：新一轮天然拿到新代数，与旧的停止请求互不干扰。这条有专门的回归（`abort_requested_before_run_does_not_stop_it`）——「点一次停止毒死之后的每一次触发」是最容易写出来的那种 bug。
- **不许用 `.output()` 无限等，且管道必须边跑边读**：`output()` 内部正是用读线程避开「写端阻塞、双方互等」的，所以手写限时循环时这一步**不能省**——子进程输出超过管道缓冲（Windows 约 4~64KB）而没人读时它写阻塞、我们等它退出，超时判定永远等不到，所谓「超时保护」就成了空话。
- **杀进程必须杀整棵树**：我们跑的是 `cmd /C <临时批处理>`、`powershell -Command`、`sh -c`，真正干活的是**孙进程**（脚本本体、被它启动的程序）。`Child::kill` 只杀直接子进程 → 命令「看起来」结束了、脚本还在后台继续跑，而且它占着 stdout 管道，连读线程都不会结束（`wait()` 之后 join 会永远挂住）。Windows 用 `taskkill /T /F`；Linux 要杀树得让子进程自成进程组（`setsid`）再 `kill(-pgid)`，**目前只 `kill()` 直接子进程，列为已知缺口**（本项的可靠性目标是「不再永久占住执行线程」，这一点已达成）。
- **反馈不假装成功**：`abort_actions` 返回的是**请求发出时**正在执行的链数量，前端据此区分「已请求停止（N 条）」与「当前没有正在执行的动作」。若只返回 `Ok(())`，用户在什么都没跑的时候点一下也会看到「已停止」，这属于假的确定性。
- **被强杀的结果要有可见的归因**：超时/中止会把原因写进 `stderr` 前缀、并把 `exit_code` 置 `None`（被强杀的进程退出码不再有语义，留着会被误读成「脚本自己返回了非零」）；真的被中止的链另外补记一条 `kind="abort"` 结果进消息中心，让「点了停止」有回应。
- **超时默认值必须「老配置也拿到」**：字段的零值语义正好是「不限时」，所以 serde 缺省和 `Settings::default()` 都走 `DEFAULT_ACTION_TIMEOUT_MS`（30 秒），不能用 `#[serde(default)]` 的零值——否则本次改动对存量用户等于没生效。

- **失败必须走「结果」这条既有通道，不要另开一套提示**：消息中心已有完整展示（卡片字段、未读红点、托盘红点、弹窗开关），失败只是同一种结果的另一个 `kind`。另开一条路径 = 用户得去两个地方看「刚才那下到底干了什么」。
- **「哪种动作失败」当标签、动作摘要当内容，两者都要**：只给类型（「文件操作失败」）在同一个快捷键挂了多个同类动作时分不清是哪一条；只给摘要则扫一眼 tab 看不出性质。摘要里变量按**本次实际取值**代入（`{target}` → `D:\nope.txt`），因为用户要认的是「刚才那一步拿什么值去做」。
- **`show_output` 沿用动作自身设置，不因为「这是失败路径」就一律静默**：命令/脚本开了「显示输出」，那它**连启动都没成功**（脚本路径不存在这类走 `Err` 而非非零退出码）同样该弹窗——否则用户会觉得「我明明开了显示输出」。
- **失败不中断后续动作（保留原语义）**：动作链是用户排的顺序，某一步失败就中止会把「这一步没成」放大成「后面全没跑」这种更大的意外。这条加了回归固定住。
- **`restart_program` 的容错继续保留**：`let _ = close_program(..)`（关闭失败不阻断重启）。「程序本来就没在运行」是靠退出码非零表达、不进 `Err`，所以这里的忽略是刻意的；`taskkill` / `pkill` 起不来属环境损坏，不为它改变重启语义。
- **失败记录不做去重 / 限流**：同一条坏动作重复触发就重复记（与命令结果一致）；真到刷屏属于 7.4-㉖「消息中心上限与截断」要解决的问题。

**规则/决策**：
- **改没改过靠「与基线签名比对」，不靠引用比对**：草稿本来就是 `cfg` 的副本（`deepClone`），引用永远不等。签名用 `JSON.stringify`，**必须把「只在保存时才读回草稿」的那些输入框算进去**（描述 / 所属层、改键的原键、长按阈值、文本扩展的触发词与替换文本）——只比草稿对象的话，改这些字段标记不亮，离开时照样静默丢，守卫等于白做。
- **脏标记用事件委托，不逐个字段插桩**：编辑页里的字段（含动态生成的动作字段、条件分支里的）数量多且会变，`input`/`change`/`click` 三个委托监听挂在编辑页容器上重算一次，比给每个 `addEventListener` 补一行可靠。程序性改动（录入触发键、录制结束、动作拖拽重排）则统一挂在 `renderActions` / `renderTriggers` / `syncRemapEditor` 末尾。
- **标记放动作行，不放标题**：快捷键标题就是行内可编辑的名称输入框（`contentEditable`），往里写「● 未保存」会让用户打字时光标跳走。这类「为了让状态可见而破坏输入」是体验修复里最典型的自伤。
- **三态而不是二态**：只给「放弃 / 取消」的话，想保留改动的人只能先取消、再手动点保存、再重新点一次那行——守卫变成路障。多出来的「保存并离开」才是这类守卫真正的价值。
- **「保存并离开」只在真的落盘后才放行**：`save()` 原本返回 `void`，失败只 toast 一句；若不改成返回成败，守卫会把「保存失败」也当成「已保存」然后放行，用户的改动就此丢掉。同理，改键「没设任何输出」这种被判无效的草稿也返回 `false` 停住，`toast` 说明原因、人留在编辑页。（与 P1-⑥「不假装成功」、P1-⑦「`abort_actions` 如实返回数量」是同一条原则。）
- **保存落盘改存草稿副本**：原先 `cfg.shortcuts[selected] = draft` 存的是**同一个对象**，保存后继续在编辑页改会直接改到内存里的 `cfg`（列表与冲突检测读的都是它），表现为「还没点保存，列表已经变了」，也让「撤销」无从实现（草稿改了 `cfg` 也跟着改）。改为 `cfg[...] = deepClone(draft)` 后两者各自独立。
- **保存要把列表「启用」开关的现值带过去**：`enabled` 只有列表行的开关能改，编辑页里没有这个控件。存副本后草稿里的 `enabled` 是打开时的旧值，保存时若照抄就会把用户刚点的开关**静默翻回去**——这是「存副本」这个改动引入的新风险，必须一起处理。
- **确认框打开期间，后来的离开请求按「取消」处理**：连点两行会同时进来两次 `confirmLeaveDraft`，若第二次覆盖掉 `unsavedPending`，第一次那次点击的 promise 永远不 resolve，那一次点击就永久挂住。宁可丢掉重复请求，也不留悬挂的 promise。
- **窗口关闭不设守卫**：`on_window_event` 里 `CloseRequested` 是 `prevent_close()` + `hide()`（托盘常驻），WebView 与草稿都还在内存里，关窗**没有可丢的东西**。加 `beforeunload` 反而可能挡住托盘「退出」（隐藏窗口里弹一个没人能点的原生对话框）。守卫只该拦真正会丢数据的那几个动作。
- **不做 `Ctrl+Z`**：撤销是「整份草稿回到上次保存的样子」这一个语义（按钮「撤销改动」说得很清楚）；接 `Ctrl+Z` 会和文本输入框自带的行内撤销打架，那是另一件事（7.3-⑮ 键盘可达性里再谈）。

**验证**：`npm --prefix ui run build`（tsc + vite）通过。**行为验证在纯浏览器演示模式（`ui/src/mock.ts`）逐条跑过**——打开条目（无标记）→ 改描述（标记亮、撤销可用）→ 点另一行（弹三态框）→「继续编辑」（留在原条目、仍是脏）→「撤销改动」（描述还原、标记熄灭）；「放弃改动」→ 切到另一行且改动丢弃；脏时点侧栏「改键」（弹框，框内文案带条目名）→ Esc 取消（留在原页）→ 再切 →「放弃改动」（切页成功）；改键页改「原键」（本页标记亮、快捷键页的标记正确保持隐藏）→「撤销改动」（还原 `CapsLock`）；「保存并离开」（切到目标行；**重新打开原条目确认改动真的进了 `cfg`**）；**列表开关不被草稿旧值盖掉**（先在列表停用该条目 → 编辑描述 → 保存 → 重开：`enabled` 仍为停用）；「取消」与「×」同样弹框（继续编辑留在页内 / 放弃改动则关闭编辑页）；新增条目（空白不脏 → 改一下变脏 → 再点「+ 新增」弹框 → 放弃后回到空白新条目）；文本扩展页同上；**保存失败不放行**（清空改键全部输出 → 保存并离开 → 仍停在改键页 + toast「请至少设置一种输出…」）。排版用计算样式与几何核对（标记 65×25 胶囊不压住「撤销改动」、确认框 460px 居中、三按钮齐全、遮罩半透明）。**未验证**：Tauri 壳里的真人点击（需要跑起 GUI 壳；本机验的是同一份 `main.ts`，差别只有 `mock.ts` 换成了真 IPC 与原生文件对话框）。逐步操作见 `docs/人工验证清单.md` §9。

##### 危险操作确认与导入方式（P1-⑨）

两处「安全级别不一致 / 说一套做一套」：**① 删除单条内容没有确认**——删除目录、删除层会弹 `ask()`，而同为破坏性操作的删除快捷键（列表行三点菜单 + 详情页按钮）、删除改键 / 文本扩展点了就没了，且详情页那一条还会连带丢掉未保存的草稿（P1-⑧ 的守卫只管「离开」，不管「删除」）。**② 导入是静默的全量替换**——`ui/src/main.ts` 点一下按钮就把整份配置换掉（含开机自启、快速唤醒键等设置），提示文案只说「清洗无效项」；`import_config` 也只回一个忽略条数，被跳过 / 被清洗掉的条目用户根本查不出是哪条。两者都属 P0-② 那条「用户的配置不能被悄悄改掉」的延长线，按数据安全处理。

**规则/决策**：
- **合并只增不删，且不跑清洗**：清洗会顺手丢掉用户手里那些不合规的老条目，「导入」就成了「导入顺便帮你删东西」。合并的职责就是把外来条目并进来，现有配置一个字不动（要覆盖就用替换）。
- **合并永不制造新冲突**：改键按 `from`、文本扩展按 `trigger`、快捷键按**触发键有交集**判「同一条」，撞车时保留现有的、跳过导入的并**逐条报出**。否则用户导入同事的配置后会莫名多出一堆自己没配过的红冲突；副作用是重复导入同一份文件天然幂等。代价是「导入更新版」不会覆盖旧条目——那条路留给「替换」，且在选择框里就说清了。
- **合并保留本机设置**：`settings` 里的开机自启、快速唤醒键、动作超时都跟机器强相关，导入别人的配置不该悄悄改掉它们。要连设置一起换就显式选「替换」——这也是选择框必须存在的理由之一。
- **替换导入前必须留档，且是复制不是改名**：`replace` 是这个应用里唯一能一次换掉整份配置的操作，`config.json.bak` 又会被**下一次保存**覆盖。留档成 `config.json.pre-import-<时间戳>`（复制，主文件随后才被覆盖；同一秒加序号）才是能长期握在手里的回滚点。留档失败不中断导入（`.bak` 仍是兜底），但要在结果里说出来。
- **导入结果从「一个计数」改成「逐条明细」**：只报个数的后果是用户查不出是哪条没进来，也分不清「合并跳过」与「解析失败丢条目」。明细直接决定用户下一步动作（去改名、去删旧的、还是干脆改用替换），属于功能而不是装饰。
- **删除确认只问「已保存的内容」**：未落盘的新增项删除等同「取消」，没有已保存的东西会丢——也弹框只会训练用户无脑点确认，把确认框本身变成噪声。同理文案要带上「删的是哪条」（快捷键名称、无名时退回触发键；改键 `原键 → 摘要`）与「正在编辑那条的未保存改动会一并丢」，否则确认框等于没问。
- **演示模式的桩也要按真实返回类型写**：`ask()` 拿到的是按钮文案不是布尔，桩返回 `true` 就让演示模式里**所有确认框静默变成「否」**——看起来像「删除功能坏了」。桩失真会把验收引到错误结论上（7.3-⑯ 就是这根线索的正式立项）。

**规则/决策**：
- **按内容指纹比对，不按 `mtime`**：`mtime` 粒度粗（FAT 系 2 秒）、同步客户端可能保留原时间戳、还会被「同一秒内改两次」骗过去；配置文件只有几 KB，整份读进来哈希最省事也最准。同理**语义相同不算改动**（编辑器重新排版、`migrate()` 补字段都会让字节不同而配置相同）——解析出来 `Eq` 内存那份就静默放过，否则红点会为「只是重新保存了一次」白闪。
- **监听路径绝不碰磁盘**（这是本项最容易做错的地方）：启动路径 `load` 的损坏自愈（留档 + 从 `.bak` 回写）在启动时是对的，搬到运行期就变成「用户正拿编辑器改 JSON，中途保存出来的半截内容被判成损坏 → 文件被改名挪走 → 旧备份盖回来」，等于监听功能主动毁掉用户的编辑。所以运行期只走新增的 `read_only`：能解析就采纳、解析不动只提示一次、磁盘原样不动（用户修好后指纹变了自然重新解析）。配套：文件消失也保持现状（既没内容可采纳，也不该清掉用户正在用的配置）。
- **自己的写入必须销账，而且要与写盘同持一把锁**：`set_config` / `import_config` 写完盘调 `adopt_own_write` 把新内容认成已知基线；若只在写完之后销账，巡检线程可能正好插在「写完」与「销账」之间，把应用自己刚写的配置当成外部修改再加载一遍（白记一条消息、白复位一次状态）。因此「写盘 + 改内存 + 销账」三件事同持 `cfg_watch`，而巡检线程的「判定 + 采纳」也用同一把锁。
- **采纳 = 换内存 + 换引擎状态 + 同步自启 + 留痕 + 广播**：外部改动的意义就是「生效」，所以替换 `state.config`（`get_config` 与钩子查表随即反映新内容，下一个应用内保存也不会再盖回去）；整份换配置后旧的时序状态（按住式层、待定和弦、注入中的修饰键）没有意义，置 `cfg_stale` 让状态机线程走 `Engine::reset`（口径与钩子重装 / 前台切换一致：注入的收回来、缓冲的丢弃不回放、锁定层保留）；开机自启变了才同步系统一次（不做无谓的注册表写入）；记一条「配置 · 外部修改」进消息中心并报出各类条目数量（用户据此确认「生效的确实是我写的那份」）；广播 `config-changed` 让界面重绘。
- **巡检用轮询而非订阅文件系统事件**：与钩子看门狗、`ResetWatch` 同一取舍——不引依赖、不写平台分支、不用管编辑器「先写临时文件再改名」与同步客户端的各种怪癖；代价只是慢一拍（1 秒），对「手改配置」这个场景无感。
- **界面刷新不能静默丢掉未保存草稿**：外部改动会把界面的 `cfg` 整份换掉，若用户正在编辑页改东西，这与 P1-⑧ 挡住的「切页/点另一行」是同一类损失。所以复用同一套口径——**有未保存改动**先弹两态框（「加载新配置」/「保留我的改动（下次保存会覆盖外部改动）」），两个按钮各自写明后果，绝不替用户决定；只是**打开了编辑页却没改**（干净草稿）就不问、直接关掉，因为留着反而危险：外部内容里的同一下标可能已经是另一条，草稿一保存就写到别人身上去。

**验证**：`cargo test --workspace` 全绿（kada-core 79 / 壳 **75**（68 → 75，新增 `config_watch` 7 条）/ kada-actions 14 / 钩子 10 + 1 ignored / 冒烟 1）。新增 7 条单测覆盖：基线静默 / 外部改动报一次后采纳 / 自己的写入不算外部修改 / 走 `config_io::save` 的真实时序 / 只换排版不算改动 / 坏内容只提示一次且磁盘未被动过 / 文件消失保持现状再出现即采纳；`cargo check -p kada`（含 `--no-default-features` 基础版，零告警）、`npm --prefix ui run build`（tsc + vite）均通过。**未验证**：壳层巡检线程与 Tauri（`config-changed` 事件、托盘红点、消息中心）、`set_config` 与监听线程共用一把锁的时序、界面两态确认框、以及「外部改动后真的生效 / 应用内保存不再覆盖」这类端到端行为——逐步操作见 `docs/人工验证清单.md` §11。

**规则/决策**：
- **等待窗的取值只有一份真相**：窗口直接读 `Config::settings`，不再各存一份到 `SequenceState` / `ChordState` 里。存一份的代价是要在「保存配置 / 导入 / 外部修改采纳」三条路径上都记得同步过去，漏一条就变成「面板上改了、实际还在按旧值跑」；直接读配置则改完立刻生效。代价是 `Engine::tick` 要收 `cfg`——壳层定时器线程因此必须在拿 `Engine` 锁**之前**取配置读锁（钩子回调路径也是「先配置、再引擎」，顺序反过来会死锁）。
- **和弦等待窗是「回放」不是「丢弃」**：旧实现的超时丢弃正是让 `F&J` 的成员键永久变哑的元凶（吞键铁律的那次改造把窗口一并删了）。这次补回来时复用「成员全部抬起」那条回放路径（`replay_pending` 把待定键按输入顺序 `tap` 出去、仍按住的记入 `settling` 抑制自动重复），所以键一个都不会少。
- **窗口的起算点是「最后一次成员键动作」，被吞进缓冲的其它键不刷新它**：这是本项唯一不显然的取舍。若让「有键被吞进缓冲」也刷新，用户一直打字就能把回放无限推后——而「按住成员键期间打的字被压着」恰恰是这个窗口要治的症状，刷新等于把药停掉。窗口过期后成员键定论成普通按键，晚按的另一个成员**不再凑成和弦**（会各自回放）——这是时间窗的固有代价，也是它可配的理由。
- **默认值 1000ms（而不是「默认不限时」）**：序列沿用原常量，和弦沿用被删掉的那个窗口值（1000ms），等于把 7.3-⑫ 当年「先复用 1000ms」的意图接回来。**行为变化要说清**：和弦从此有默认 1 秒窗口，两个成员相隔超过 1 秒的「慢和弦」不再触发（按普通按键回放）；需要这种用法就把窗口调大或填 0（= 不限时，即改造后一直以来的行为）。
- **`0` = 不限时，两个字段同一口径**：与「动作超时」（`action_timeout_ms`）一致，`0` 是有效的「关掉这个窗口」取值，不是缺省值——所以 serde 缺省必须显式给 1000（`#[serde(default)]` 的零值会让老配置**静默**变成不限时，等于偷偷改用户行为），core 里那条 `0` 往返用例就是钉这个的。序列的不限时语义是「一直等，直到断链或命中」；和弦的是「等成员全部抬起才定论」。
- **UI 按毫秒而不是秒**：`action_timeout_ms` 用秒（默认 30 秒）没问题，但 1000ms 这种亚秒粒度用秒表达不了（500ms 只能填 0.5，取整后就没了）。两个输入框的兜底与「动作超时」同一口径：负数 / 非数字按 `0` 处理，并在显示时对缺字段的老配置补 1000，避免输入框空白。

**验证**：`cargo test --workspace` 全绿（kada-core **82**（79 → 82，新增 `settings_timeout_tests` 3 条）/ 壳 **80**（75 → 80，新增等待窗 5 条）/ kada-actions 14 / 钩子 10 + 1 ignored / 冒烟 1）；`cargo check -p kada` 与 `cargo check -p kada --no-default-features`（基础版）、`npm --prefix ui run build`（tsc + vite）均通过。新增单测覆盖：默认值随常量 / 老配置缺字段取 1000（不是 0）/ `0` 往返不被盖回、序列窗口取自设置（5000ms 内不回放）/ 序列 `0` = 不限时（且 `F9 J K` 仍能命中）/ 和弦窗口到点按输入顺序回放 `F A` 且过期后 `F`、`J` 不再凑和弦 / 过期同样可由下一个事件懒判 / 和弦 `0` = 不限时（相隔 10ms 仍算和弦）。**未验证**：真实按键的时序手感（1 秒窗口在真人手上是什么感觉）、设置页输入框 → 落盘 → 引擎生效的整条链路、外部手改这两个字段后的生效，以及「老配置缺字段」在真机上的行为——逐步操作见 `docs/人工验证清单.md` §12。

**规则/决策**：
- **透明浮窗必须 `focusable(false)`（本轮最硬的一条约束）**：`toast` 与 `hud` 都是置顶透明小窗，会被反复 `show()`。`focused(false)` 只在**首次**显示时用 `SW_SHOWNOACTIVATE`（tao 实现：`MARKER_DONT_FOCUS` 用完即清），之后退回 `SW_SHOW`，也就是说**第二次显示就可能把焦点抢走**。抢走焦点的后果不止打断打字：`GetForegroundWindow` 会变成我们自己的浮窗，① 前台条件（前台应用 / 窗口标题）全部读错；② `ResetWatch` 的「前台窗口切换」判定命中 → `Engine::reset` → 按住的 momentary 层被踢掉、注入的修饰键被收回——**正好是「按住切层键期间弹出指示窗」这个必经路径**。加 `.focusable(false)`（Windows = `WS_EX_NOACTIVATE`）后窗口永不被激活，这三件事一起解决。顺带把 `ensure_toast` 也补上：触发气泡每按一次快捷键就 show 一次，第二次起就在抢焦点（此前没人报，是因为抢完用户再点回来也没留下线索）。
- **在定时器线程上推送，钩子回调一行都不改**：状态变化来自按钮、但推送动作（动托盘、建窗、发事件）绝不能进回调——那等于把整个输入层挂在界面上（回调超时会被系统摘钩）。定时器线程本来就在 60ms 一拍地跑状态机，顺带比一次快照几乎零成本；代价是**指示最多晚 60ms**，对「看一眼状态」完全无感。这也是快照要能 `==` 的原因（`BTreeSet` 转 `Vec` 而非 `HashSet`：迭代顺序固定才比得准、才不抖）。
- **建窗那一步另起线程，不占着定时器线程**：`publish_status` 里真正重的只有「建 WebView」——首次要上百毫秒。而这条定时器线程正是 `Engine::tick` 的落地处（序列 leader 超时回放、和弦等待窗超时回放、连击等待窗提交），占住它等于让**已经被吞掉的键**晚几百毫秒才补回给用户。所以托盘提示、隐藏、存载荷都就地做完（都是廉价调用），只有「建窗 + `emit`」交给 `std::thread::spawn`——与触发气泡完全同一条约定（`show_toast` 也是在 spawn 里调 `ensure_toast` 的）。这次 emit 晚到不会导致错显示：`hud_ready` 会再查一次当前载荷，过期就把窗藏回去（见上一条）。
- **暂停 / 录制期间照常推状态**：原来 `spawn_engine_ticker` 在暂停与录制时 `continue`，本次改成仍取快照推指示、只是不推进状态机。理由：暂停不影响「已经按住的层还在生效」这件事——指示跟着消失反而制造了一个新的误会（用户以为是暂停清掉了状态）。录制期间同理（录制只让事件不进状态机，不改已注入的修饰键）。
- **指示开关参与变化比对**：`last_status` 存的是 `(载荷, 开关)` 对。否则用户在锁定层生效期间关掉悬浮指示，得等到下次状态变化才真的消失——而锁定层可能一直开着，等于「关了没反应」。
- **悬浮窗尺寸/位置由前端量完回报（`hud_ready`）**：窗口宽度取决于内容（层名 + 几条修饰键），位置又取决于宽度（贴底部居中），所以只能等前端渲染完再定；`hud_ready` 里再查一次「状态是否已过期 / 指示是否被关掉」，否则量尺寸的几十毫秒里状态结束了，反而会把刚藏起来的窗又亮回来。尺寸钳 120~900 × 24~240，异常值不至于把窗口撑满屏幕；层名超长在 CSS 里省略号截断。
- **托盘提示不设开关、悬浮窗设开关**：托盘提示零成本且只在悬停时可见，没有关掉的必要（关掉反而让人以为功能没了）；悬浮窗会在锁定层期间长期占据屏幕底部，必须给一个关掉的出口，所以进 `Settings`（默认开——默认关等于这项功能对大多数人不存在）。
- **长按锁定层的指示常驻是「有意」而不是 bug**：锁定层生效期间基础层按键被遮蔽，用户此时最需要知道「现在是哪一层」；设置页文案把这句写清楚了（否则用户会去反馈「有个小条赖在屏幕上不下去」）。

**规则/决策**：
- **`oneshot`/`sticky` 的值域是任意键，集合存 `Key`**：原先 `arm_oneshot`/`toggle_sticky` 用 `key_as_modifier` 判一下，非修饰键的值被**静默丢弃**——配置里写了「单次 A」，运行时什么也不做，用户看到的是「配了没用」（同 §3.16 那类隐蔽故障）。改存 `Key` 后语义统一为「替你按住这个键」：修饰键是常见用法（下一次按键带 Ctrl），非修饰键就是「按住它到下一个键按完」（侧键粘滞 = 按住说话）。`EngineStatus` 一并存 `Key`，指示才不会因为「只认修饰键」而整条消失。
- **只有修饰键才参与后续键的 `Shortcut.mods` 补全**：`ModsState::mods()` 从全部注入键里 `filter_map(Key::as_modifier)`。非修饰键补不进 `Shortcut.mods`（那是修饰位集合），也不该补——`A` 的「按住」是通过真实的 down/up 事件表达的，不需要也不应该混进 mods。
- **武装的键自己再按下不算消费，且不重复注入**：oneshot 的消费时机是「下一个**非修饰键**抬起」，若武装的恰好是非修饰键（`A`），它自己那一下抬起会被当成「用掉了」，等于按住它之后立刻松开——所以消费条件加 `!mods.oneshot.contains(key)`。同时 `arm_oneshot` 对「已在武装中」直接 return：同一个键连发两次 down 会被目标程序看成连按两次。
- **和弦成员的 `mods` 语义是「凑齐那一刻必须按住的修饰键」**：把成员表示成完整 `Shortcut` 而不是裸 `Key`，是为了复用现有的类型与 `format_shortcut`（显示原样回到 `Ctrl+Alt`），也让 `Ctrl+F&J` 这种「要求整段按住 Ctrl」自然可表达。判定时刻是**某个非修饰键成员按下那一刻**（只有那一刻才调 `press`）——这就是「纯修饰键成员」必须配至少一个非修饰键成员的原因：没有可吞的键，就没有判定时机。
- **修饰键成员从不被吞、也不进按住集合**：它们只表示「要求按住」，其状态由钩子层给的 `mods` 表达。吞掉修饰键会破坏全局组合（`Ctrl+Alt+Tab` 退化成 `Ctrl+Tab`）；登记进按住集合则会让「按着 Ctrl 打字」时把每个字母都压进待定缓冲。core 的 `press` 另挡一道（收到修饰键直接 `NoMatch`），保证集合里只有非修饰键——即使壳层将来改错也不会静默污染。
- **和弦判重按「排序后的 `(成员键, 修饰要求)`」**：`F&J` 与 `J&F` 等价（无序），但 `F&J` 与 `Ctrl+F&J` 是**两条不同的触发键**（后者多一个修饰要求），不能再按「成员键集合」判重。
- **和弦间的软冲突是「一个的要求被另一个全覆盖」**：成员更少、或成员键相同而修饰要求更宽的那个**必然先凑齐**，更严的那条永远轮不到。判 `Warn` 而非 `Error`——两边都是合法配置，只是有一条不生效（口径与「层可达性」警告一致）。「成员更少必然先凑齐」与书写顺序无关，单列一条判据；「成员键相同、只差修饰要求」则同一刻凑齐、靠列表靠前先判到，故只在「更宽的写在前面」时报（写反了则两条都可达，不报）。
- **UI 全键下拉要能兜住手写值**：`fillKeySelect` 原先只把表里的键填进 `option`，若 `value` 是表外的别名（配置里手写 `Escape`，而表里是 `Esc`），`sel.value = value` 会落空——下拉显示空白，用户一保存就把这个值丢掉。补一个 `value` 不在表里时追加同名选项的分支。
- **和弦录入把修饰键写在第一个成员上**：语义上「修饰要求」是「凑齐那一刻按着它」，与写在哪个成员无关，所以写在第一个成员上最简单（也便于阅读）；后端只看「凑齐那一刻的 `mods`」。

**规则/决策**：
- **tap 必须装在会话级（`kCGSessionEventTap`），不能图「最早看到」去装 HID 级**：`CGEventTapCreate` 在 HID 位置**只有 root 建得出来**（Apple `CGEvent.h`：「Only processes running as the root user may locate an event tap at the point where HID events enter the window server; for other users, this function returns NULL」）。装错位置的后果不是「少收几个事件」，而是**每个普通用户**都建不出 tap → 每次启动都走「输入层起不来」这条分支、快捷键与改键全废。会话级是辅助功能权限覆盖得到的最前一层，仍早于窗口服务器把事件派发给应用，吞键 / 改键效果一致；代价只是我们自己注入到 HID 的事件会顺流经过这个 tap，靠注入识别放行。
- **注入识别留两条判据（Private 事件源 ∪ 创建者 pid == 本进程）**：判据①（`kCGEventSourceStateID == kCGEventSourceStatePrivate`）依赖一条系统行为——「Private 源造出来的事件，读它的 state id 字段就是 -1」——而**本仓库开发机是 Windows，这条行为在开发机上没有任何办法验证**。它一旦不成立，放行判据失效的后果是自己注入的 ⌘V 被自己当成按键处理（用户恰好绑了 ⌘V 就是无限触发）。判据②（`kCGEventSourceUnixProcessID == getpid()`）只多读一个整数，且**不可能误伤硬件事件**（硬件事件由窗口服务器创建、其它应用注入的带它们的 pid），两条取或等于白拿一层保险。边界用纯函数 `looks_injected(state_id, creator_pid, self_pid)` 钉住（4 条断言），端到端那条只断言「本进程造的事件必须被认出」、不锁死靠哪一条认出来。
- **AX 属性名用字面量、不链 `kAX*` 符号**：SDK 里 `kAXTitleAttribute` 这类名字，有的版本是 `#define ... CFSTR("AXTitle")` 宏、有的是导出的 `CFStringRef` 变量。写成 `extern static` 时，宏那种情况是**链接期**未定义符号——而 macOS 的链接在开发机上跑不了（`cargo check` 只做类型检查，看不出这类问题），只会在真机或 CI 的 macOS job 上炸。属性名本身是稳定 ABI（`AXFocusedApplication` / `AXFocusedWindow` / `AXTitle` / `AXTrustedCheckOptionPrompt`），直接造句既省事、又少一处「只有真机才能验」的隐患。
- **AX 返回值先验类型再当字符串用**：`AXUIElementCopyAttributeValue` 返回的是 `CFTypeRef`，只有文档承诺是字符串的那些属性才是 `CFString`；类型对不上时按 CFString 去解析是**未定义行为**（不是报错、是崩）。窗口标题这条路径跑在「前台窗口」条件求值与 60ms 巡检线程上，崩一次就是整个应用没了，故加 `CFGetTypeID(value) == CFString::type_id()` 这道闸（`ax_string`：类型不符就释放并返回 None）。
- **`hooks_supported()` 在 macOS 是「运行时授权」而不是「编译期能力」**：值就是 `AXIsProcessTrusted()`。没授权时如实报 false，用户看到的是「要授权」而不是「录了半天一片空白」；录制入口的文案也随之换成授权指引（`RECORD_UNAVAILABLE`）而不是「当前平台暂不支持」——后者会让用户彻底放弃。
- **macOS 上「输入层起不来」不让 setup 失败**：与 Windows / Linux 的门槛相反（那边起不来是异常，让 setup 失败、用户能看见报错）。macOS 的 tap 要用户去系统设置里手动授予辅助功能权限，而**首次启动必然没权限**——若让 setup 失败，应用根本起不来，用户连设置页都进不去、也就永远拿不到那份权限。故改为照常启动 + 把「系统设置 → 隐私与安全性 → 辅助功能 → 勾选 Kada（改完要重启 Kada）」记进消息中心（`start` 已经顺手弹过一次系统授权框）。
- **前台上下文的粒度是「应用」不是「窗口」**：AX 的 `AXFocusedApplication` 给的是前台应用的 pid，用它做「前台切换 → 复位输入状态」的变化检测时，同应用内换窗口不触发复位——风险小得多（被吞的键仍落在同一个进程里）。窗口**标题**仍取（供「窗口标题包含」类条件），只是不参与变化检测；`CGWindowList` 那条能拿到窗口级信息的路径要「屏幕录制」权限，比辅助功能更难拿，故不用。
- **投递事件到 HID 位置不需要 root（与「建 tap」的要求相反）**：`CGEventPost(kCGHIDEventTap, ..)` 是合成按键的常规做法，普通进程即可；发出的事件仍会经过我们自己那个会话级 tap，靠注入识别放行。每发一个键都把「当前该带的修饰位」显式写进事件 `flags`——注入的修饰键虽然会更新系统状态位，但同一批事件里的后续键不该依赖那个时序（`⌘V` 的 V 必须自带 Command 位，否则部分应用读 flags 时看不到修饰键）。
- **开发机（Windows）对 macOS 的验证边界**：`cargo check --target aarch64-apple-darwin` 能查 `kada-core` / `kada-hook` / `kada-actions`（纯 Rust 依赖，可 `--all-targets` 连单测与 examples 一起查），**查不了 Tauri 壳**（`ring` 要真 `cc`/clang）。所以壳层的 macOS 分支改了之后要么逐处人工核对，要么等 CI 的 `macos-latest` job；而**链接期问题、运行时权限、真实系统行为**这三类永远只能真机或 CI 验——遇到这类判断，代码里要写明「开发机验不了」，并尽量留一条不依赖未验证假设的兜底路径（注入识别那两条判据就是照这个原则加的）。

**验证**：`cargo test --workspace` 全绿（kada-core 92 / 壳 94 / kada-actions 14 / 钩子 10 + 1 ignored / 冒烟 1）；`cargo check -p kada`（完整版）与 `cargo check -p kada --no-default-features`（基础版）通过；**macOS 目标的交叉检查**：`cargo check -p kada-hook --target aarch64-apple-darwin --all-targets`（含单测与 examples）与 `cargo check -p kada-actions --target aarch64-apple-darwin` 通过——`aarch64-apple-darwin` 目标早已装好，这两个 crate 的 macOS 依赖（core-foundation / core-graphics / arboard）都是纯 Rust，所以这两条**真能编到 `macos.rs`**；为确认不是缓存假绿，往 `macos.rs` 里故意插了一个不存在的符号验证它会报错，再还原。新增/调整的单测：`injected_events_are_recognizable`（本进程从 Private 源造的事件必须被认出）、`injection_guard_boundaries`（两条判据的边界：Private 源 / 本进程 / 二者皆非）。**未验证**：整条 macOS 链路尚无真机验证——授权流程、真机按键（快捷键 / 改键 / 序列 / 和弦 / 层 / 文本扩展 / 录制）、AX 前台条件的实际取值、CI 的 macOS job 实跑（那里只是把 `macos-latest` 加进了矩阵）。逐步操作见 `docs/人工验证清单.md` §15。**为什么只能人工跑**：同 §13/§14，低层钩子与事件 tap 都忽略合成事件，合成按键驱动不了状态机。

**规则/决策**：
- **Linux「起不来」改照常启动（对齐 macOS）**：起不来几乎都是权限没配好，不是代码异常——「setup 失败、应用报错退出」让首次装机的用户死路一条（设置页进不去、指引看不到）。改为照常启动 + 错误串（带可照抄命令）进消息中心；修好权限重启即可。Windows 保持失败退出（那边起不来是真异常）。
- **错误分诊按「用户下一步动作」组织**，不按技术分类：`EBUSY` → 关掉别的工具（不是加权限）；文件在却枚举不到 → 加 input 组（evdev 对无权限设备在枚举阶段就静默跳过，这是「看得见文件 ≠ 打得开」的坑）；`/dev/uinput` 缺失与无权限是两条命令（`modprobe` vs udev 规则），混在一起用户会执行错的那条。
- **设备丢失复位对齐 Windows `reset_runtime_state` 口径**：被替换、已注入的目标键**先补 up 再清表**（否则系统里那个键永远按着）；`reinstall_count()` 复用 Windows 的通道与语义——壳层 `ResetWatch` 轮询计数复位 `Engine`，一行不用改就接通。热插拔**重扫**（拔了再插自动恢复监听）刻意不做（7.4-㉜），本次只保证「丢了不误判」。
- **鼠标钩子的边界是有意收窄**：触摸板 / 触摸屏 / 指点杆一律不抓——evdev 抓取是设备级的独占，多点触摸与 ABS 协议在「翻译成 KeyEvent 再转发」的模型里表达不了，抓了等于整个触摸板失灵。判定用 `INPUT_PROP_*` 属性（新内核）+ `BTN_TOOL_FINGER`/`BTN_TOUCH`（老内核兜底）双保险。代价：这些设备的中键/侧键不能作触发键，文档已写明。
- **`PlatformCaps` 分 `listen` / `inject` 两张表**：同一颗键可能「听得到但注入不了」（未来某些平台），分开报才能给对提示文案（「不会触发」vs「没有输出」）。平台扫描只报 `Warn` 不拦保存——配置是跨平台同步介质，在 A 平台不生效不代表配置错了。
- **`fetch_events` 先 collect 再 match**：evdev 的 `fetch_events(&mut self) -> Result<FetchEventsSync<'_>>` 返回的迭代器借住 `devices[i]`，match 臂里的 `devices.remove(i)` 是第二次可变借用（E0499）。旧代码能过 CI 说明当时锁的 evdev 版本迭代器实现不同；显式 collect 把生命周期切断，不依赖库内部实现细节。

**验证**：`cargo test --workspace` 全绿（壳 94 / core 100（含平台扫描 8 条新测试）/ actions 14 / hook 10 + 1 ignored / 冒烟 1）；`cargo check -p kada-hook --target x86_64-unknown-linux-gnu --all-targets` 完整版与 `--no-default-features` 基础版、`-p kada-actions` 同 target、`-p kada-hook -p kada-core -p kada-actions --target aarch64-apple-darwin --all-targets`（darwin 回归）、`cargo check -p kada`（完整 / 基础）、`npm --prefix ui run build` 全部通过。**未验证**：Linux 无真机——权限分诊实际输出、鼠标键触发/改键/注入、拔设备复位、触摸板跳过判定、REL 转发的滚轮手感，都只能在 Linux 真机或 CI ubuntu job 上验；`cargo check` 只覆盖类型与借用正确性。建议 CI（当前三个未 push 的提交 + 本次一起 push 后）重点看 ubuntu job

- **尺寸由前端量、位置只在首次摆**：内容随快捷键条数与字号变（同 `hud_ready` 套路）；`hints_placed` 之后的重排/缩放不再重定位，否则会把刚拖到的位置弹回去。还原时保存的位置不在任何显示器工作区就回主屏右侧（配置是跨平台同步介质，双屏拖到副屏再同步到单屏不能落在屏外）。
- **拖动不落盘、松手记一次**：拖动中每帧写盘既慢又浪费；`hints_move` 只动窗口，`hints_commit` 一次记下。
- **四个可见性入口必须对齐**（窗口 × / 设置页 / 托盘菜单 / 替换导入）：统一走 `apply_hints_visible`，否则会出现「菜单勾着、窗口却没了」这种查不出原因的错位。
- **`config-updated`（应用内写盘广播）与 `config-changed`（外部改动）语义分离**：提示框窗口据前者重画，主界面只取 `settings.hints`（不整份 `syncSettings`——那会盖掉用户正在输入的字段）；后者会触发未保存草稿确认，不可混用。
- **两个 CSS/布局坑（浏览器实测抓的）**：① CSS 变量只能由 JS 设在 `:root`，在 `.hints-panel` 里再声明一次默认值会**遮蔽继承值**（症状：变量已变、字体死活不动）；② 列表上限不能用 `100vh`——窗口高度正是按内容量出来的，用 vh 做上限 = 「量出高度→撑大窗口→上限变高→再量更大」的自增长循环，改按 `window.screen.availHeight` 算。
- **规划号取 ㊳**：㉖ 已被「消息中心上限与截断」占用，文档已连续用到 ㊲——引用规划号前先扫一遍文档里的圈号。

**验证**：`cargo test --workspace` 全绿（core **105**（101→105）/ 壳 95 / actions 14 / hook 11+1）；`cargo check -p kada` 完整版与 `--no-default-features`、`npm --prefix ui run build` 通过；浏览器 `#hints`（mock）实测滚轮钳制与长列表上限；**真机实测**（临时 identifier + 隔离配置起 debug 实例）：窗口按持久化的 105% 字号量出 287×242 → 落成 307×262 并停在上次保存的位置，拖动 / 滚轮 / × 全部落盘、重启后 `visible=false` 不再建窗。**待人工复跑**：托盘菜单勾选项、多显示器跨屏拖拽（`docs/人工验证清单.md` §18）。

**规则/决策**：
- **设备标识只 Linux 有真值，其余平台用 `PlatformCaps` 如实标注**：不去猜、不造假 id——Windows/macOS 上 `DeviceIs` 恒走「否则」分支，`get_conflicts` 报 `Warn`（不拦保存，配置跨平台同步可能挪到 Linux 用）。这与「前台条件在 Linux 恒不成立」的处理同一套机制。
- **设备在回调线程上同步取、不放后台线程**：`current_device()` 是「最近一次事件的设备」，`fire` 一 spawn 到线程里再读就可能被下一个事件覆盖（前台窗口那边可以容忍这点、设备不行——一台键盘按下的瞬间另一台的键插进来就会读错）。取到的 `String` move 进线程。
- **`current_device` 用 evdev 设备名而非设备路径**：路径会随插拔 / USB 口变化，名字更稳、也更贴近用户在界面里能认出来的东西；代价是**同名设备无法区分**（已知边界）。匹配沿用前台进程名那套「不区分大小写、含 `*`/`?` 走通配、否则子串」，用户不必抄全名。
- **范围边界（有意）**：设备条件只作用于 `If` 动作，**不做**触发时门控（`ShortcutItem` / `Remap` 的 `when` 字段是后续）——同一快捷键能按设备走不同分支，但「同一物理键在不同键盘上触发不同条目」暂不支持；改键更无法按设备区分。文档已写明。
- **mock 的桩要与演示配置自洽**：冲突文案引用的触发键 / 层名必须在演示配置里真实存在，否则又是一个「看着像坏了」的假象；更新事件必须自己推（演示模式没有后端事件源）。

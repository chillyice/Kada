# Kada 人工验证清单

> **这份文档解决什么问题**：Kada 有一批改动**只能在真机、由真人操作**才能确认（锁屏、睡眠唤醒、Alt-Tab 切窗口、GUI 点击），自动化测试覆盖不到——单测能证明「复位函数写对了」，证明不了「真锁屏那一下确实触发了它」。这些验收项此前散落在 `docs/变更归档.md` 各条目的「**未验证**」句里，只有一句话，接手的人不知道从哪下手。

> 这里把它们收成**可照做、可复跑**的步骤：每条都有前置配置、操作步骤、预期现象、以及「出现什么就算失败」。默认从**最新的可靠性项**往回排。
>
> **谁该读**：要验收这些改动的人（目前就是作者本人）。**什么时候跑**：改到钩子 / 状态机 / 动作执行后跑相关那几条（不必每次全跑）；发版前若时间允许，跑第 1~8 条。

## 0. 通用准备（每条都要用）

### 0.1 怎么看到日志

壳层留痕走 `eprintln!`，**只有带控制台的构建才看得到**：`src-tauri/src/main.rs` 是 `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`——release 版没有控制台，stderr 会直接丢掉；**debug 版从终端启动才有输出**。

```powershell
# 先退出正在运行的那一个（托盘右键 → 退出）；两个实例会抢同一套全局钩子
taskkill /IM kada.exe /F

# 需要时先构建 debug 版
cargo build -p kada

# 从终端启动，日志就打在窗口里
.\target\debug\kada.exe
```

要验证的复位留痕是这一行（`_` 处是原因）：

```
kada: 输入状态已复位（前台窗口切换）
kada: 输入状态已复位（钩子已重装）
```

**注意**：这行**只在壳层真的丢了状态时才打印**（`Engine::reset` 返回 `false` 就什么都不打）——所以「没看到日志」不等于「复位没跑」；能看到它时是好消息，看不到时要靠下面的**功能现象**判断。

### 0.2 两条纪律

- **debug 版与 release 版共用同一份配置**（`%APPDATA%\com.kada\config.json`）。测试期间加的测试条目（改键 / 文本扩展 / 快捷键）测完记得删掉，否则会一直生效。
- **关主窗口 ≠ 退出**（托盘常驻是设计）。退出只能走托盘菜单「退出」，或 `taskkill /IM kada.exe /F`。

### 0.3 通用观测位置

| 要看什么 | 在哪看 |
|---------|-------|
| 复位留痕、注入失败、创建窗口失败 | 启动它的那个终端窗口（仅 debug 版） |
| 命令 / 脚本结果、中止记录 | 主窗口左侧「消息」页（托盘图标红点 = 有未读） |
| 动作超时设置 | 主窗口左侧「设置」页 →「动作超时」（**按秒**录入，0 = 不限） |
| 打开主窗口 | 双击托盘图标（左键），或托盘右键 →「打开咔哒」，或双击你设的快速唤醒键 |

## 1. 前台切换 → 收回注入的修饰键（P1-④） ✅ 2026-09-29 通过

**要证的事**：按住切层/长按键期间注入出去的 Ctrl，在 Alt-Tab 切窗口时被**补一个 up** 收回来。不复位的后果是「修饰键粘住」——系统层面 Ctrl 一直按着，新窗口里敲什么都成组合键。

**前置配置**：改键页新增一条，`from` = `CapsLock`，「长按」（长按输出）= `Ctrl`，保存。
（短按输出留空即可——留空时短按会按吞键铁律回放原键，不影响本测试。）

**步骤**：

1. 打开记事本（或任意能输入文本的窗口），让它在最前台。
2. **按住 CapsLock 不放**，再按一下 `K`。
   这一步让状态机判定为「长按」（roll 判定），把 Ctrl **物理注入**下去——此刻系统层面 Ctrl 是按下状态。
3. **保持按住 CapsLock**，按 `Alt+Tab` 切到另一个窗口（另一个记事本 / 浏览器地址栏）。
4. 等大约 **0.5 秒**，让新窗口稳定在前台。
   前台切换要**连续两轮**巡检（各 60ms）才认，所以给足两轮以上。
5. 松开 CapsLock。
6. 在新窗口里敲一下字母 `a`（**不要**碰 Ctrl）。

**预期**：新窗口里正常出现 `a`。

**判失败**：敲 `a` 没有任何字符出现，或触发了 **Ctrl+A 全选**（浏览器地址栏 / 记事本会全选）——说明注入的 Ctrl 从未被收回，**修饰键粘住了**，本项不通过。

**顺带确认**：终端里应出现 `kada: 输入状态已复位（前台窗口切换）`（在切窗口后约 120ms 内；若此前没有任何待定状态则可能不打，见 §0.1）。

**万一 Ctrl 真的粘住了怎么恢复**：按一下物理 `Ctrl` 键再松开——真实的一对 down/up 会把系统状态冲正，不用重启应用。

## 2. 前台切换 → 热串缓冲不回放（P1-④） ✅ 2026-09-29 通过

**要证的事**：在 A 窗口敲了一半的文本扩展触发词，切到 B 窗口后敲后缀**不会**在 B 里展开成替换文本。复位口径是「缓冲里的东西一律丢弃不回放」——因为复位时前台目标已经变了，把旧按键注入到新窗口（可能是密码框）比丢掉更糟。

**前置配置**：确认「文本扩展」页有一条触发词，比如 `addr`（替换文本随便是什么都行）。没有就加一条，保存。

**步骤**：

1. 打开窗口 A（记事本），点击进入可输入状态。
2. 在 A 里敲 `add`（**不要**再敲空格 / 回车 / Tab，也不要敲完整触发词）。
3. `Alt+Tab` 切到窗口 B（另一个记事本，或浏览器里的输入框），等约 0.5 秒。
4. 在 B 里敲 `r`，紧接着敲一下空格。

**预期**：B 里看到的就是你亲手敲的 `r `（或连上 B 里原本的内容）——**不展开**成替换文本。

**判失败**：B 里突然变成替换文本（触发词被回删、注入了替换内容）——说明在 A 窗口敲了一半的缓冲被带过了窗口边界，本项不通过。

> 这条测试的价值在于它**能被肉眼立刻分辨**：成功与失败输出的是两段完全不同的文字，不需要任何工具辅助。

## 3. 锁屏 → 解锁（P0-① 重装 + P1-④ 复位） ✅ 2026-09-29 通过

**要证的事**：`Win+L` 锁屏再解锁后，钩子被看门狗判为「已重装」（判据是 `WTSInfoEx.SessionFlags` 的 锁定→未锁定 跃迁：反直觉字段 0=锁定、1=未锁定），壳层跟着复位。

**步骤**：

1. 保持 debug 版从终端运行（§0.1）。
2. 按 `Win+L` 锁屏，等 2 秒以上，再解锁回到桌面。
3. 解锁后**立刻**做两件事：按一次你配好的快捷键（如 `Alt+X`）；再敲一次文本扩展（触发词 + 空格）。
4. 看一眼终端输出。

**预期**：快捷键与文本扩展都正常生效；若解锁前壳层有残留状态，终端会多出 `kada: 输入状态已复位（钩子已重装）`。

**判失败**：解锁后快捷键 / 改键 / 文本扩展**全部无响应**（说明钩子没被重装，看门狗这条判据失效），或出现「修饰键粘住」——都算不通过。

**说明**：看门狗巡检 1 秒一次，所以解锁后最多约 1 秒才重装并复位落地，属正常；这一步同时也是 P0-① 看门狗唯一能由真人稳定复现的触发路径。

## 4. 休眠 → 唤醒（P0-①） ⬜ 未执行

**要证的事**：看门狗能用 `GetTickCount` 的跃变（**该计数把睡眠时间也算进去**）发现机器睡过，并重装钩子。

**状态**：**未执行**——2026-09-29 首轮人工验证唯一没跑的一条。看门狗的重装动作本身已由 §3（解锁路径）在真机确认，但「相邻巡检间隔 > 10s ⇒ 机器睡过」这条判据仍只由单测覆盖，没在真机上跑过。可以下次休假前顺手做。

**步骤**：

1. 保持 debug 版从终端运行。
2. 开始菜单 → 电源 → 睡眠。**睡够 10 秒以上**（判据是「相邻两次巡检间隔 > 10s」，睡太短不足以越过阈值）。
3. 唤醒机器（动鼠标 / 按键盘）。
4. 唤醒后立刻按一次快捷键 + 敲一次文本扩展。

**预期**：都正常生效；终端可能出现 `kada: 输入状态已复位（钩子已重装）`。

**判失败**：唤醒后所有触发无响应，或修饰键粘住。

## 5. 冷启动双击唤醒（P1-⑤） ✅ 2026-09-29 通过

**要证的事**：唤醒路径的**建窗**跑在后台线程，不会把钩子回调拖过系统超时线（约 300ms）而被摘钩。这条最凶险的形态是**开机自启**：主窗口没预建，首次双击唤醒要冷启动 WebView（几百毫秒），正好撞在那条路上。`--autostart` 参数就是用来复现这个状态的。

**前置配置**：设置页「快速唤醒」选一个键（如「双击 Alt」），保存。

**步骤**：

1. 完全退出 Kada（托盘 →「退出」）。
2. **用静默模式启动**（模拟开机自启，主窗口不预建——这是本测试的关键）：

   ```powershell
   .\target\debug\kada.exe --autostart
   ```

   观察：不应有任何窗口出现（只有托盘图标）。
3. 随便点开一个别的窗口（如记事本），让**主窗口处于未创建状态**。
4. 快速双击你设的唤醒键（两击间隔 ≤ 400ms）。
5. 看主窗口是否出现、终端是否报错。
6. **重复第 3~5 步 3~5 次**，其中至少一次是「不等待、连点两轮双击」——用于撞「并发建窗」那条竞态。
7. 再验证唤醒键本身**不被拦截**：在记事本里，`Alt+Tab`、`Alt+字母` 应照常可用。

**预期**：主窗口每次都正常出现；终端**没有** `创建主窗口失败`；`Alt+Tab` / `Alt+字母` 正常。

**判失败**：唤醒键按了没反应；终端出现 `创建主窗口失败`（并发建窗的回查分支没生效）；或唤醒后**快捷键全部失效**（钩子被回调超时摘掉了，这正是本项要防的）。

## 6. 动作超时 + 杀整棵进程树（P1-⑦） ✅ 2026-09-29 通过

**要证的事**：命令挂住时被**限时**终止（不再是无限等待），而且是连**孙进程**一起杀（`Child::kill` 杀不掉 `cmd /C` 下面真正干活的那层）。

**前置配置**：

1. 设置页「动作超时」填 `2`（秒），保存。改完立即生效，不用重启（超时值在触发时从配置读出）。
2. 新建一条快捷键（如 `Alt+F9`），动作 = **执行命令**（Shell 选 CMD），命令填：

   ```
   powershell -NoProfile -Command "Start-Sleep -Seconds 30; New-Item -Path '%TEMP%\kada_tree_marker.txt' -ItemType File | Out-Null"
   ```

   这条命令的结构是刻意选的：我们的进程 → `cmd /C <临时批处理>` → `powershell`（**孙进程**）→ 睡 30 秒后建标记文件。只杀直接子进程的话，标记文件照样会出现。
3. 先手工删掉 `%TEMP%\kada_tree_marker.txt`（若存在）。在资源管理器地址栏输入 `%TEMP%` 回车即可打开该目录。

**步骤**：

4. 触发 `Alt+F9`。
5. 观察动作何时结束（命令本身要跑 30 秒，被超时终止应在约 **2 秒**就返回）。
6. 打开主窗口 →「消息」页，看新增的那条结果。
7. **再等 35 秒**，回到 `%TEMP%` 目录看标记文件在不在。
8. **对照组（很重要）**：把「动作超时」改成 `0`（不限），再触发一次，等到命令自然结束（约 30 秒）——这次标记文件**应该**出现。

**预期**：

- 第 5 步：约 2 秒返回（不是 30 秒）。
- 第 6 步：结果里 `stderr` 含一句 `〔咔哒〕执行超时（超过 2 秒），已强制终止该进程及其子进程。`；**退出码显示「—」**（被强杀的进程退出码没有语义，程序置空，前端渲染成「—」）。
- 第 7 步：标记文件**不存在**。

**判失败**：

- 第 5 步等了 30 秒才结束 → 超时没生效。
- 第 6 步没有「执行超时…」这句 → 原因没写进 stderr（用户看不到归因）。
- **第 7 步文件出现了 → 只杀了直接子进程、孙进程还在跑**，这是本项最关键的验收点，出现即不通过。
- 第 8 步对照组的文件也没出现 → 说明是命令本身没跑起来（比如引号被转义坏），前面的「没出现」是假阳性，要重新验证。

> 第 8 步的对照不能省：没有它，「文件不存在」这个结果无法区分「杀干净了」和「命令压根没执行」。

## 7. 停止执行按钮（P1-⑦） ✅ 2026-09-29 通过

**要证的事**：用户点「停止执行」能真的叫停正在跑的动作链，且**不假装成功**——没有在跑的东西时如实说「当前没有正在执行的动作」。

**前置配置**：

1. 设置页「动作超时」填 `0`（不限）——避免 30 秒自动超时结束干扰本测试。
2. 新建一条快捷键（如 `Alt+F10`），动作 = 执行命令（CMD）：`ping -n 60 127.0.0.1 >nul`（约跑 59 秒）。

**步骤**：

3. 触发 `Alt+F10`（命令开始跑）。
4. 立刻打开主窗口（双击托盘图标）→「消息」页 → 点右上角「**■ 停止执行**」。
5. 看提示与命令是否停。
6. **再点一次**「■ 停止执行」（此刻没有在跑的动作）。

**预期**：

- 第 4~5 步：提示 **`已请求停止（1 条正在执行）`**；命令**立刻**结束（判定粒度 20ms，最多迟 20ms 就开始杀进程）；「消息」页新增一条 kind 为 abort 的记录，内容是 `已停止执行：剩余动作不再执行，正在运行的命令 / 脚本已强制终止。`
- 第 6 步：提示 **`当前没有正在执行的动作`**。

**判失败**：

- 第 5 步提示「当前没有正在执行的动作」（说明「正在执行」计数没加上去，`RunGuard` 漏了），或提示了「已请求停止」但命令还在跑（中止判定点失效）。
- 第 6 步仍然提示「已请求停止（N 条正在执行）」→ 计数泄漏（动作链结束没减回去），之后 UI 会永远显示「有东西在跑」。

> 第 6 步就是「反馈不假装成功」这条设计的验收：什么都不跑的时候点停止，也必须得到诚实的回答。

## 8. 动作失败上报消息中心（P1-⑥） ✅ 2026-09-29 通过

**要证的事**：一个必然失败的动作，用户能在消息中心看到「**哪一步**失败、拿**什么值**去做的、**为什么**失败」，而不是只有「按了没反应」。（release 版没有控制台，stderr 日志看不到，所以只能靠消息中心判断。）

**前置配置**：

1. 新建一条快捷键（如 `Alt+F10`），动作 = 文件操作 → 删除，路径填一个**不存在**的路径（如 `D:\没有这个目录\x.txt`）。
2. 同一条快捷键后面再追加一个动作：暂停 100 毫秒（它不会产生任何记录，用来顺带看「一步失败不中断后续动作」——触发一次应当只多**一条**记录）。
3. 再新建一条快捷键（如 `Alt+F11`），动作 = 执行脚本，路径填一个**不存在**的脚本文件，并把该动作的「弹窗显示结果」**打开**。

**步骤**：

4. 触发 `Alt+F10`（坏路径动作）。
5. 打开主窗口（双击托盘图标）→「消息」页，看新增的那条记录。
6. 触发 `Alt+F11`（起不来的脚本，开了「弹窗显示结果」）。

**预期**：

- 第 4 步：托盘图标出现**红点**，应用内「消息」入口亮红点。
- 第 5 步：tab 标题是 **`文件操作失败 · 名称`**（没填名称则是 `文件操作失败 · Alt+F10`）；卡片里「命令」一栏是 **`删除 D:\没有这个目录\x.txt`**（若该动作填了「描述」，则显示 `描述（删除 …）`）；stderr 是失败原因（`删除失败：「…」不存在`）；退出码 `—`。
- 第 6 步：**弹窗自动出现**（因为该动作开了「弹窗显示结果」），标题 `命令结果 · 脚本失败`，stderr 里是脚本起不来的系统错误。

**判失败**：

- 第 5 步消息中心**没有任何新记录** → 失败仍只在 stderr 日志里（本项未生效）。
- 第 5 步记录里「命令」一栏为空、或原样留着 `{变量名}` 这类占位符 → 摘要没渲染 / 变量没代入。
- 第 6 步**没有弹窗** → `show_output` 被失败路径一律降级成静默了（应当沿用动作自身的设置）。
- 若第 5 步出现不止一条记录 → 说明有别的动作也在报（本例的第二个动作是暂停，没有失败路径）。

> 第 6 步是「命令/脚本连启动都没成功也该弹窗」这条设计的验收；第 4~5 步的红点则是所有非弹窗类失败的默认表现。

## 9. 未保存改动守卫（P1-⑧） ⬜ 待真人复跑（纯浏览器演示模式已验，见末尾）

**要证的事**：编辑页里改到一半，点另一行 / 切页 / 关编辑页**不会静默丢改动**——要么被问一句，要么保存下来；且「保存并离开」真的落盘了才放行。

**前置配置**：无（用现有任意条目即可）。**本项不需要 debug 版日志**，看界面现象就够。

**步骤与预期**（每步都给了判失败）：

1. 打开「快捷键」页 → 点一条已有条目 → 改「描述」输入框。
   - 预期：动作行出现**黄色「● 未保存」标记**，「撤销改动」按钮由禁用变为可用。
   - 判失败：改了描述标记不亮 → 签名没把「描述」这个只在保存时才读的字段算进去。
2. 点「撤销改动」。
   - 预期：描述还原成打开时的内容，标记消失、按钮回到禁用；编辑页**不关**。
   - 判失败：描述没还原，或编辑页被关掉/跳走。
3. 再改一次描述 → 点**列表里另一条**。
   - 预期：弹出确认框「**快捷键「xx」有未保存的改动。**」，三个按钮「继续编辑 / 放弃改动 / 保存并离开」。
   - 判失败：直接切过去了（改动静默丢失）。
4. 点「继续编辑」。再点另一条 → 点「放弃改动」。
   - 预期：第 4 步留在原条目且仍是脏；之后切到另一条，原条目的描述**没有**被改。
   - 判失败：「继续编辑」之后仍然切走了。
5. 重新打开原条目 → 改描述 → 点「**保存并离开**」。
   - 预期：切到目标条目；**再重新打开原条目，描述是刚保存的内容**（这一步是「真的落盘了吗」的验收）。
   - 判失败：切过去了但重开后描述还是旧的 → 保存没成功却放行了。
6. 脏状态下点左侧导航「改键」（切页）。
   - 预期：同样弹确认框（框内文案带条目名）；点「继续编辑」留在原页；也可以直接按 **Esc**，等价于「继续编辑」。
   - 判失败：Esc 之后切页了（Esc 不该是破坏性动作）。
7. 「取消」按钮与右上角「×」：脏状态下点它们。
   - 预期：也弹确认框；「继续编辑」留在编辑页，「放弃改动」才关闭编辑页。
   - 判失败：直接关掉（改动静默丢失）。
8. 「+ 新增」→ 什么都不填就再点「+ 新增」。
   - 预期：**不弹框**（空白新条目不算改动），直接换成新的空白编辑页。
9. 「+ 新增」→ 填点东西 → 再点「+ 新增」。
   - 预期：弹框；「放弃改动」后回到空白的新条目（标题「（未命名）」、标记消失）。
10. 改键页：打开一条改键 → 改「原键」下拉 → 点「撤销改动」。
    - 预期：本页标记亮 → 撤销后回原键，标记灭。**顺带看**：切到别的页时不该看到别的页的标记亮着。
    - 判失败：改了「原键」标记不亮（这是「只在保存时才读回草稿的字段」里最容易漏的一个）。
11. 保存失败不放行：打开一条改键 → 把「短按 / 长按 / 改为」**全部清空**（此时该条目已无任何输出）→ 点侧栏切页 → 弹框里点「保存并离开」。
    - 预期：**留在改键页**，toast 提示「请至少设置一种输出：…」，标记仍然亮着。
    - 判失败：切页了（说明「保存失败也放行」，改动会丢）。
12. 列表开关不被盖掉：打开某条快捷键 → 在**列表行**上把它的启用开关点成停用 → 在编辑页改点东西 → 点「保存」→ 关掉再重开该条。
    - 预期：开关**保持停用**（编辑页里没有启用开关，保存不该把列表上刚点的状态翻回去）。
    - 判失败：开关又自己变成启用了。
13. 关窗不丢：脏状态下直接关主窗口（右上角 ×）。
    - 预期：**不弹任何确认框**（关窗只是收进托盘）；从托盘再打开主窗口，编辑页与改动**都还在**（草稿在内存里，程序没退出）。
    - 判失败：关窗后重开发现草稿没了。

**判失败（汇总）**：任何一步「改动没被提示就消失了」；「保存并离开」之后重开发现内容没落盘；标记亮着但点保存后仍亮（或反之）；Esc 造成破坏性结果。

**状态**：⬜ **真人复跑待做**（Tauri 壳里的点击）。**2026-09-29 已在纯浏览器演示模式（`ui/src/mock.ts`）把上面 1~12 步的逻辑等价地跑过一轮，全部符合预期**——差异只有 mock 换成了真 IPC 与原生文件对话框，第 13 步（关窗收托盘）演示模式没有对应行为、只能真人验。之所以仍标「待真人复跑」：本清单的规矩是**只认真机结果**，演示模式通过不等于壳里通过（比如真实保存要走 `set_config` 落盘，失败分支要真出错才能触发）。

## 10. 删除确认 + 导入合并 / 替换（P1-⑨） ⬜ 待真人复跑

**要验的**：删除任何**已保存**的条目都先问一句，且问的那条与被删的那条是同一条；导入不再点一下就整份替换，而是先选「合并 / 替换」，替换前自动留档，导入结果能逐条复盘。

**前置**：随便配几条快捷键（其中一条**放进一个自建目录**）、一条改键、一条文本扩展；再准备两份 JSON 备用——**A**：从「导出配置」导出的当前配置副本；**B**：手改 A 得到的一份「有撞车也有新条目」的配置（例如其中一条快捷键的触发键与现有某条相同、另加一条新的改键与原键相同的改键、再加一条全新触发键的快捷键）。

1. **删除快捷键（列表行菜单）**：点某行的 `⋯` → 「删除」。
   - 预期：弹出确认框，文案是「删除快捷键「名称」？删除后应用内无法撤销。」（无名条目退回显示触发键）。
   - 判失败：直接删掉了、没有任何确认。
2. 上一步的确认框点**取消**（或按 Esc / 点窗口关闭）。
   - 预期：那一行**还在**。
   - 判失败：取消之后条目消失了。
3. 再来一次并确认。
   - 预期：行消失、toast「已保存」；**从托盘退出应用再启动，这一条确实没了**（这一步才是「真落盘了」的验收）。
   - 判失败：界面上没了但重启后又回来了（说明只改了内存）。
4. **删除快捷键（详情页按钮）**：打开一条 → 底部「删除」→ 确认。
   - 预期：同样弹确认框；确认后列表少一条、编辑页关闭到空态。
   - 判失败：详情页的「删除」不问一句就删。
5. **未保存改动时的删除**：打开一条 → 改一下描述（动作行出现黄色「● 未保存」）→ 点「删除」。
   - 预期：确认框里**多一句**「该条还有未保存的改动，会一并丢弃。」。
   - 判失败：没提这件事（用户以为只是删了已保存的内容）。
6. **未落盘的新增项**：点「+ 新增」→ 填点东西 → 点「删除」。
   - 预期：**不弹确认框**，直接回到空态（等同「取消」，没有已保存内容会丢）。
   - 判失败：弹框了（噪声）。
7. **删除目录报出波及范围**：把那两条快捷键放进自建目录 → 目录行 `⋯` → 「删除」。
   - 预期：文案「删除目录「x」及其中的 2 条快捷键？删除后无法撤销。」；确认后目录与其中的条目一起消失。
   - 判失败：文案不报条数（用户不知道要删掉多少东西）。
8. **删除改键 / 文本扩展**：同 1~3，条文案分别是「改键「CapsLock → Ctrl」」「文本扩展「;addr」」。
9. **导入-取消**：设置 → 「导入配置」→ 选 A。
   - 预期：先弹「导入配置」框，正文说明**合并**（只新增、本机设置不动）与**替换**（整份覆盖含设置、会留档）两种方式；点「取消」（或 Esc / 点遮罩）→ **什么都没发生**（配置没变、没有 toast、没有弹结果框）。
   - 判失败：不选就直接导入了，或 Esc 之后还是导入了。
10. **导入-替换 + 留档**：在 A 上先加两条现有配置里没有的条目并保存导出，改名为 C → 设置 → 导入 C → 选「替换（覆盖全部）」。
    - 预期：结果弹窗「已替换为导入的配置：共 N 条…」+ 一行**留档路径**；`%APPDATA%\com.kada\` 下出现 `config.json.pre-import-<时间戳>`，**其内容 = 导入前的配置**；列表只剩 C 里的条目；**开机自启 / 快速唤醒键跟着 C 走**（替换含设置，这条是「替换与合并的区别」的验收）。
    - 判失败：没有留档文件；或留档内容是导入后的（那就白留了）。
11. **导入-合并**：用第 10 步的留档文件（或直接改回来）恢复到导入前的配置 → 导入 C → 选「合并」。
    - 预期：结果弹窗「已合并：新增 N 条，跳过 / 忽略 M 条」+ **逐条明细**；现有条目**一条不少**、C 里的新条目追加在后面；**设置没变**（自启 / 唤醒键 / 超时保持原样）。
    - 判失败：现有条目被删掉或改名；设置被导入文件改掉。
12. **合并的撞车口径**：导入 B → 选「合并」。
    - 预期：明细里逐条出现「快捷键「x」未导入：触发键 Ctrl+Alt+B 已存在」「改键「CapsLock」未导入：该键已有改键」之类；列表**不出现重复条目**、冲突页**不新增红冲突**（合并不会替用户制造冲突）。
    - 判失败：出现两条触发键相同的快捷键、或冲突数变多。
13. **合并幂等**：**再导入一次 B**（同样选合并）。
    - 预期：「新增 0 条，跳过 / 忽略 N 条」，配置与上一步完全一致（重复导入不翻倍）。
    - 判失败：条目翻倍了。
14. **合并的引用完整性**：导入一份含「新层 + 一条长按进入该层的改键」的配置 → 合并。
    - 预期：改键页里这条改键的「长按进入层」下拉**指向那个新层**（不是空白），摘要显示「长按进层「导航层」」。
    - 判失败：层没进来、改键整条作废（这是「先并层再并条目」要挡住的事）。

**判失败（汇总）**：删除任何**已保存**内容时没有确认框；确认框里说的条目与实际被删的不是同一条；取消之后条目还是没了；未落盘的新增项也弹框；点「导入配置」不选方式就整份替换；替换导入后磁盘上没有 `pre-import` 留档；合并删改现有条目、或让设置被导入文件改掉；合并后冒出用户没配过的冲突、或条目翻倍；合并后条目引用的层/目录丢了。

**状态**：⬜ **待真人复跑**（原生确认框 + 真实文件选择 + 跨进程落盘确认）。**2026-09-29 已在纯浏览器演示模式（`ui/src/mock.ts`）把逻辑等价地跑过一轮**：行菜单删除与详情页删除都真的删掉了条目并走了 `set_config`；导入的「合并 / 替换 / 取消」三条路径都按对应 `mode` 发起 `import_config`，结果弹窗文案与逐条明细正确，替换路径带出了留档行。演示模式验不到的是：`ask()` 的原生对话框本身、真实文件对话框、磁盘上的 `pre-import` 留档文件、以及第 3/11 步「重启后仍在」这类跨进程确认。

> **顺带修掉的桩**：演示模式的 `plugin:dialog|message` 原先返回布尔 `true`，而真实后端返回的是**被点击按钮的文案**（`ask()` 拿它跟 okLabel 默认值 `"Yes"` 比对）——于是**演示模式下所有确认框都被判成「否」**，删除目录 / 删除层点了没反应且看不出原因。本次一并改正（`mock.ts` 返回 `"Yes"` / `"Ok"`）。以后在演示模式里验确认框，记得这条已经修了。

## 11. 配置外部修改监听（P1-⑩） ⬜ 待真人复跑

**要验的**：运行期手改 `config.json`（或恢复备份、同步落盘）**真的生效**；应用内的下一个保存**不会把外部改动盖掉**；外部内容坏了（编辑器写到一半）时**磁盘与内存都不被动**；界面上有未保存草稿时**不静默丢弃**。

**前置**：按 §0.1 从终端启动 debug 版（能看见日志，`kada: 输入状态已复位（配置已重新加载）` 就打在窗口里）。配置路径：`%APPDATA%\com.kada\config.json`（同目录还有 `config.json.bak`）。用记事本 / VS Code 打开它备用。准备一条已保存的快捷键（例如触发键 `Ctrl+Alt+K`，下面都拿它举例）。

1. **外部改动生效**：把那条快捷键的触发键从 `Ctrl+Alt+K` 改成 `Ctrl+Alt+9`，**保存文件**。
   - 预期：约 1 秒内（监听每秒巡检一次）——按 `Ctrl+Alt+9` 触发该快捷键，按 `Ctrl+Alt+K` **不再**触发；托盘亮红点，「消息 → 命令结果」里出现一条「配置」：`检测到配置文件被外部修改，已重新加载生效`，细节里报出快捷键 / 改键 / 文本扩展 / 层 / 目录各多少条。
   - 判失败：等多久都不生效（可按 `Ctrl+Alt+K` 仍然触发）；或进消息页看不到任何记录（外部改动静默发生了）。
2. **应用内保存不再覆盖外部改动**：主窗口开着（第 1 步之后）→ 列表里那条**显示的已经是 `Ctrl+Alt+9`** → 随便动一下别的条目并点「保存」。
   - 预期：保存过后 `config.json` 里那条**仍是 `Ctrl+Alt+9`**（打开文件确认），没有被改回 `Ctrl+Alt+K`。
   - 判失败：文件里又变回旧触发键（说明界面用的是过期配置，外部改动被保存覆盖——这正是本项要修的问题）。
3. **自己的保存不误报**：在第 2 步保存的同时看终端与消息页。

## 12. 序列 / 和弦等待窗进设置（P2-⑫） ⬜ 待真人复跑

**要验的**：设置页两个新窗口（「序列等待」「和弦等待」）**真的管用**——改了立刻生效、不用重载配置；超时的后果是「被吞掉的键原样补回」而不是丢键；填 `0` = 不限时。

**前置**：按 §0.1 从终端启动 debug 版。准备两条已保存的快捷键：序列 `F9 J K`、和弦 `F & J`（`F&J` 两个成员是非修饰裸键）。合上主窗口不会退出应用（托盘常驻）。

1. **默认值看得见**：打开「设置」页。
   - 预期：「序列等待」「和弦等待」两个输入框里都是 `1000`，单位提示写「毫秒（0 = 不限）」，下方文案说清了两者分别是什么、超时会怎样。
   - 判失败：输入框空白 / 显示 `NaN`（老配置缺字段没兜住）或单位标成「秒」。
2. **序列等待 = 默认 1 秒**：按一下 `F9` 就撒手、**不等**（不要按 J/K）。
   - 预期：约 1 秒后 `F9` 自己「补」出来（光标处出现一个 F9 的效果——多半是输入法/系统对 F9 的默认动作，或至少不再被吞住）；期间按 `F9 J K` 仍能正常触发那条快捷键。
   - 判失败：`F9` 被永久吞掉（这个键像坏了一样什么都不发生）。
3. **调大窗口**：设置页把「序列等待」改成 `3000`（改完点开别处让输入框失焦，或直接按回车）。
   - 预期：`%APPDATA%\com.kada\config.json` 里 `sequence_timeout_ms` 变成 `3000`；再按一下 `F9` 撒手，**3 秒内**都不回放（按 `F9 J` 能在 3 秒窗口内继续推进序列）。
   - 判失败：还是 1 秒就回放（说明窗口仍然写死，设置没生效）。
4. **填 0 = 不限时**：把「序列等待」改成 `0`。
   - 预期：按 `F9` 撒手后**一直不回放**（等到你按下一个键才按断链/推进处理，那个键也会照常打出来）；`F9 J K` 照常能触发。
   - 判失败：填 0 后按 `F9` 立刻（或 1 秒后）回放。
5. **和弦等待（默认 1 秒）**：把「序列等待」改回 `1000`，「和弦等待」保持 `1000`。按住 `F` **不松**，同时打几个字母（如 `a s d`）。
   - 预期：字母先被压住，**约 1 秒后**按 `f a s d` 的顺序一次性补出来（顺序与输入一致，不能变成 `a s d f`）。
   - 判失败：字母一直不出来（要等 `F` 松开才吐）；或补出来时顺序错乱；或字母被吞掉不还。
6. **过期后不再凑和弦**：重复第 5 步，但这次在按 `F` 后**等 1 秒以上**再按 `J`。
   - 预期：**不触发**那条和弦快捷键，`F` 与 `J` 作为两个普通按键被补出来（`f`、`j`）。
   - 判失败：还是触发了和弦（说明窗口没起作用）；或 `F`/`J` 有一个没出来。
7. **窗口内照常触发**：把「和弦等待」调大到 `3000`（或改回 `1000`），按 `F` 后**马上**按 `J`。
   - 预期：立刻触发那条和弦快捷键（正常行为不受影响）。
   - 判失败：和弦不再触发（改设置把功能改坏了）。
8. **填 0 = 不限时（旧行为）**：把「和弦等待」改成 `0`。
   - 预期：按住 `F` 等 3 秒以上再按 `J` **仍然触发**（＝本次改造前的行为）；按住 `F` 期间打的字要等 `F` 松开才补出来。
   - 判失败：填 0 反而变成「立刻回放」。
9. **老配置兼容**：退出 Kada，把 `%APPDATA%\com.kada\config.json` 里 `settings` 段的 `sequence_timeout_ms` / `chord_timeout_ms` **两个字段删掉**（模拟本项之前写的配置），保存，重启应用。
   - 预期：设置页两个框显示 `1000`（**不是** 0），序列与和弦行为与第 2 / 5 步一致。
   - 判失败：显示 0 / 按键行为变成「不限时」（那等于老用户被静默改了行为）。
10. **外部改这两项也生效**（与 §11 同源，可选）：运行期直接手改 `config.json` 里 `chord_timeout_ms` 为 `0` 保存。
    - 预期：约 1 秒后采纳（消息页出现一条「配置 · 外部修改」），和弦行为跟着变成「不限时」——不必重启。

**判失败（汇总）**：设置页两个框空白 / 显示 NaN；改了不生效（仍按 1000 走）；填 0 变成立刻回放；超时把键吞掉不还（键变哑）或回放顺序乱；和弦在窗口内也不触发了（改坏了正常路径）；老配置缺字段时被当成 0。

**状态**：⬜ **待真人复跑**。本次只有单测与构建覆盖：`kada-core` `settings_timeout_tests` 3 条（默认值随常量 / 老配置缺字段取 1000 / `0` 往返不被盖回）+ `Engine` 5 条（序列窗口取自设置、序列 `0` = 不限时且不影响命中、和弦窗口到点按输入顺序回放、过期也可由下一个事件懒判、和弦 `0` = 不限时即旧行为）+ `cargo check`（完整 / 基础版）+ 前端构建。**验不到的部分**：真实按键的时序手感、设置页输入框到落盘再到引擎生效的整条链路、以及外部改这两项（要靠 §11 的监听链路）。

## 13. 输入状态可视指示（P2-⑬） ⬜ 待真人复跑

**要验的**：悬浮指示窗与托盘提示**真的显示对了**——有层 / 有注入键时出现、消失时收起、三种形态分得清；它**不抢焦点**（不能因为它在屏幕上就把用户输入抢走或让前台条件读错）；设置里关掉立刻生效。**这条只能人工跑**：低层钩子对带 `LLKHF_INJECTED` 的注入事件一律放行、不进状态机（防回环，见 `kada-hook/src/win.rs`），所以 `SendKeys` / `SendInput` 这类合成按键**驱动不了状态机**，自动化构造不出「层生效」这个前置条件。

**前置**：按 §0.1 从终端启动 debug 版。配置里准备三样东西（都保存在改键里）：① 一个**长按进入层**的切层键（如「长按 `Tab` → 层 L1`」）；② 一个**长按锁定层**的切层键（如「长按 `CapsLock` → 层 L2」，本步专门验常驻指示）；③ 两个改键——`F1` 设「单次键 Ctrl」、`F2` 设「粘滞键 Shift」。另外把一个层重命名为长名字（如 20 个汉字）备用。

1. **启动时干净**：启动后什么都不按。
   - 预期：屏幕底部**没有**任何悬浮窗（指示窗是懒创建的，没东西生效就不建）；托盘图标悬停提示是「咔哒 Kada」。
   - 判失败：启动即出现一条空胶囊 / 托盘提示一开始就带着状态文字。
2. **按住式切层 → 出现与收起**：按住 `Tab` 不放，再按一下任意字母（触发 momentary 进层）。
   - 预期：屏幕**底部居中**出现一条胶囊，内容是「层 · <层名>（按住）」；松开 `Tab` 后胶囊立刻消失。
   - 判失败：不出现；或松开切层键后不消失（指示卡住，说明状态推送断了）；或窗口出现在左上角 / 被裁掉半截（定位与尺寸算法问题）。
3. **锁定层常驻是预期行为**：长按 `CapsLock` 触发锁定层（长按后松开）。
   - 预期：胶囊变成「层 · <层名>（锁定）」，且**松开后仍然挂着**（这是有意的：锁定层生效期间基础层按键被遮蔽，此时最需要知道「现在是哪一层」）；再长按一次退出锁定层 → 胶囊消失。
   - 判失败：锁定后指示不出现（那这条功能就漏掉了最需要它的时候）。
4. **三类注入键分得清**：分别点一下 `F1`（单次 Ctrl）、`F2`（粘滞 Shift），再按住 `Tab` 进层。
   - 预期：胶囊依次多出「单次 Ctrl」「粘滞 Shift」「按住 …」，三枚颜色不同（单次琥珀 / 粘滞绿 / 按住蓝）；`F1` 的那个在下一次按非修饰键后消失，`F2` 的那个再点一次 `F2` 才消失。
   - 判失败：三种混成一条 / 颜色一样 / 释放后指示不跟着变。
5. **不抢焦点（关键项）**：先打开记事本点进去（让它是前台窗口），然后长按 `CapsLock` 进锁定层，让指示窗挂在屏幕上，**接着在记事本里连续打字**。
   - 预期：字符照常打进记事本（指示窗不吃键、不抢焦点）；`Alt+Tab` 切换窗口正常；托盘右键菜单正常弹出。
   - 判失败：打字打不进记事本（焦点被指示窗抢了）、`Alt+Tab` 失灵、或指示窗出现在 `Alt+Tab` 列表里。
6. **不误触发输入状态复位**：接第 5 步（锁定层生效、指示窗挂着），按一条**层内**快捷键（锁定层里配的）。
   - 预期：该快捷键正常触发（层还在、没有被复位掉）；`%APPDATA%` 控制台里**不该**出现 `kada: 输入状态已复位（前台窗口切换）` 这类刷屏。
   - 判失败：层内快捷键不响应（指示窗被当成了「前台切换」而复位输入状态，说明 `focusable(false)` 没生效）；或控制台反复打印复位日志。
7. **托盘提示同步**：把鼠标移到托盘图标上（不点）。
   - 预期：提示是「咔哒 Kada · 层：<层名>（锁定） · 单次 Ctrl · 粘滞 Shift」这样的摘要（有层和修饰键时）；全部松开后回到「咔哒 Kada」。
   - 判失败：提示一直不变 / 显示了但内容是空的或只有分隔符。
8. **关掉开关立刻生效**：让锁定层生效（指示窗挂着），打开设置页取消勾选「显示输入状态悬浮指示」。
   - 预期：胶囊**立刻**消失（不必等下次状态变化）；托盘提示仍然工作；重启应用后依然不再出现。
   - 判失败：取消勾选后指示还挂着（说明指示开关没参与变化比对）。
9. **长层名不撑破窗口**：把某个层重命名为很长的名字，进该层。
   - 预期：层名胶囊里的文字以省略号截断，胶囊整体仍在屏幕内、没有被窗口边缘裁掉。
   - 判失败：文字被硬切（没有省略号）/ 胶囊超出窗口宽度被截断。
10. **演示模式可预览**：`npm --prefix ui run dev` 后浏览器直开 `http://localhost:1420/#hud`。
    - 预期：渲染出「层 · 导航层（锁定） / 按住 Ctrl / 粘滞 Shift / 单次 Alt」四枚胶囊（演示载荷），这条不需要真机钩子。
    - 判失败：白屏 / 只有一条空胶囊（说明渲染逻辑坏了）。
11. **老配置兼容**：退出 Kada，把 `config.json` 里 `settings.show_status_hud` 字段**删掉**（模拟本项之前写的配置），重启。
    - 预期：设置页那个勾选是**勾上**的（缺字段默认开），指示照常工作。
    - 判失败：缺字段被当成「关」（老用户静默失去这个功能）。

## 14. 单次 / 粘滞任意键与带修饰和弦（P2-⑭） ⬜ 待真人复跑

**要验的**：① `oneshot`/`sticky` 用**非修饰键**时真的是「替你按住它」（而不是像以前那样被静默丢弃、配了等于没配）；② 和弦成员带修饰（`Ctrl+F&J`）与纯修饰键成员（`Ctrl+Alt&J`）真的能凑齐触发，且**修饰键从不被吞**（`Ctrl+Alt+Tab` 仍是 `Ctrl+Alt+Tab`）；③ 没凑齐时成员键按吞键铁律**原样回放**（键不变哑）；④ 和弦间的超集软冲突能被检测出来。**这条只能人工跑**：低层钩子忽略注入事件、不进状态机，合成按键构造不出前置条件（同 §13）。

**前置**：按 §0.1 从终端启动 debug 版。配置里准备（都保存）：① 改键 `F1` = **粘滞 `MouseBack`**（侧键「按住说话」）；② 改键 `F2` = **单次 `Enter`**；③ 两条快捷键（各给一个能看见的动作，如气泡或输入文本 `x` / `y`）——`Ctrl+F&J`、`Ctrl+Alt&J`；④ 同层再放两条 `F&J` 与 `F&J&K`（用于第 7 步验软冲突）。打开一个记事本窗口备用。

1. **单次键用非修饰键（值域真的扩了）**：点一下 `F1` 之外的 `F2`（单次 `Enter`），然后**什么都不按**看记事本。
   - 预期：光标**立刻换到下一行**（Enter 在武装那一刻就被物理按下）；状态指示出现「单次 Enter」。
   - 判失败：指示里**没有**「单次 Enter」（说明非修饰键的值被 `key_as_modifier` 那条老逻辑丢掉了——本项要修的就是它）；或记事本毫无反应。
2. **单次在下一个键抬起后释放**：接上一步，在记事本里打一个字母 `a` 再**松开**它。
   - 预期：输入 `a`；松开 `a` 之后指示里的「单次 Enter」消失（Enter 被释放）。
   - 判失败：指示一直挂着（没释放，等于 Enter 永久按住）；或打字时被 `a` 之外的字符干扰。
3. **粘滞非修饰键（侧键按住说话）**：点一下 `F1`（粘滞 `MouseBack`）。
   - 预期：指示出现「粘滞 MouseBack」并**保持**（键被锁住一直按着）；在浏览器里点一下页面再点前进按钮后，侧键「后退」能生效（MouseBack 确实处于按住/触发态）。再点一下 `F1` → 指示消失。
   - 判失败：指示不出现（非修饰键被丢掉）；或再点一下不消失（解不开锁）。
4. **带修饰的和弦**：按住 `Ctrl` 不放，按 `F`、再按 `J`（`Ctrl` 全程按住）。
   - 预期：触发 `Ctrl+F&J` 的那条动作；指示显示按住 Ctrl；松开后复位。
   - 判失败：不触发；或触发成别的条目。
5. **纯修饰键成员**：按住 `Ctrl` 与 `Alt`，再按 `J`。
   - 预期：触发 `Ctrl+Alt&J` 的动作（两个修饰键必须在**按 J 之前**就按住）。
   - 判失败：不触发（说明修饰键成员的「要求按住」判定没生效）。
6. **修饰键从不被吞（关键项）**：按住 `Ctrl` 与 `Alt`，然后按 `Tab`。
   - 预期：**仍是 `Ctrl+Alt+Tab`**（切换窗口生效）——修饰键被放行，没有被和弦吞成 `Ctrl+Tab` 或 `Alt+Tab`。
   - 判失败：`Ctrl+Alt+Tab` 退化成 `Ctrl+Tab` / 无反应（修饰键被吞了，会影响全局组合键）。
7. **没凑齐原样回放**：单独按一下 `F`（不按 `J`）、单独按一下 `J`（不按 `F`），各松手。
   - 预期：记事本里正常打出 `f`、`j`（各自的按下与抬起都补回来，键不变哑）。
   - 判失败：某个键不出字符（被吞掉没回放）。
8. **和弦间软冲突提示**：把 `F&J` 与 `F&J&K` 放在**同一层**并保存（两条 `Ctrl` 和弦另放别的层或删掉）。
   - 预期：消息页「冲突」标签出现一条 **Warn**（黄色）：「和弦『F&J&K』永远触发不到：『F&J』的要求更宽…」；把两条书写顺序对调后重新保存，**仍报 `F&J&K`**（成员更少的那条必然先凑齐，与顺序无关）。
   - 判失败：两条都不报；或把 `F&J` 报成「永远触发不到」（方向反了）。
9. **不同修饰不误报**：只留 `Ctrl+F&J` 与 `Alt+F&J`（去掉 `F&J`/`F&J&K`）。
   - 预期：**没有**冲突提示（两条在各自修饰键下都可达）。
   - 判失败：报了冲突（把「互不包含的修饰要求」误判成遮蔽）。
10. **老配置兼容**：退出 Kada，确认配置里原有的「单次/粘滞修饰键」（`Ctrl`/`Shift` 这类）改键仍然有效——值域是**放宽**不是改语义，无需迁移。
    - 预期：老的单次/粘滞改键行为与以前完全一致；`Ctrl+F&J` 这类新写法的旧配置（若有）也能正常加载。
    - 判失败：老的修饰键改键失效（说明改造破坏了原路径）。
11. **编辑器值域与录入**：打开改键编辑器。
    - 预期：「单次键 / 粘滞键」两个下拉是**全键表**（能选到 `A`、`F5`、`MouseBack` 等，不再只有四个修饰键）；和弦录入时**按住 `Ctrl` 再按两个字母**，提交文本是 `Ctrl+X&Y` 形式。
    - 判失败：下拉里只有 Ctrl/Alt/Shift/Meta；或按住修饰键录入被当成成员而报「不能是修饰键」。

**判失败（汇总）**：非修饰键的单次/粘滞在指示与功能上都不生效（值域没真扩）；单次不在下一个键抬起后释放、或武装键自身再按被判成消费；粘滞第二次点击解不开锁；带修饰和弦凑不齐 / 修饰键被吞（`Ctrl+Alt+Tab` 退化）/ 没凑齐时不回放（键变哑）；修饰键成员要求按住却不需要按住就能触发；和弦超集软冲突漏报或方向反了；不同修饰要求被误报成冲突；老配置的修饰键改键失效；编辑器下拉仍是四个修饰键。

**状态**：⬜ **待真人复跑**。已有覆盖（`cargo test --workspace` 全绿）：`kada-core` 冲突 6 条（修饰键成员不遮蔽组合 / `F&J` 与 `Ctrl+F&J` 不算重复 / 超集警告含反序 / 同键更宽要求按顺序判 / 不同修饰要求不冲突 / 跨层不判）+ 和弦解析与 tracker 4 条（带修饰成员解析与显示 / 纯修饰键成员折叠 / 成员修饰须按住 / 修饰键成员不进集合）+ `Engine` 5 条（单次普通键按住到下一键抬起 / 自重按不重复注入 / 粘滞普通键两次切换 / 带修饰和弦须按住修饰键 / 修饰键成员不被吞）+ 指示载荷 1 条（非修饰键如实显示键名）+ `cargo check`（完整版 / 基础版）+ 前端构建。**验不到的部分**：真实按键下的手感与语义（尤其「替你按住它」在目标程序里看到的时序、侧键粘滞的实际效果）、修饰键成员在真机钩子 mods 上报下的判定、以及冲突提示在消息页面的呈现。

## 目前做不到的验证（不必尝试）

- **「回调超时被系统摘除」**：需要钩子回调真的卡住超过 `LowLevelHooksTimeout`（约 300ms）才会被系统摘掉，人为触发不了。这条路径的判据（心跳停摆）由单测 `watchdog_spots_hook_that_stopped_receiving_events` 覆盖，重装动作由冒烟测试走 `request_reinstall()` 走同一条代码路径。
- **macOS 全链路**：开发机是 Windows，对 macOS 只能做类型级验证（`cargo check --target aarch64-apple-darwin`，且只覆盖 `kada-hook` / `kada-core` / `kada-actions`；Tauri 壳因 `ring` 要真 clang 而无法交叉检查）。链接期符号、运行时权限、真实系统行为（注入识别、AX 查询、唤醒自愈）都只能靠真机或 CI 的 macos job——见 §15。
- **Linux 侧杀进程树**：Linux 分支目前只 `kill()` 直接子进程（孙进程杀不掉），是**已记录在案的已知缺口**（见 `需求设计说明书.md` §5.7）。本机是 Windows，Linux 分支只能保证编译通过。
- **「键盘钩子单独被摘、鼠标钩子还活着」**：`GetLastInputInfo` 是键盘与鼠标的合并信号，这种半边失效发现不了（心跳一直被鼠标事件喂着），是看门狗的已知天花板。

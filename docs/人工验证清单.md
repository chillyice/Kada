# Kada 人工验证清单

> **这份文档解决什么问题**：Kada 有一批改动**只能在真机、由真人操作**才能确认（锁屏、睡眠唤醒、Alt-Tab 切窗口、GUI 点击），自动化测试覆盖不到——单测能证明「复位函数写对了」，证明不了「真锁屏那一下确实触发了它」。这些验收项此前散落在 `docs/变更归档.md` 各条目的「**未验证**」句里，只有一句话，接手的人不知道从哪下手。
>
> 这里把它们收成**可照做、可复跑**的步骤：每条都有前置配置、操作步骤、预期现象、以及「出现什么就算失败」。默认从**最新的可靠性项**往回排。
>
> **谁该读**：要验收这些改动的人（目前就是作者本人）。**什么时候跑**：改到钩子 / 状态机 / 动作执行后跑相关那几条（不必每次全跑）；发版前若时间允许，跑第 1~8 条。

## 0. 通用准备（每条都要用）

### 0.1 怎么看到日志

壳层留痕走 `eprintln!`，**只有带控制台的构建才看得到**：`src-tauri/src/main.rs` 是 `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`——release 版没有控制台，stderr 会直接丢掉；**debug 版从终端启动才有输出**。

```powershell
# 先退出正在运行的那一个（托盘右键 → 退出）；两个实例会抢同一套全局钩子
taskkill /IM kada.exe /F

# 需要时先构建 debug 版
cargo build -p kada

# 从终端启动，日志就打在窗口里
.\target\debug\kada.exe
```

要验证的复位留痕是这一行（`_` 处是原因）：

```
kada: 输入状态已复位（前台窗口切换）
kada: 输入状态已复位（钩子已重装）
```

**注意**：这行**只在壳层真的丢了状态时才打印**（`Engine::reset` 返回 `false` 就什么都不打）——所以「没看到日志」不等于「复位没跑」；能看到它时是好消息，看不到时要靠下面的**功能现象**判断。

### 0.2 两条纪律

- **debug 版与 release 版共用同一份配置**（`%APPDATA%\com.kada\config.json`）。测试期间加的测试条目（改键 / 文本扩展 / 快捷键）测完记得删掉，否则会一直生效。
- **关主窗口 ≠ 退出**（托盘常驻是设计）。退出只能走托盘菜单「退出」，或 `taskkill /IM kada.exe /F`。

### 0.3 通用观测位置

| 要看什么 | 在哪看 |
|---------|-------|
| 复位留痕、注入失败、创建窗口失败 | 启动它的那个终端窗口（仅 debug 版） |

## 1. 前台切换 → 收回注入的修饰键（P1-④） ✅ 2026-09-29 通过

**要证的事**：按住切层/长按键期间注入出去的 Ctrl，在 Alt-Tab 切窗口时被**补一个 up** 收回来。不复位的后果是「修饰键粘住」——系统层面 Ctrl 一直按着，新窗口里敲什么都成组合键。

**前置配置**：改键页新增一条，`from` = `CapsLock`，「长按」（长按输出）= `Ctrl`，保存。
（短按输出留空即可——留空时短按会按吞键铁律回放原键，不影响本测试。）

**步骤**：

1. 打开记事本（或任意能输入文本的窗口），让它在最前台。
2. **按住 CapsLock 不放**，再按一下 `K`。
   这一步让状态机判定为「长按」（roll 判定），把 Ctrl **物理注入**下去——此刻系统层面 Ctrl 是按下状态。
3. **保持按住 CapsLock**，按 `Alt+Tab` 切到另一个窗口（另一个记事本 / 浏览器地址栏）。
4. 等大约 **0.5 秒**，让新窗口稳定在前台。
   前台切换要**连续两轮**巡检（各 60ms）才认，所以给足两轮以上。
5. 松开 CapsLock。
6. 在新窗口里敲一下字母 `a`（**不要**碰 Ctrl）。

**预期**：新窗口里正常出现 `a`。

**判失败**：敲 `a` 没有任何字符出现，或触发了 **Ctrl+A 全选**（浏览器地址栏 / 记事本会全选）——说明注入的 Ctrl 从未被收回，**修饰键粘住了**，本项不通过。

**顺带确认**：终端里应出现 `kada: 输入状态已复位（前台窗口切换）`（在切窗口后约 120ms 内；若此前没有任何待定状态则可能不打，见 §0.1）。

**万一 Ctrl 真的粘住了怎么恢复**：按一下物理 `Ctrl` 键再松开——真实的一对 down/up 会把系统状态冲正，不用重启应用。

## 2. 前台切换 → 热串缓冲不回放（P1-④） ✅ 2026-09-29 通过

**要证的事**：在 A 窗口敲了一半的文本扩展触发词，切到 B 窗口后敲后缀**不会**在 B 里展开成替换文本。复位口径是「缓冲里的东西一律丢弃不回放」——因为复位时前台目标已经变了，把旧按键注入到新窗口（可能是密码框）比丢掉更糟。

**前置配置**：确认「文本扩展」页有一条触发词，比如 `addr`（替换文本随便是什么都行）。没有就加一条，保存。

**步骤**：

1. 打开窗口 A（记事本），点击进入可输入状态。
2. 在 A 里敲 `add`（**不要**再敲空格 / 回车 / Tab，也不要敲完整触发词）。
3. `Alt+Tab` 切到窗口 B（另一个记事本，或浏览器里的输入框），等约 0.5 秒。
4. 在 B 里敲 `r`，紧接着敲一下空格。

**预期**：B 里看到的就是你亲手敲的 `r `（或连上 B 里原本的内容）——**不展开**成替换文本。

**判失败**：B 里突然变成替换文本（触发词被回删、注入了替换内容）——说明在 A 窗口敲了一半的缓冲被带过了窗口边界，本项不通过。

> 这条测试的价值在于它**能被肉眼立刻分辨**：成功与失败输出的是两段完全不同的文字，不需要任何工具辅助。

## 3. 锁屏 → 解锁（P0-① 重装 + P1-④ 复位） ✅ 2026-09-29 通过

**要证的事**：`Win+L` 锁屏再解锁后，钩子被看门狗判为「已重装」（判据是 `WTSInfoEx.SessionFlags` 的 锁定→未锁定 跃迁：反直觉字段 0=锁定、1=未锁定），壳层跟着复位。

**步骤**：

1. 保持 debug 版从终端运行（§0.1）。
2. 按 `Win+L` 锁屏，等 2 秒以上，再解锁回到桌面。
3. 解锁后**立刻**做两件事：按一次你配好的快捷键（如 `Alt+X`）；再敲一次文本扩展（触发词 + 空格）。
4. 看一眼终端输出。

**预期**：快捷键与文本扩展都正常生效；若解锁前壳层有残留状态，终端会多出 `kada: 输入状态已复位（钩子已重装）`。

**判失败**：解锁后快捷键 / 改键 / 文本扩展**全部无响应**（说明钩子没被重装，看门狗这条判据失效），或出现「修饰键粘住」——都算不通过。

**说明**：看门狗巡检 1 秒一次，所以解锁后最多约 1 秒才重装并复位落地，属正常；这一步同时也是 P0-① 看门狗唯一能由真人稳定复现的触发路径。

## 4. 休眠 → 唤醒（P0-①） ⬜ 未执行

**要证的事**：看门狗能用 `GetTickCount` 的跃变（**该计数把睡眠时间也算进去**）发现机器睡过，并重装钩子。

**状态**：**未执行**——2026-09-29 首轮人工验证唯一没跑的一条。看门狗的重装动作本身已由 §3（解锁路径）在真机确认，但「相邻巡检间隔 > 10s ⇒ 机器睡过」这条判据仍只由单测覆盖，没在真机上跑过。可以下次休假前顺手做。

**步骤**：

1. 保持 debug 版从终端运行。
2. 开始菜单 → 电源 → 睡眠。**睡够 10 秒以上**（判据是「相邻两次巡检间隔 > 10s」，睡太短不足以越过阈值）。
3. 唤醒机器（动鼠标 / 按键盘）。
4. 唤醒后立刻按一次快捷键 + 敲一次文本扩展。

**预期**：都正常生效；终端可能出现 `kada: 输入状态已复位（钩子已重装）`。

**判失败**：唤醒后所有触发无响应，或修饰键粘住。

## 5. 冷启动双击唤醒（P1-⑤） ✅ 2026-09-29 通过

**要证的事**：唤醒路径的**建窗**跑在后台线程，不会把钩子回调拖过系统超时线（约 300ms）而被摘钩。这条最凶险的形态是**开机自启**：主窗口没预建，首次双击唤醒要冷启动 WebView（几百毫秒），正好撞在那条路上。`--autostart` 参数就是用来复现这个状态的。

**前置配置**：设置页「快速唤醒」选一个键（如「双击 Alt」），保存。

**步骤**：

1. 完全退出 Kada（托盘 →「退出」）。
2. **用静默模式启动**（模拟开机自启，主窗口不预建——这是本测试的关键）：

   ```powershell
   .\target\debug\kada.exe --autostart
   ```

   观察：不应有任何窗口出现（只有托盘图标）。
3. 随便点开一个别的窗口（如记事本），让**主窗口处于未创建状态**。
4. 快速双击你设的唤醒键（两击间隔 ≤ 400ms）。
5. 看主窗口是否出现、终端是否报错。
6. **重复第 3~5 步 3~5 次**，其中至少一次是「不等待、连点两轮双击」——用于撞「并发建窗」那条竞态。
7. 再验证唤醒键本身**不被拦截**：在记事本里，`Alt+Tab`、`Alt+字母` 应照常可用。

**预期**：主窗口每次都正常出现；终端**没有** `创建主窗口失败`；`Alt+Tab` / `Alt+字母` 正常。

**判失败**：唤醒键按了没反应；终端出现 `创建主窗口失败`（并发建窗的回查分支没生效）；或唤醒后**快捷键全部失效**（钩子被回调超时摘掉了，这正是本项要防的）。

## 6. 动作超时 + 杀整棵进程树（P1-⑦） ✅ 2026-09-29 通过

**要证的事**：命令挂住时被**限时**终止（不再是无限等待），而且是连**孙进程**一起杀（`Child::kill` 杀不掉 `cmd /C` 下面真正干活的那层）。

**前置配置**：

1. 设置页「动作超时」填 `2`（秒），保存。改完立即生效，不用重启（超时值在触发时从配置读出）。
2. 新建一条快捷键（如 `Alt+F9`），动作 = **执行命令**（Shell 选 CMD），命令填：

   ```
   powershell -NoProfile -Command "Start-Sleep -Seconds 30; New-Item -Path '%TEMP%\kada_tree_marker.txt' -ItemType File | Out-Null"
   ```

   这条命令的结构是刻意选的：我们的进程 → `cmd /C <临时批处理>` → `powershell`（**孙进程**）→ 睡 30 秒后建标记文件。只杀直接子进程的话，标记文件照样会出现。
3. 先手工删掉 `%TEMP%\kada_tree_marker.txt`（若存在）。在资源管理器地址栏输入 `%TEMP%` 回车即可打开该目录。

**步骤**：

4. 触发 `Alt+F9`。
5. 观察动作何时结束（命令本身要跑 30 秒，被超时终止应在约 **2 秒**就返回）。
6. 打开主窗口 →「消息」页，看新增的那条结果。
7. **再等 35 秒**，回到 `%TEMP%` 目录看标记文件在不在。
8. **对照组（很重要）**：把「动作超时」改成 `0`（不限），再触发一次，等到命令自然结束（约 30 秒）——这次标记文件**应该**出现。

**预期**：

- 第 5 步：约 2 秒返回（不是 30 秒）。
- 第 6 步：结果里 `stderr` 含一句 `〔咔哒〕执行超时（超过 2 秒），已强制终止该进程及其子进程。`；**退出码显示「—」**（被强杀的进程退出码没有语义，程序置空，前端渲染成「—」）。
- 第 7 步：标记文件**不存在**。

**判失败**：

- 第 5 步等了 30 秒才结束 → 超时没生效。
- 第 6 步没有「执行超时…」这句 → 原因没写进 stderr（用户看不到归因）。
- **第 7 步文件出现了 → 只杀了直接子进程、孙进程还在跑**，这是本项最关键的验收点，出现即不通过。
- 第 8 步对照组的文件也没出现 → 说明是命令本身没跑起来（比如引号被转义坏），前面的「没出现」是假阳性，要重新验证。

> 第 8 步的对照不能省：没有它，「文件不存在」这个结果无法区分「杀干净了」和「命令压根没执行」。

## 7. 停止执行按钮（P1-⑦） ✅ 2026-09-29 通过

**要证的事**：用户点「停止执行」能真的叫停正在跑的动作链，且**不假装成功**——没有在跑的东西时如实说「当前没有正在执行的动作」。

**2026-10-21 入口改版**：按钮从标签栏右端移到卡片头「执行中」徽标右侧（■ 图标，只在执行中的记录上出现），本节的点击位置已同步；改版后需复跑一次。

**前置配置**：

1. 设置页「动作超时」填 `0`（不限）——避免 30 秒自动超时结束干扰本测试。
2. 新建一条快捷键（如 `Alt+F10`），动作 = 执行命令（CMD）：`ping -n 60 127.0.0.1 >nul`（约跑 59 秒）。

**步骤**：

3. 触发 `Alt+F10`（命令开始跑）。
4. 立刻打开主窗口（双击托盘图标）→「消息」页：正在跑的那条记录自动排在最上面并被选中 → 点卡片头「**执行中**」徽标右侧的 ■ 图标按钮。
5. 看提示与命令是否停。
6. 切到一条已结束的记录（或等命令停完），确认「执行中」旁边**不再有** ■ 按钮。

**预期**：

- 第 4~5 步：提示 **`已请求停止（1 条正在执行）`**；命令**立刻**结束（判定粒度 20ms，最多迟 20ms 就开始杀进程）；「消息」页新增一条 kind 为 abort 的记录，内容是 `已停止执行：剩余动作不再执行，正在运行的命令 / 脚本已强制终止。`
- 第 6 步：跑完 / 已中止的记录上没有停止按钮；若恰好在「刚跑完、界面还没重绘」的一瞬点到，提示仍是如实的 **`当前没有正在执行的动作`**。

**判失败**：

- 第 5 步提示「当前没有正在执行的动作」（说明「正在执行」计数没加上去，`RunGuard` 漏了），或提示了「已请求停止」但命令还在跑（中止判定点失效）。
- 第 6 步已结束的记录上仍显示 ■ 按钮（状态判定没跟上）→ 按钮会一直留在那儿，点了只能说「没有正在执行的动作」。

> 第 6 步就是「反馈不假装成功」这条设计的验收：什么都不跑的时候点停止，也必须得到诚实的回答。

## 8. 动作失败上报消息中心（P1-⑥） ✅ 2026-09-29 通过

**要证的事**：一个必然失败的动作，用户能在消息中心看到「**哪一步**失败、拿**什么值**去做的、**为什么**失败」，而不是只有「按了没反应」。（release 版没有控制台，stderr 日志看不到，所以只能靠消息中心判断。）

**前置配置**：

1. 新建一条快捷键（如 `Alt+F10`），动作 = 文件操作 → 删除，路径填一个**不存在**的路径（如 `D:\没有这个目录\x.txt`）。
2. 同一条快捷键后面再追加一个动作：暂停 100 毫秒（它不会产生任何记录，用来顺带看「一步失败不中断后续动作」——触发一次应当只多**一条**记录）。
3. 再新建一条快捷键（如 `Alt+F11`），动作 = 执行脚本，路径填一个**不存在**的脚本文件，并把该动作的「弹窗显示结果」**打开**。

**步骤**：

4. 触发 `Alt+F10`（坏路径动作）。
5. 打开主窗口（双击托盘图标）→「消息」页，看新增的那条记录。
6. 触发 `Alt+F11`（起不来的脚本，开了「弹窗显示结果」）。

**预期**：

- 第 4 步：托盘图标出现**红点**，应用内「消息」入口亮红点。
- 第 5 步：tab 标题是 **`文件操作失败 · 名称`**（没填名称则是 `文件操作失败 · Alt+F10`）——注意列表头是「**执行记录**」，一次触发一条记录；该记录的时间线里**失败的动作块**（红色边框）与后面那个不产结果的「暂停」块都在，块上 hover 有起止时刻与耗时；卡片里「命令」一栏是 **`删除 D:\没有这个目录\x.txt`**（若该动作填了「描述」，则显示 `描述（删除 …）`）；stderr 是失败原因（`删除失败：「…」不存在`）；退出码 `—`。
- 第 6 步：**弹窗自动出现**（因为该动作开了「弹窗显示结果」），标题 `命令结果 · 脚本失败`，stderr 里是脚本起不来的系统错误。

**判失败**：

- 第 5 步消息中心**没有任何新记录** → 失败仍只在 stderr 日志里（本项未生效）。
- 第 5 步记录里「命令」一栏为空、或原样留着 `{变量名}` 这类占位符 → 摘要没渲染 / 变量没代入。
- 第 6 步**没有弹窗** → `show_output` 被失败路径一律降级成静默了（应当沿用动作自身的设置）。
- 若第 5 步出现不止一条记录 → 说明有别的动作也在报（本例的第二个动作是暂停，没有失败路径）。

> 第 6 步是「命令/脚本连启动都没成功也该弹窗」这条设计的验收；第 4~5 步的红点则是所有非弹窗类失败的默认表现。

## 9. 未保存改动守卫（P1-⑧） ⬜ 待真人复跑（纯浏览器演示模式已验，见末尾）

**要证的事**：编辑页里改到一半，点另一行 / 切页 / 关编辑页**不会静默丢改动**——要么被问一句，要么保存下来；且「保存并离开」真的落盘了才放行。

**前置配置**：无（用现有任意条目即可）。**本项不需要 debug 版日志**，看界面现象就够。

**步骤与预期**（每步都给了判失败）：

1. 打开「快捷键」页 → 点一条已有条目 → 改「描述」输入框。
   - 预期：**标题行右侧**亮出**黄色「● 未保存」标记**，同排「撤销改动」（↶）图标由禁用变为可用。
   - 判失败：改了描述标记不亮 → 签名没把「描述」这个只在保存时才读的字段算进去。
2. 点「撤销改动」。
   - 预期：描述还原成打开时的内容，标记消失、按钮回到禁用；编辑页**不关**。
   - 判失败：描述没还原，或编辑页被关掉/跳走。
3. 再改一次描述 → 点**列表里另一条**。
   - 预期：弹出确认框「**快捷键「xx」有未保存的改动。**」，三个按钮「继续编辑 / 放弃改动 / 保存并离开」。
   - 判失败：直接切过去了（改动静默丢失）。
4. 点「继续编辑」。再点另一条 → 点「放弃改动」。
   - 预期：第 4 步留在原条目且仍是脏；之后切到另一条，原条目的描述**没有**被改。
   - 判失败：「继续编辑」之后仍然切走了。
5. 重新打开原条目 → 改描述 → 点「**保存并离开**」。
   - 预期：切到目标条目；**再重新打开原条目，描述是刚保存的内容**（这一步是「真的落盘了吗」的验收）。
   - 判失败：切过去了但重开后描述还是旧的 → 保存没成功却放行了。
6. 脏状态下点左侧导航「改键」（切页）。
   - 预期：同样弹确认框（框内文案带条目名）；点「继续编辑」留在原页；也可以直接按 **Esc**，等价于「继续编辑」。
   - 判失败：Esc 之后切页了（Esc 不该是破坏性动作）。
7. 标题行右侧的「取消（✕）」图标：脏状态下点它。
   - 预期：也弹确认框；「继续编辑」留在编辑页，「放弃改动」才关闭编辑页。
   - 判失败：直接关掉（改动静默丢失）。
8. 「+ 新增」→ 什么都不填就再点「+ 新增」。
   - 预期：**不弹框**（空白新条目不算改动），直接换成新的空白编辑页。
9. 「+ 新增」→ 填点东西 → 再点「+ 新增」。
   - 预期：弹框；「放弃改动」后回到空白的新条目（标题「（未命名）」、标记消失）。
10. 改键页：打开一条改键 → 点「原键」输入框出按键下拉、选一个 → 点「撤销改动」（↶）。
    - 预期：本页标记亮 → 撤销后回原键，标记灭。**顺带看**：切到别的页时不该看到别的页的标记亮着。
    - 判失败：改了「原键」标记不亮（这是「只在保存时才读回草稿的字段」里最容易漏的一个）。
11. 保存失败不放行：打开一条改键 → 把「短按 / 长按 / 改为」**全部清空**（此时该条目已无任何输出）→ 点侧栏切页 → 弹框里点「保存并离开」。
    - 预期：**留在改键页**，toast 提示「请至少设置一种输出：…」，标记仍然亮着。
    - 判失败：切页了（说明「保存失败也放行」，改动会丢）。
12. 列表启用态不被盖掉：打开某条快捷键 → 在**列表行**的 `⋯` 菜单点「禁用」 → 在编辑页改点东西 → 点「保存」→ 关掉再重开该条。
    - 预期：该行**仍压暗（停用）**（编辑页里没有启停控件，保存不该把列表上刚设的状态翻回去）。
    - 判失败：开关又自己变成启用了。
13. 关窗不丢：脏状态下直接关主窗口（右上角 ×）。
    - 预期：**不弹任何确认框**（关窗只是收进托盘）；从托盘再打开主窗口，编辑页与改动**都还在**（草稿在内存里，程序没退出）。
    - 判失败：关窗后重开发现草稿没了。

**判失败（汇总）**：任何一步「改动没被提示就消失了」；「保存并离开」之后重开发现内容没落盘；标记亮着但点保存后仍亮（或反之）；Esc 造成破坏性结果。

**状态**：⬜ **真人复跑待做**（Tauri 壳里的点击）。**2026-09-29 已在纯浏览器演示模式（`ui/src/mock.ts`）把上面 1~12 步的逻辑等价地跑过一轮，全部符合预期**——差异只有 mock 换成了真 IPC 与原生文件对话框，第 13 步（关窗收托盘）演示模式没有对应行为、只能真人验。之所以仍标「待真人复跑」：本清单的规矩是**只认真机结果**，演示模式通过不等于壳里通过（比如真实保存要走 `set_config` 落盘，失败分支要真出错才能触发）。

## 10. 删除确认 + 导入合并 / 替换（P1-⑨） ⬜ 待真人复跑

**要验的**：删除任何**已保存**的条目都先问一句，且问的那条与被删的那条是同一条；导入不再点一下就整份替换，而是先选「合并 / 替换」，替换前自动留档，导入结果能逐条复盘。

**前置**：随便配几条快捷键（其中一条**放进一个自建目录**）、一条改键、一条文本扩展；再准备两份 JSON 备用——**A**：从「导出配置」导出的当前配置副本；**B**：手改 A 得到的一份「有撞车也有新条目」的配置（例如其中一条快捷键的触发键与现有某条相同、另加一条新的改键与原键相同的改键、再加一条全新触发键的快捷键）。

1. **删除快捷键（列表行菜单）**：点某行的 `⋯` → 「删除」。
   - 预期：弹出确认框，文案是「删除快捷键「名称」？删除后应用内无法撤销。」（无名条目退回显示触发键）。
   - 判失败：直接删掉了、没有任何确认。
2. 上一步的确认框点**取消**（或按 Esc / 点窗口关闭）。
   - 预期：那一行**还在**。
   - 判失败：取消之后条目消失了。
3. 再来一次并确认。
   - 预期：行消失、toast「已保存」；**从托盘退出应用再启动，这一条确实没了**（这一步才是「真落盘了」的验收）。
   - 判失败：界面上没了但重启后又回来了（说明只改了内存）。
4. **删除快捷键（标题行按钮）**：打开一条 → 标题行右侧垃圾桶图标 → 确认。
   - 预期：同样弹确认框；确认后列表少一条、编辑页关闭到空态。
   - 判失败：标题行的「删除」不问一句就删。
5. **未保存改动时的删除**：打开一条 → 改一下描述（标题行亮出黄色「● 未保存」）→ 点标题行垃圾桶图标。
   - 预期：确认框里**多一句**「该条还有未保存的改动，会一并丢弃。」。
   - 判失败：没提这件事（用户以为只是删了已保存的内容）。
6. **未落盘的新增项**：点「+ 新增」→ 填点东西 → 点「删除」。
   - 预期：**不弹确认框**，直接回到空态（等同「取消」，没有已保存内容会丢）。
   - 判失败：弹框了（噪声）。
7. **删除目录报出波及范围**：把那两条快捷键放进自建目录 → 目录行 `⋯` → 「删除」。
   - 预期：文案「删除目录「x」及其中的 2 条快捷键？删除后无法撤销。」；确认后目录与其中的条目一起消失。
   - 判失败：文案不报条数（用户不知道要删掉多少东西）。
8. **删除改键 / 文本扩展**：同 1~3，条文案分别是「改键「CapsLock → Ctrl」」「文本扩展「;addr」」。
9. **导入-取消**：设置 → 「导入配置」→ 选 A。
   - 预期：先弹「导入配置」框，正文说明**合并**（只新增、本机设置不动）与**替换**（整份覆盖含设置、会留档）两种方式；点「取消」（或 Esc / 点遮罩）→ **什么都没发生**（配置没变、没有 toast、没有弹结果框）。
   - 判失败：不选就直接导入了，或 Esc 之后还是导入了。
10. **导入-替换 + 留档**：在 A 上先加两条现有配置里没有的条目并保存导出，改名为 C → 设置 → 导入 C → 选「替换（覆盖全部）」。
    - 预期：结果弹窗「已替换为导入的配置：共 N 条…」+ 一行**留档路径**；`%APPDATA%\com.kada\` 下出现 `config.json.pre-import-<时间戳>`，**其内容 = 导入前的配置**；列表只剩 C 里的条目；**开机自启 / 快速唤醒键跟着 C 走**（替换含设置，这条是「替换与合并的区别」的验收）。
    - 判失败：没有留档文件；或留档内容是导入后的（那就白留了）。
11. **导入-合并**：用第 10 步的留档文件（或直接改回来）恢复到导入前的配置 → 导入 C → 选「合并」。
    - 预期：结果弹窗「已合并：新增 N 条，跳过 / 忽略 M 条」+ **逐条明细**；现有条目**一条不少**、C 里的新条目追加在后面；**设置没变**（自启 / 唤醒键 / 超时保持原样）。
    - 判失败：现有条目被删掉或改名；设置被导入文件改掉。
12. **合并的撞车口径**：导入 B → 选「合并」。
    - 预期：明细里逐条出现「快捷键「x」未导入：触发键 Ctrl+Alt+B 已存在」「改键「CapsLock」未导入：该键已有改键」之类；列表**不出现重复条目**、冲突页**不新增红冲突**（合并不会替用户制造冲突）。
    - 判失败：出现两条触发键相同的快捷键、或冲突数变多。
13. **合并幂等**：**再导入一次 B**（同样选合并）。
    - 预期：「新增 0 条，跳过 / 忽略 N 条」，配置与上一步完全一致（重复导入不翻倍）。
    - 判失败：条目翻倍了。
14. **合并的引用完整性**：导入一份含「新层 + 一条长按进入该层的改键」的配置 → 合并。
    - 预期：改键页里这条改键的「长按进入层」下拉**指向那个新层**（不是空白），摘要显示「长按进层「导航层」」。
    - 判失败：层没进来、改键整条作废（这是「先并层再并条目」要挡住的事）。

**判失败（汇总）**：删除任何**已保存**内容时没有确认框；确认框里说的条目与实际被删的不是同一条；取消之后条目还是没了；未落盘的新增项也弹框；点「导入配置」不选方式就整份替换；替换导入后磁盘上没有 `pre-import` 留档；合并删改现有条目、或让设置被导入文件改掉；合并后冒出用户没配过的冲突、或条目翻倍；合并后条目引用的层/目录丢了。

**状态**：⬜ **待真人复跑**（原生确认框 + 真实文件选择 + 跨进程落盘确认）。**2026-09-29 已在纯浏览器演示模式（`ui/src/mock.ts`）把逻辑等价地跑过一轮**：行菜单删除与详情页删除都真的删掉了条目并走了 `set_config`；导入的「合并 / 替换 / 取消」三条路径都按对应 `mode` 发起 `import_config`，结果弹窗文案与逐条明细正确，替换路径带出了留档行。演示模式验不到的是：`ask()` 的原生对话框本身、真实文件对话框、磁盘上的 `pre-import` 留档文件、以及第 3/11 步「重启后仍在」这类跨进程确认。

> **顺带修掉的桩**：演示模式的 `plugin:dialog|message` 原先返回布尔 `true`，而真实后端返回的是**被点击按钮的文案**（`ask()` 拿它跟 okLabel 默认值 `"Yes"` 比对）——于是**演示模式下所有确认框都被判成「否」**，删除目录 / 删除层点了没反应且看不出原因。本次一并改正（`mock.ts` 返回 `"Yes"` / `"Ok"`）。以后在演示模式里验确认框，记得这条已经修了。

## 11. 配置外部修改监听（P1-⑩） ⬜ 待真人复跑

**要验的**：运行期手改 `config.json`（或恢复备份、同步落盘）**真的生效**；应用内的下一个保存**不会把外部改动盖掉**；外部内容坏了（编辑器写到一半）时**磁盘与内存都不被动**；界面上有未保存草稿时**不静默丢弃**。

**前置**：按 §0.1 从终端启动 debug 版（能看见日志，`kada: 输入状态已复位（配置已重新加载）` 就打在窗口里）。配置路径：`%APPDATA%\com.kada\config.json`（同目录还有 `config.json.bak`）。用记事本 / VS Code 打开它备用。准备一条已保存的快捷键（例如触发键 `Ctrl+Alt+K`，下面都拿它举例）。

1. **外部改动生效**：把那条快捷键的触发键从 `Ctrl+Alt+K` 改成 `Ctrl+Alt+9`，**保存文件**。
   - 预期：约 1 秒内（监听每秒巡检一次）——按 `Ctrl+Alt+9` 触发该快捷键，按 `Ctrl+Alt+K` **不再**触发；托盘亮红点，「消息 → 命令结果」里出现一条「配置」：`检测到配置文件被外部修改，已重新加载生效`，细节里报出快捷键 / 改键 / 文本扩展 / 层 / 目录各多少条。
   - 判失败：等多久都不生效（可按 `Ctrl+Alt+K` 仍然触发）；或进消息页看不到任何记录（外部改动静默发生了）。
2. **应用内保存不再覆盖外部改动**：主窗口开着（第 1 步之后）→ 列表里那条**显示的已经是 `Ctrl+Alt+9`** → 随便动一下别的条目并点「保存」。
   - 预期：保存过后 `config.json` 里那条**仍是 `Ctrl+Alt+9`**（打开文件确认），没有被改回 `Ctrl+Alt+K`。
   - 判失败：文件里又变回旧触发键（说明界面用的是过期配置，外部改动被保存覆盖——这正是本项要修的问题）。
3. **自己的保存不误报**：在第 2 步保存的同时看终端与消息页。
   - 预期：**不出现**「外部修改」的记录（应用自己写的盘不该被自己当成外部改动）；只有界面上的「已保存」。
   - 判失败：每保存一次就冒一条「检测到配置文件被外部修改」。
4. **半截 JSON 不动磁盘**：把文件内容改成半截 JSON（例如删掉结尾几个字符、或 `{ "shortcuts": [` 之后截断）再保存。
   - 预期：约 1 秒内出现一条「配置」记录：`配置文件被外部修改，但内容无法解析：已保留当前配置`，细节说明磁盘内容未被改动。**关键**：`%APPDATA%\com.kada\` 下**不出现** `config.json.corrupt-<时间戳>`，`config.json.bak` 也**没被改写**，磁盘上仍是那半截内容；快捷键照旧按**上一份好配置**工作（第 1 步的 `Ctrl+Alt+9` 仍生效）；同一条坏内容**只提示一次**（不每秒刷屏）。
   - 判失败：出现 `.corrupt-` 留档、或文件被 `.bak` 覆盖回去（那说明监听走了启动路径的自愈，会毁掉用户正在编辑的内容）；或坏内容被采纳成「空配置」（快捷键全失效）。
5. **修好后自动重新加载**：把第 4 步的文件补成合法 JSON（比如把触发键改成 `Ctrl+Alt+8`）再保存。
   - 预期：约 1 秒内采纳，`Ctrl+Alt+8` 生效、又出现一条「已重新加载生效」。
   - 判失败：坏过一次之后再也不加载了。
6. **恢复备份**：把 `config.json.bak` 复制成 `config.json`（覆盖）。
   - 预期：约 1 秒内采纳（触发键回到备份里的那个），出现一条「已重新加载生效」。
   - 判失败：覆盖后不生效（这就是「恢复备份不生效」的老毛病）。
7. **未保存草稿不静默丢弃**：打开那条快捷键的编辑页 → 改一下「描述」（标题行亮出黄色「● 未保存」）→ 再去外部改文件保存。

## 12. 序列 / 和弦等待窗进设置（P2-⑫） ⬜ 待真人复跑

**要验的**：设置页两个新窗口（「序列等待」「和弦等待」）**真的管用**——改了立刻生效、不用重载配置；超时的后果是「被吞掉的键原样补回」而不是丢键；填 `0` = 不限时。

**前置**：按 §0.1 从终端启动 debug 版。准备两条已保存的快捷键：序列 `F9 J K`、和弦 `F & J`（`F&J` 两个成员是非修饰裸键）。合上主窗口不会退出应用（托盘常驻）。

1. **默认值看得见**：打开「设置」页。

4. **填 0 = 不限时**：把「序列等待」改成 `0`。
   - 预期：按 `F9` 撒手后**一直不回放**（等到你按下一个键才按断链/推进处理，那个键也会照常打出来）；`F9 J K` 照常能触发。

5. **和弦等待（默认 1 秒）**：把「序列等待」改回 `1000`，「和弦等待」保持 `1000`。按住 `F` **不松**，同时打几个字母（如 `a s d`）。

   - 判失败：字母一直不出来（要等 `F` 松开才吐）；或补出来时顺序错乱；或字母被吞掉不还。
6. **过期后不再凑和弦**：重复第 5 步，但这次在按 `F` 后**等 1 秒以上**再按 `J`。
   - 预期：**不触发**那条和弦快捷键，`F` 与 `J` 作为两个普通按键被补出来（`f`、`j`）。
   - 判失败：还是触发了和弦（说明窗口没起作用）；或 `F`/`J` 有一个没出来。
7. **窗口内照常触发**：把「和弦等待」调大到 `3000`（或改回 `1000`），按 `F` 后**马上**按 `J`。
   - 预期：立刻触发那条和弦快捷键（正常行为不受影响）。
   - 判失败：和弦不再触发（改设置把功能改坏了）。
8. **填 0 = 不限时（旧行为）**：把「和弦等待」改成 `0`。
   - 预期：按住 `F` 等 3 秒以上再按 `J` **仍然触发**（＝本次改造前的行为）；按住 `F` 期间打的字要等 `F` 松开才补出来。
   - 判失败：填 0 反而变成「立刻回放」。
9. **老配置兼容**：退出 Kada，把 `%APPDATA%\com.kada\config.json` 里 `settings` 段的 `sequence_timeout_ms` / `chord_timeout_ms` **两个字段删掉**（模拟本项之前写的配置），保存，重启应用。
   - 预期：设置页两个框显示 `1000`（**不是** 0），序列与和弦行为与第 2 / 5 步一致。
   - 判失败：显示 0 / 按键行为变成「不限时」（那等于老用户被静默改了行为）。
10. **外部改这两项也生效**（与 §11 同源，可选）：运行期直接手改 `config.json` 里 `chord_timeout_ms` 为 `0` 保存。
    - 预期：约 1 秒后采纳（消息页出现一条「配置 · 外部修改」），和弦行为跟着变成「不限时」——不必重启。

**判失败（汇总）**：设置页两个框空白 / 显示 NaN；改了不生效（仍按 1000 走）；填 0 变成立刻回放；超时把键吞掉不还（键变哑）或回放顺序乱；和弦在窗口内也不触发了（改坏了正常路径）；老配置缺字段时被当成 0。

**状态**：⬜ **待真人复跑**。本次只有单测与构建覆盖：`kada-core` `settings_timeout_tests` 3 条（默认值随常量 / 老配置缺字段取 1000 / `0` 往返不被盖回）+ `Engine` 5 条（序列窗口取自设置、序列 `0` = 不限时且不影响命中、和弦窗口到点按输入顺序回放、过期也可由下一个事件懒判、和弦 `0` = 不限时即旧行为）+ `cargo check`（完整 / 基础版）+ 前端构建。**验不到的部分**：真实按键的时序手感、设置页输入框到落盘再到引擎生效的整条链路、以及外部改这两项（要靠 §11 的监听链路）。

## 14. 单次 / 粘滞任意键与带修饰和弦（P2-⑭） ⬜ 待真人复跑

**要验的**：① `oneshot`/`sticky` 用**非修饰键**时真的是「替你按住它」（而不是像以前那样被静默丢弃、配了等于没配）；② 和弦成员带修饰（`Ctrl+F&J`）与纯修饰键成员（`Ctrl+Alt&J`）真的能凑齐触发，且**修饰键从不被吞**（`Ctrl+Alt+Tab` 仍是 `Ctrl+Alt+Tab`）；③ 没凑齐时成员键按吞键铁律**原样回放**（键不变哑）；④ 和弦间的超集软冲突能被检测出来。**这条只能人工跑**：低层钩子忽略注入事件、不进状态机，合成按键构造不出前置条件（同 §13）。

**前置**：按 §0.1 从终端启动 debug 版。配置里准备（都保存）：① 改键 `F1` = **粘滞 `MouseBack`**（侧键「按住说话」）；② 改键 `F2` = **单次 `Enter`**；③ 两条快捷键（各给一个能看见的动作，如气泡或输入文本 `x` / `y`）——`Ctrl+F&J`、`Ctrl+Alt&J`；④ 同层再放两条 `F&J` 与 `F&J&K`（用于第 7 步验软冲突）。打开一个记事本窗口备用。

1. **单次键用非修饰键（值域真的扩了）**：点一下 `F1` 之外的 `F2`（单次 `Enter`），然后**什么都不按**看记事本。
   - 预期：光标**立刻换到下一行**（Enter 在武装那一刻就被物理按下）；状态指示出现「单次 Enter」。
   - 判失败：指示里**没有**「单次 Enter」（说明非修饰键的值被 `key_as_modifier` 那条老逻辑丢掉了——本项要修的就是它）；或记事本毫无反应。
2. **单次在下一个键抬起后释放**：接上一步，在记事本里打一个字母 `a` 再**松开**它。
   - 预期：输入 `a`；松开 `a` 之后指示里的「单次 Enter」消失（Enter 被释放）。
   - 判失败：指示一直挂着（没释放，等于 Enter 永久按住）；或打字时被 `a` 之外的字符干扰。
3. **粘滞非修饰键（侧键按住说话）**：点一下 `F1`（粘滞 `MouseBack`）。
   - 预期：指示出现「粘滞 MouseBack」并**保持**（键被锁住一直按着）；在浏览器里点一下页面再点前进按钮后，侧键「后退」能生效（MouseBack 确实处于按住/触发态）。再点一下 `F1` → 指示消失。
   - 判失败：指示不出现（非修饰键被丢掉）；或再点一下不消失（解不开锁）。
4. **带修饰的和弦**：按住 `Ctrl` 不放，按 `F`、再按 `J`（`Ctrl` 全程按住）。
   - 预期：触发 `Ctrl+F&J` 的那条动作；指示显示按住 Ctrl；松开后复位。
   - 判失败：不触发；或触发成别的条目。
5. **纯修饰键成员**：按住 `Ctrl` 与 `Alt`，再按 `J`。
   - 预期：触发 `Ctrl+Alt&J` 的动作（两个修饰键必须在**按 J 之前**就按住）。
   - 判失败：不触发（说明修饰键成员的「要求按住」判定没生效）。
6. **修饰键从不被吞（关键项）**：按住 `Ctrl` 与 `Alt`，然后按 `Tab`。
   - 预期：**仍是 `Ctrl+Alt+Tab`**（切换窗口生效）——修饰键被放行，没有被和弦吞成 `Ctrl+Tab` 或 `Alt+Tab`。
   - 判失败：`Ctrl+Alt+Tab` 退化成 `Ctrl+Tab` / 无反应（修饰键被吞了，会影响全局组合键）。
7. **没凑齐原样回放**：单独按一下 `F`（不按 `J`）、单独按一下 `J`（不按 `F`），各松手。
   - 预期：记事本里正常打出 `f`、`j`（各自的按下与抬起都补回来，键不变哑）。
   - 判失败：某个键不出字符（被吞掉没回放）。
8. **和弦间软冲突提示**：把 `F&J` 与 `F&J&K` 放在**同一层**并保存（两条 `Ctrl` 和弦另放别的层或删掉）。
   - 预期：消息页「冲突」标签出现一条 **Warn**（黄色）：「和弦『F&J&K』永远触发不到：『F&J』的要求更宽…」；把两条书写顺序对调后重新保存，**仍报 `F&J&K`**（成员更少的那条必然先凑齐，与顺序无关）。
   - 判失败：两条都不报；或把 `F&J` 报成「永远触发不到」（方向反了）。
9. **不同修饰不误报**：只留 `Ctrl+F&J` 与 `Alt+F&J`（去掉 `F&J`/`F&J&K`）。
   - 预期：**没有**冲突提示（两条在各自修饰键下都可达）。
   - 判失败：报了冲突（把「互不包含的修饰要求」误判成遮蔽）。
10. **老配置兼容**：退出 Kada，确认配置里原有的「单次/粘滞修饰键」（`Ctrl`/`Shift` 这类）改键仍然有效——值域是**放宽**不是改语义，无需迁移。
    - 预期：老的单次/粘滞改键行为与以前完全一致；`Ctrl+F&J` 这类新写法的旧配置（若有）也能正常加载。
    - 判失败：老的修饰键改键失效（说明改造破坏了原路径）。
11. **编辑器值域与录入**：打开改键编辑器。
    - 预期：「单次键 / 粘滞键」两个下拉是**全键表**（能选到 `A`、`F5`、`MouseBack` 等，不再只有四个修饰键）；和弦录入时**按住 `Ctrl` 再按两个字母**，提交文本是 `Ctrl+X&Y` 形式。
    - 判失败：下拉里只有 Ctrl/Alt/Shift/Meta；或按住修饰键录入被当成成员而报「不能是修饰键」。

**判失败（汇总）**：非修饰键的单次/粘滞在指示与功能上都不生效（值域没真扩）；单次不在下一个键抬起后释放、或武装键自身再按被判成消费；粘滞第二次点击解不开锁；带修饰和弦凑不齐 / 修饰键被吞（`Ctrl+Alt+Tab` 退化）/ 没凑齐时不回放（键变哑）；修饰键成员要求按住却不需要按住就能触发；和弦超集软冲突漏报或方向反了；不同修饰要求被误报成冲突；老配置的修饰键改键失效；编辑器下拉仍是四个修饰键。

**状态**：⬜ **待真人复跑**。已有覆盖（`cargo test --workspace` 全绿）：`kada-core` 冲突 6 条（修饰键成员不遮蔽组合 / `F&J` 与 `Ctrl+F&J` 不算重复 / 超集警告含反序 / 同键更宽要求按顺序判 / 不同修饰要求不冲突 / 跨层不判）+ 和弦解析与 tracker 4 条（带修饰成员解析与显示 / 纯修饰键成员折叠 / 成员修饰须按住 / 修饰键成员不进集合）+ `Engine` 5 条（单次普通键按住到下一键抬起 / 自重按不重复注入 / 粘滞普通键两次切换 / 带修饰和弦须按住修饰键 / 修饰键成员不被吞）+ 指示载荷 1 条（非修饰键如实显示键名）+ `cargo check`（完整版 / 基础版）+ 前端构建。**验不到的部分**：真实按键下的手感与语义（尤其「替你按住它」在目标程序里看到的时序、侧键粘滞的实际效果）、修饰键成员在真机钩子 mods 上报下的判定、以及冲突提示在消息页面的呈现。

## 16. UI 键盘可达性与表单打磨（⑮⑳） ⬜ 待真人复跑（纯浏览器演示模式已验逻辑）

**要验的**：⑮ 列表行键盘可达、hover-only 控件的 focus 等价、重绘不丢焦点、结果弹窗焦点陷阱与 Esc、Ctrl+S / Ctrl+F / Delete 全局键、行菜单键盘化；⑳ 筛选、多选批量启停、复制一份、合并列表同类拖拽排序、数值钳制、内联校验。**这条能在浏览器演示模式预演大半**（`npm --prefix ui run dev` 后直开 `http://[::1]:1420/`），但「全局键 / 焦点环 / 拖拽手感」要以壳内真机为准。

1. **键盘走查**：不碰鼠标，Tab 从地址栏进界面逐个走——列表行应可聚焦（`role="option"`），回车/空格打开详情或展开目录；聚焦行后「⋯」应出现（`:focus-within`）；帮助问号聚焦时气泡应显示。
   - 判失败：某行聚焦后毫无视觉反馈；回车无反应；「⋯」只有鼠标悬停才出现。
2. **重绘焦点**：聚焦某行 → 按空格切换该行「启用」开关。
   - 预期：焦点仍在该行（可继续 Tab）。
   - 判失败：焦点掉回 body，Tab 要从头数。
3. **结果弹窗**：触发一条 `show_output` 的命令快捷键 → 弹窗内 Tab 应在框内循环、Esc 关闭并归还焦点。
   - 判失败：Tab 跑到弹窗背后的界面；Esc 关掉的是别的层。
4. **全局键**：编辑页改描述 → `Ctrl+S` 保存；`Ctrl+F` 聚焦搜索；聚焦详情页某条 → `Delete` 弹删除确认；打开录制后按 `Ctrl+S`——录到的应是按键而非触发保存。
   - 判失败：任一全局键无响应；或录制时 `Ctrl+S` 触发了保存（捕获阶段拦截失效）。
5. **筛选 + 多选**：「筛选 → 有冲突」下拉只留冲突条目；Ctrl 加减 / Shift 范围多选 → 行菜单「禁用」一次落盘（已无「全选」按钮，筛选收窄 + Shift 范围选即整段选取）；Shift 范围选**不跨目录**（锚点与目标不在同一目录时只选目标本身）；目录行 `⋯` / 右键「启用该目录 / 禁用该目录」一次把该目录子树里全部条目启停（文案带条数）。
   - 判失败：筛选漏条目（改键冲突的「键 → 目标」合引号格式没认出来）；批量保存后部分条目没变；Shift 范围选跨过了目录边界；目录级启停漏掉子目录里的条目。
6. **数值与校验**：长按阈值填 `10`（<50）保存 → 落盘应为 50；路径填 `a<b` → 行下红字；扩展触发词清空保存 → 应被拦住（否则整条被 `save()` 剔除，用户以为存了其实没了）；新增改键不动原键直接保存 → 应被拦住并把原键框标红（新建默认原键为空，不再预填 `CapsLock`）。
   - 判失败：负值 / 越界值落盘；红字常驻（存量值一打开就标红）。

**状态**：⬜ 待真人复跑（演示模式已验：筛选 / 批量 / 拖拽 / 校验逻辑；`npm --prefix ui run build` 通过）。

## 20. 执行记录：时间线与流水线两种视图 ⬜ 待验证

**要证的事**：一次触发后，消息页这条记录能看清「每个动作」的执行情况——不是只有命令类动作。文本 / 按键 / 延迟这类动作原先完全不落痕迹，「按了没反应」在界面上无从查起。

**前置配置**：

1. 新建一条快捷键（如 `Alt+F12`，名称填「演示执行」），依次加四个动作：① 文本操作（原样输入 `hello`）；② **并行执行**，成员放两条命令（`timeout /t 3` 与 `echo ok`，Windows）；③ 条件判断（条件填一个必然成立的条件，如「路径存在」`D:\`），then 里放一条命令；④ 暂停 1000 毫秒。
2. 另建一条快捷键（`Alt+F13`）只放一条必然失败的删除（路径不存在），用来同时看「有失败」的配色与结论徽标。

**步骤**：

3. 触发 `Alt+F12`（**链还在跑时**就切到消息页看，别等它跑完）。
4. 等链跑完后，点开这条记录 → 切「时间线」。
5. 点某个动作块。
6. 切「流水线」，点其中一个动作块。

**预期**：

- 第 3 步：记录**边跑边长**（tab 在「执行中」，每结束一个动作就多出一个块），不是跑完才出现；四个顶层动作 + 并行容器 + 三个成员 + 条件容器 + 分支动作全都在，**文本与延迟动作也有块**。
- 第 4 步：横轴是时间（标尺 0 → 总耗时）；并行的两条命令**在同一时间窗口里并排**（不重叠地占满整段时间）；条件块横跨它那条分支；失败块红色边框。hover 任一块给出「开始 → 结束（耗时）」。
- 第 5 步：块选中、**下方展开详情**（开始 / 结束 / 耗时 / 状态 / stdout / stderr / 退出码；命令类动作能看到 stdout）。
- 第 6 步：流水线**自上而下**；条件判断只画走的那条分支、标着「条件成立」；并行两个成员各占一条泳道、标着「并行 1 / 并行 2」，左侧竖线 + 肘形连接；点块**就地展开**同样的详情。
- 触发 `Alt+F13`：该记录顶部的结论徽标是「**有失败**」，失败块在两种视图里都标红。

**判失败**：

- 链跑完后记录才出现（没有逐步推送）／只有命令类动作有块（文本 / 按键 / 延迟没留步 → 「按了没反应」又查不到了）。
- 时间线上并行成员上下排开而不是同一时间窗口并排（泳道分配错）／时间块宽度与实际耗时对不上（块尾外伸 12px 是给后块遮盖用的，看主体比例）。
- 时间线右侧顶出横向滚动条（末刻度 / 末块溢出内容区，`.tl` 右留白失效）／后触发的块盖不住前块、看不出遮盖层次。
- 流水线里条件和并行都画成一条直线（没分泳道），或分支标的是**没走**的那条。
- 「停止执行」后：记录里多出一个「已中止」收尾块、剩余动作不再执行（见 §6 的中止验收）。

## 23. 同步存档（本地文件夹通道） ⬜ **待真人复跑**（壳单测 + 构建已过，界面流程没点过）

**要验的**：选一个目录（如 OneDrive 文件夹）后，**每次配置落盘都会自动在那目录里写一份** `kada-config.json`；「立即同步」手动推一次有明确反馈；「从存档恢复」能把目录里的那份合并 / 替换回来；目录不存在 / 被占用时**本地保存照常成功**、只是同步失败不打扰（规划 7.1-㉝，口径见 `需求设计说明书.md` §5.6）。

**前置**：一份可用的配置（随便加一条快捷键便于区分）。建议用**另一个空目录**模拟 OneDrive 目录，不真动云端。

**步骤**：

1. 设置页「配置与数据」卡片 → 点「同步存档」行的**选择目录…** → 选一个空目录 → 保存。
2. 看该目录里是否出现 `kada-config.json`（点开确认是完整 JSON，含刚加的快捷键）；同步存档行的路径文字是否更新为新目录。
3. 随便改一个设置（如换个「动作超时」）→ 回目录看 `kada-config.json` 的修改时间是否跟着更新（自动推送）。
4. 点**立即同步** → 看是否弹「已同步到 <路径>」。
5. 把 `kada-config.json` 复制到一个**新目录**，再在设置里把同步目录改成那个新目录 → 点**从存档恢复…** → 选「合并」或「替换」→ 看导入结果弹窗与列表变化。
6. 反向用例：把同步目录**删掉**（或改名）→ 再改一个设置 → 本地保存应**照常成功**（界面无报错）、只在终端日志里看到 `同步存档写入失败`。
7. 点**清除** → 路径文字回到「未设置」，之后改配置不再往任何目录写。

**预期**：`kada-config.json` 每次保存后都更新、内容与本地一致；目录里另有 `kada-config.json.bak`（`config_io::save` 自带的上次良好副本）；恢复走的是与「导入配置」同一套界面（合并 / 替换 + 结果弹窗）；目录坏掉不拦本地保存。

**判失败**：

- 选了目录后目录里没有 `kada-config.json`，或改了配置它不更新（多半是某条写入路径漏调 `push_sync`，见 §5.6 的维护注意）。
- 同步目录不可用时**本地保存也失败 / 界面报错**（自动推送应尽力而为，只打日志）。
- 「从存档恢复」把本机 `settings` 或现有条目**改了而没出合并结果**（说明走成了意外的整份替换）。
- `kada-config.json` 是半截 / 空文件（说明没用原子写，退回 `fs::write` 了）。

## 24. 鼠标操作录制 ⬜ **待真人复跑**（壳单测 + 构建已过，真机鼠标没录过）

**要验的**：在「鼠标操作」动作编辑器里点「● 录制鼠标操作」后，录一段鼠标动作（移动到某处点击 / 滚轮 / 侧键），停止时录到的鼠标操作替换掉当前动作，保存后能正确回放（规划 7.1-㊱ 扩展，口径见 `需求设计说明书.md` §5.2）。

**前置**：随便一条快捷键，动作类型选「鼠标操作」；Windows 上若配置里没有鼠标键触发，录制期间钩子层应临时挂上鼠标钩子。

**步骤**：

1. 打开该动作 → 点「● 录制鼠标操作」→ 按钮变「■ 录制中（点此停止）」。
2. 把光标移到屏幕某处**点一下左键**，再移到别处**滚一下滚轮**，再移到第三处**按一下侧键（后退/前进）**，然后移到一个**没动就点**的位置点一下右键。
3. 点「■ 录制中」停止 → 动作列表里当前那条被替换成一串鼠标操作：每段位移一条「移动光标」+ 点击 / 滚轮。
4. 点标题行「执行」跑一遍，看光标是否按记录顺序移动并点击 / 滚动到相同位置。
5. **边界**：开始录制后**不碰鼠标**直接停止 → 提示「未录到鼠标动作」、当前动作保留；录制期间按键盘（如 `Ctrl+S`）→ 不应触发保存、也不应被录进鼠标动作。
6. macOS / Linux 各跑一遍同流程（macOS 要用滚轮方向与 Windows 一致；Linux 触控板不适用，须用真鼠标）。

**预期**：录到的位移是「移动到该处再触发」的量（连续移动不录，只记触发点）；侧键记为「鼠标点击侧键·后退 / 前进」；回放落点与录制时基本一致。

**判失败**：

- 动作里出现**连续移动**刷屏（说明把移动事件也逐条录了，应只记触发点位移）。
- 侧键点击**没录到**或录成了按键组合（应落到鼠标操作动作的侧键）。
- 录制期间 `Ctrl+S` 触发了保存（暂停租约没生效）。
- 保存时提示「鼠标移动 / 滚轮的偏移不能同时为 0」的坏条目（说明滚轮量为 0 的次格信号没被丢弃）。
- Windows 上配置不含鼠标键触发时，录制期间**点鼠标左/右键被吞**（录制应只观察、永远放行）。

## 25. Windows 多键盘设备识别（Raw Input 旁路） ⬜ **待真人复跑**（单测 + 注册冒烟已过，需两台键盘真机）

**要验的**：`DeviceIs` 条件在 Windows 上生效——同一颗物理键在**不同键盘**上触发不同条目（触发侧 `when` 门控，7.1-㊶）或 `If` 分支走不同路（规划 7.1-㊷，口径见 `需求设计说明书.md` §4.1 / `架构设计.md` §3.22）。macOS 仍恒不成立（7.2-㊷ 余项）。

**前置**：两台键盘（外接键盘 + 笔记本自带键盘即可）；一条快捷键（如 `Ctrl+K`）加**触发条件**「设备是」。Windows 的标识是 **HID 设备接口路径**（含 `VID_xxxx&PID_xxxx`），匹配按不区分大小写的子串 / 通配。**怎么拿标识**：先填 `*`（通配恒真）验证「设备上下文非空」；要精确区分时把 `VID_xxxx&PID_xxxx` 片段填进去（可在 `设备管理器` 里看硬件的硬件 ID，或在 `win.rs::note_raw_input` 里临时 `eprintln!("{name}")` 按一次键读出、验完删）。

**步骤**：

1. 配一条 `Ctrl+K`，触发条件「设备是」填 `*`（通配，恒真）→ 保存。
2. 在**键盘 A** 上按 `Ctrl+K` → 触发（用一个易观察的动作区分，如「打开网址」）。
3. 在**键盘 B** 上按 `Ctrl+K` → 同样触发（此时只证明「设备上下文非空」，不能证明区分成功）。
4. 条件改成只含**键盘 B** 的 `VID/PID` 片段 → 在 B 上按 → 触发；在 A 上按 → **不触发**（条件不成立、落空放行）。
5. 配第二条**同 `Ctrl+K`、条件只含键盘 A 片段**的条目 → 两条并存：A 上按走 A 条、B 上按走 B 条（同触发键按设备分流，冲突列表**不应**报「重复触发键」）。
6. **边界（一跳延迟）**：一只键盘打一会儿后换**另一只**敲第一个键——按文档口径，切换后第一个键可能归到旧设备；从第二个键起应稳定正确。

**预期**：设备上下文非空；同一 `Ctrl+K` 在两台键盘上各走各的条目；`when` 不同不算重复触发键。

**判失败**：

- 两台键盘上 `DeviceIs` 都不成立（恒走「否则」）→ Raw Input 旁路没起效：看终端有没有 `kada-hook: 注册键盘 Raw Input 失败` / `创建 Raw Input 窗口失败`（此时壳层如实把设备条件报「恒不成立」）。
- 切换键盘后**持续**归错设备（不止第一个键）→ 匹配 / 缓存逻辑有问题。
- 同 `Ctrl+K` 两条都填了设备条件却被报「硬冲突」→ `when` 没进判重指纹。

## 26. 快捷键录入鼠标侧键（组合键 / 序列 / 和弦） ⬜ **待真人复跑**（构建已过，真机鼠标没录过）

**要验的**：快捷键编辑器的三处录入（「录入组合键」「录入序列」「录入和弦」）能录到鼠标键——中键 `MouseMiddle`、侧键后退 `MouseBack`、侧键前进 `MouseForward`（规划 7.1-㊺，口径见 `需求设计说明书.md` §6.5）。左/右键**不录**（那是普通点击，不该当触发键）。

**前置**：主窗口左侧「快捷键」→ 打开一条条目，来到模式行的按键框（右侧三枚录入图标：键盘 / » / 四宫格）。用带中键与侧键的鼠标。

**步骤**：

1. **组合键**：点「录入组合键」（键盘图标）→ 按一下**鼠标侧键（后退）** → 触发键胶囊出现 `MouseBack`。
2. **带修饰组合**：再录一次，**按住 `Ctrl` 的同时按侧键** → 得到 `Ctrl+MouseBack`（修饰键前缀）。
3. **中键**：同样录一次中键 → `MouseMiddle`（录入时不应触发页面自动滚动）。
4. **序列**：点「录入序列」→ 按 `F9` 再按一下侧键 → 状态条显示 `F9 MouseBack`，回车提交（至少 2 步）。
5. **和弦**：点「录入和弦」→ 按住 `F9` 再按住侧键 → 状态条显示 `F9&MouseBack`，松开提交；只按一个鼠标键（无第二个成员）应视为取消。
6. **保存 → 真机触发**：保存后回主界面，在浏览器里按一下该侧键 / 组合键，看动作是否执行。
7. **边界**：录入时点左/右键**不应**被录成触发键；点「录入」按钮本身（左键）不应被当输入。

**判失败**：

- 按侧键毫无反应（`mousedown` 没监听到）→ 配置里已有鼠标键触发时，录入期间应已 `set_paused` 放行，检查暂停租约是否生效。
- 左/右键被录成了鼠标键（DOM `button` 号映射错：应为 1=中键、3=后退、4=前进）。
- 录入期间侧键把 WebView **导航走了**（触发后退/前进）而不是被录入。
- 带修饰的录入丢了 `Ctrl` 前缀。

**为什么只能人工**：低层钩子与 DOM 鼠标事件都不能用单测驱动，构建只证明类型与逻辑编译通过。

## 27. 文本动作「隐藏内容」开关（显示为 ***） ⬜ **待真人复跑**（构建 + 单测 + 浏览器演示模式已过，真机与落盘回显没跑）

**要验的**：`Action::Text` 的「输入文本」编辑框下面那枚「隐藏内容（显示为 ***）」开关——打开后编辑框位置换成一块 `***`（真文本不渲染、连长度都不露）、卡片头部摘要变 `输入文本：***`、执行记录里这一步的摘要也只写 `输入文本 ***`；**注入的内容一字不改**（口径见 `需求设计说明书.md` §3 / §5.4 / §6.5）。

**前置**：一条挂了「文本操作 → 输入文本」动作的快捷键（没有就新建一条，动作类型选「文本操作」、子类型保持「输入文本」，随便填一段文字）。多动作条目默认收起，先点圆点 / 手柄 / 图标展开卡片。

**步骤**：

1. **开关出现**：展开该动作卡片 → 编辑框（textarea）**下方**出现开关行「隐藏内容（显示为 ***）」，默认关。
2. **打开**：点亮开关 → 编辑框被一块 `***` 的框体顶掉（框体大小与编辑框一致，卡片高度不跳），开关保持点亮。
3. **摘要**：点圆点 / 手柄收起这张卡片 → 头部摘要显示 `输入文本：***`（同一张卡里别的动作照常显示自己的摘要）。
4. **落盘回显**：保存（Ctrl+S 或 ✓）→ 关闭编辑页 → 重新打开这条条目 → 展开该动作：开关仍是亮的、编辑框仍是 `***`（说明 `masked` 真进了 `config.json`；也可直接打开 `%APPDATA%\com.kada\config.json` 看 `"masked": true`）。
5. **取消隐藏不丢内容**：关掉开关 → 编辑框恢复，文字**原样**在（不是空的、也不是 `***`）。
6. **执行不改行为**：保持隐藏 → 在真实程序里触发这条快捷键 → 目标程序收到的必须是**原文**（不是 `***`）；同时「消息」页这条执行记录里，该步摘要是 `输入文本 ***`。
7. **老配置兼容**：手工把 `config.json` 里某条文本动作的 `masked` 键删掉 → 重载配置（托盘「重载配置」或重启）→ 条目不报错、按「不隐藏」显示，且再保存时不会多出 `"masked": false` 这种噪音键。

**判失败**：

- 勾上开关后编辑框还是显示原文（隐藏态没换掉 textarea，或摘要仍是原文）。
- 取消隐藏后编辑框空了 / 变成 `***`（真文本被占位符覆盖 = 数据被吃掉）。
- 重开条目开关又变回关闭（`masked` 没落盘 / 被清洗掉）。
- 触发后注入的是 `***`（把展示用的掩码当成内容注入了）。
- 「消息」页执行记录里能看到隐藏文本的原文（漏掩一处）。
- 删掉 `masked` 键的老配置打不开或报错（`#[serde(default)]` 没生效）。

**为什么只能人工**：真机点击、`config.json` 落盘后的重开回显、以及「触发时注入的确实是原文」这三件都发生在 Tauri 壳与系统输入层里；浏览器演示模式的 `set_config` 是空实现，落盘往返只有 Rust 单测覆盖（`text_action_masked_roundtrip` / `masked_text_action_hides_body_in_summary`）。

## 28. 命令 / 脚本动作「隐藏控制台窗口」开关 ⬜ **待真人复跑**（构建 + 单测已过，真机黑窗没看过）

**要验的**：「执行命令」「执行脚本」编辑器里的「隐藏控制台窗口」开关（`hide_window`，口径见 `需求设计说明书.md` §3 / §6.5）——勾上后触发命令 / 脚本时不再弹出黑色控制台窗口，且「弹窗显示结果」与存变量照常工作。

**前置**：两条快捷键，各挂一个「执行命令」（如 `ping -n 3 127.0.0.1`）与「执行脚本」动作（如一个 `python time.sleep(2)` 脚本），都勾上「隐藏控制台窗口」；命令可顺手开「弹窗显示结果」。

**步骤**：

1. **开关出现**：打开两个编辑器 → 「弹窗显示结果」**右边紧挨着**（同一行）一枚「隐藏控制台窗口」开关，默认关。
2. **不隐藏对照组**：开关关着触发 → 桌面闪出一个黑色控制台窗口（原有行为）。
3. **隐藏生效**：勾上保存后触发 → 黑窗**不**再出现；开了「弹窗显示结果」的照样弹结果、内容正常（输出捕获没被挡掉）。
4. **存变量照旧**：命令输出存变量（`var` 填名）→ 隐藏态下后续动作照样读到输出全文。
5. **落盘回显**：保存 → 重开条目 → 开关仍亮；`config.json` 里可见 `"hide_window": true`。
6. **老配置兼容**：手工删掉某条命令动作的 `hide_window` 键 → 重载 → 不报错、按「不隐藏」执行，再保存不多出 `"hide_window": false`。
7. **交互式命令例外**：隐藏态跑一个需要黑窗交互的命令（如 `choice`）→ 窗口不出现、命令等不到输入——这是预期取舍（纯后台命令才该开）。

**判失败**：

- 勾上后黑窗照样闪（`CREATE_NO_WINDOW` 没生效 / 参数没透传到 `run_cmd`）。
- 隐藏后「弹窗显示结果」弹出的内容空了（把窗口和管道一起砍了）。
- 重开条目开关变回关（没落盘）。
- 删键的老配置报错（`#[serde(default)]` 没生效）。

**为什么只能人工**：黑窗是 Windows 进程创建的可见副作用，单测只能验 `GetConsoleWindow` 判空（`hide_window_really_removes_the_console`），真机闪窗只能人眼看。

## 29. 操作系统动作「切换虚拟桌面」 ⬜ **待真人复跑**（构建 + 单测 + 浏览器演示模式已过，真机切桌面没跑）

**要验的**：**操作系统**动作（独立一类，`Action::System` / `SystemOperation::SwitchDesktop`——不再在文件/目录动作的下拉里，口径见 `需求设计说明书.md` §3 / §5.7 / §6.5）——触发后**真的切到相邻虚拟桌面**，且触发键上按住的修饰键不会污染注入的组合键。

**前置**：

1. 先建出**至少两个虚拟桌面**（Windows `Win+Ctrl+D` 新建一个，并在上面随便开一个窗口，好肉眼看出切没切）。
2. 一条快捷键，挂「操作系统 → 切换虚拟桌面」动作，方向先选「下一个（右）」；触发键选一个**带修饰键**的组合（如 `Ctrl+Alt+→`）——第 4 步要靠它。

**步骤**：

1. **类型与下拉出现**：新建动作 → 类型下拉里有独立的「操作系统」（图标 🖥️，与「文件/目录」并列）；选中后子操作下拉是「切换虚拟桌面」，卡片只显示一个「方向」下拉（上一个（左）/ 下一个（右），默认「下一个」）+ 一行平台键位说明，没有别的输入框；「文件/目录」的子操作下拉里**不再有**「切换虚拟桌面」。
2. **摘要**：收起卡片 → 头部摘要显示 `切换虚拟桌面：下一个`；把方向改成「上一个（左）」→ 摘要跟着变。
3. **真切桌面**：触发 → 桌面切到相邻那一个（Windows / macOS 是水平方向，Linux GNOME 是上下方向，见第 6 步）；方向改成「上一个（左）」再触发 → 切回来。
4. **修饰键不污染**：连着按触发键几次 → 每次都是干净地切一个桌面，不会变成 `Ctrl+Alt+Win+Ctrl+←` 那种混合组合（壳层靠 `injects_keys` 认出这个动作、先等物理修饰键松开，见 §5.7）。
5. **执行记录**：触发后去「消息」页看这次执行 → 该步摘要是 `切换到下一个虚拟桌面`，状态 `ok`。
6. **各平台键位对照**（按你在哪个系统上验）：
   - **Windows**：应等价于手按 `Win+Ctrl+→` / `Win+Ctrl+←`。
   - **macOS**：应等价于 `⌃→` / `⌃←`（Mission Control 的「向左/右移动一个空间」；系统设置里改过这两个快捷键的话本动作会失效——改用「按键组合」动作）。
   - **Linux（GNOME）**：应等价于 `Super+PageDown` / `Super+PageUp`；KDE / XFCE 默认键位不同，失效属预期（改用「按键组合」）。
7. **老配置兼容**：手工把 `config.json` 里该动作的 `"direction"` 键删掉（只留 `{"op":"switch_desktop"}`）→ 重载配置 → 不报错、按「下一个」执行。
8. **只有一个桌面时不炸**：删到只剩一个虚拟桌面 → 触发 → 无反应但**不报错**、执行记录仍是 `ok`（系统对「没有相邻桌面」就是什么都不做）。

**判失败**：

- 触发后桌面没动，但执行记录里这步是 `ok`（注入静默失效——组合键没到系统，或键位不对）。
- 桌面切了，但顺带触发了别的动作（注入组合键被触发键的修饰键污染，`injects_keys` 没认出这个动作）。
- 摘要写反（选「上一个」显示「下一个」）或换方向后摘要不更新。
- 删掉 `direction` 的老配置报错打不开（`#[serde(default)]` 没生效）。
- 子操作下拉里选了「切换虚拟桌面」后还要填路径（`newOsOp` 给错了默认形状）。

**为什么只能人工**：真正的效果（桌面切没切）由系统外壳决定，Rust 侧单测只能钉住「往哪个平台注入哪串键」这张映射表（`desktop_keys_follow_each_platforms_defaults`——CI 的 windows / ubuntu / macos 矩阵合起来覆盖三支）。「系统是否真响应注入键」「触发修饰键有没有污染」只能在真机上肉眼验。

## 30. 输入层环境诊断（厂商接管识别，7.1-㊽） ⬜ **待真人复跑**（构建 + 单测 + 探针真机识别已过，真机提示随接管软件退出而消失没跑）

**要验的**：`需求设计说明书.md` §4.6 的**档位 A**——探测有没有会 divert 按键的厂商软件在跑（Logi Options+ / G HUB / 雷云 / SteelSeries GG / iCUE，Linux 侧另有 `keyd` / `input-remapper`），在**配置用到鼠标键**时给一条能照做的提示，且这个提示**误报可关闭**、**不拖慢、不在没装这类软件的机器上出现**。本档**只报告不修**：它不改抓取、不改注入，也不解决 divert（那是 `docs/底层输入能力规划.md` 档位 C 的事）。

**前置**：

1. 一台**装了 Logi Options+（或任一目录里的接管软件）并让它运行**的机器——没装的话第 3~6 步验不成，可只跑第 1 / 7 / 8 步。
2. 配置里**至少一条快捷键或改键用到鼠标键**（中键 / 侧键，如`F1 → 粘滞 MouseBack`；没有就随手加一条）。第 4 步靠它。

**步骤**：

1. **先跑探针（不看界面，先确认探测本身对不对）**：`cargo run -p kada-hook --example input_env_probe` → 装了接管软件的机器上应列出它（如「检测到 1 个 / `logi-options-plus`（Logi Options+）」）；没装则应打印「接管者：未检测到」。再单独确认 HVCI 那一行与真实状态一致：`reg query "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity" /v Enabled`（键不存在 → 探针应报「读不到」，**不是**报成「已关闭」）。
2. **设置页卡片**：打开设置 → 「输入层环境」卡片在「键位层」与「提权窗口注入」之间 → 结论区文本与第 1 步一致；勾选框默认**勾上**；点「重新检测」文本不变（同一结论）。
3. **外观与文案**：命中项应显示**软件名 + 一句处置办法**（左侧有竖线标出），不是只有一句「可能有问题」；末尾一行是内存完整性状态，且**措辞是陈述、不是警告**（它不影响 Kada 现在的用户态钩子，见 §4.6）。
4. **冲突通道（只在配置用到鼠标键时出现）**：保持第 2 条前置（快捷键里带鼠标键）→ 「消息 → 冲突」页的「平台 / 环境限制」组里应出现一条：`检测到「Logi Options+」正在运行：它可能把鼠标侧键…`；快捷键列表顶部的冲突气泡计数同步（「M 条当前环境用不了」）。**把配置里那条鼠标键快捷方式删掉（或禁用）→ 这条提示应消失**，其余冲突不受影响。
5. **真机闭环**：**退出 Logi Options+**（托盘图标 → 退出）→ 设置页点「重新检测」→ 结论区应变成「未检测到会接管按键的厂商软件（已查 8 类）」；「消息 → 冲突」里那条也随之消失（探测结果有 3 秒缓存，最多等 3 秒或再点一次）。**重新启动 Options+** → 两处都恢复。
6. **接管时的真实行为**（回归观察，与 V0.85~V0.87 那轮同口径）：Options+ 运行中，MX Anywhere 3 的**侧键**无法触发 Kada；在 Options+ 里把该按键改成「无操作」→ 立刻能触发，**不用退出 Options+**。这条同时是「提示里那句处置办法确实管用」的证据。
7. **误报可关闭（整条链路静默）**：把设置页「识别厂商接管的按键」**取消勾选** → 结论区变「已关闭。开启后 Kada 才会检测…」，且「消息 → 冲突」里那条环境提示消失；重新勾上 → 都回来（不需要重启应用）。关掉期间**探测本身也不跑**（不要求肉眼可见，理解为「功能按开关语义完整关闭」）。
8. **不影响没装这类软件的机器**：在另一台（或临时把目录里所有接管软件都退出）→ 设置页结论区是「未检测到…（已查 8 类）」，「消息 → 冲突」里**一条环境提示都不出现**，冷启动与编辑配置的手感不变（探测带 3 秒缓存，不该有卡顿感）。
9. **平台口径（macOS，有机器才跑）**：设置页结论区应说「当前平台暂不支持这项检测（Windows / Linux 已支持）」——**不能说成「未检测到」**（那是「查过了很干净」的意思，与「这个平台没做」是两句话，见 §4.6）。
10. **老配置兼容**：手工把 `config.json` 的 `settings` 里 `input_env_diag` 删掉 → 重载配置 → 卡片开关仍显示**勾上**、提示照常出现（`#[serde(default)]` 取 true），不报错。
11. **按条忽略（只掐这一条）**：命中项右侧点「忽略」→ 该条变暗、竖线变虚线、按钮变「恢复提示」，**「消息 → 冲突」里只剩它那一条消失**（同一台机器上若还跑着别的接管者，别的那条仍报）；退出再进设置页、重启应用，忽略状态都还在（落盘在 `settings.input_env_ignored`）。点「恢复提示」→ 冲突里那条回来。**总开关关掉 → 整个结论区变「已关闭」（忽略列表不动，重新打开后仍记得）**；再把 `input_env_ignored` 手工从 `config.json` 删掉 → 重载后所有提示回来（`#[serde(default)]` 空表）。

**判失败**：

- 探针与设置页结论不一致（探测是真跑的，两处读同一份缓存，不一致说明有一处在别处另算了一遍）。
- 配置里**没有**任何鼠标键，却仍报环境提示（门控失效 = 误报，正是档位 A 声明要避免的东西）。
- 退出接管软件后提示不消失（说明结论被缓存住了或探测的是别的东西）。
- 关掉开关后提示仍在（开关只关了显示、没关探测）。
- HVCI 读不到却报「已关闭」（把 `None` 当 `false` 用）。
- 界面把 macOS 的能力缺口说成「未检测到」（把「没做」说成「没问题」）。
- 删掉 `input_env_diag` 的老配置报错打不开。
- 点「忽略」后**别的接管者**的提示也没了（粒度退化成总开关），或恢复后冲突里不回来。

**macOS 侧（探测已随 7.1-㊽ 余项补齐，libproc 进程表）**：有 Mac 时在装了 Logi Options+ 的机器上跑 `cargo run -p kada-hook --example input_env_probe`，应列出 `logi-options-plus`（`proc_pidpath` 拿得到路径基名）；设置页卡片应显示「检测到 / 未检测到」的真实结论——**不再出现「当前平台暂不支持这项检测」**。Options+ 的 macOS 代理进程名若与 Windows 版不同导致漏认，往 `kada_core::DIVERTERS` 补片段即可。

**为什么只能人工**：探测本身（`CreateToolhelp32Snapshot` / 注册表 / `/proc` / libproc）在每台机器上结果都不同，只能对着真实环境核对；而「退出厂商软件 → 提示消失」这条闭环要真的去操作厂商软件（自动化测试只能喂合成 `InputEnv`，证明不了探测在真机上认得出谁）。真实 divert 行为（第 6 步）更是设备固件与厂商代理的交互，任何单测都替代不了。

**探针备忘**：`input_env_probe` 是这条链路的核对入口——真机「到底认出了谁、有没有漏认」看它。漏认（装了却没认出）是**已知边界**：目录靠进程名片段匹配，改名 / 自研代理认不出来；补条目往 `kada_core::DIVERTERS` 加匹配片段（该结构体 `processes` 有说明）。

## 31. 提权窗口注入（提权伴随进程，7.1-㉑a） ⬜ **待真人复跑**（构建 + 单测 + 非提权探针全过，UAC 与真机注入没跑）

**要验的**：`需求设计说明书.md` §4.7——前台是**提权窗口**（如以管理员身份启动的记事本）时，Text / Keys / Mouse 动作经一个**按需拉起的提权进程**重放后能生效；**没打开开关时行为与现在完全一致**；关掉开关 / 退出 Kada 后提权进程**不留在系统里**。安全桌面的边界（UAC 授权框本身、锁屏、登录界面进不去）如实即可，不作为失败判据。

**前置**：

1. Windows 真机（这套东西是 Windows 专属，对手是 UIPI）。
2. 一个**提权窗口**：`Win` → 输入 `notepad` → 右键「以管理员身份运行」（或任意管理员启动的程序，需在窗口里能打字）。
3. 一条用到 **Text** 或 **Keys** 动作的快捷键（如 `Ctrl+Alt+T` → 输入文本 `hi`），并且**已在普通窗口里验过它能用**（先排除配置本身的问题）。
4. 一段管理员记事本里可点到的内容用于 Mouse 动作（可选，第 5 步第三小项）。

**步骤**：

1. **先跑探针（把不需要 UAC 的那一段自动验掉）**：`cargo run -p kada-hook --example elevated_probe` → 应依次打印一串 `✓`（开关没开不路由且不留提示 / 非提权对端被拒 / DACL 与双方身份校验通过 / 一批 op 往返 / 按键批次往返 / 坏 op 被整批拒 / 200 个 op 的大批次 / 客户端一断开代理就退出），末行提示「真提权那一段请人工验」。任何一行 panic 都是失败。
2. **卡片位置与未开启态**：设置 → 「提权窗口注入」卡片在「键位层」与「配置与数据」之间；结论区是「未启用。打开上面的开关后点「启动提权进程」」，右上按钮**置灰**并提示「先打开上面的开关」。
3. **不开开关 = 与现状完全一致**（回归红线）：以管理员身份启动记事本并让它在前台 → 按第 3 条前置里的快捷键 → **没有反应**（动作其实跑了，注入被 UIPI 拦掉，与之前一模一样）；此时「消息」页应多出一条标签「提权窗口注入」的提示，说清前台是提权窗口、去设置页打开开关要怎么点。**再连按几次不该刷屏**（「开关没开」这一类只报一次）。
4. **打开开关 + 启动提权进程（这里会弹 UAC）**：勾上细开关 → 结论区变「开关已打开，但提权进程没在运行——点右上角…」；点「启动提权进程」→ 界面就地显示「正在请求管理员授权（会弹 UAC…）…」→ 弹出 UAC 授权框 → 点「是」→ 约 1~2 秒内结论区变「已连接：提权进程在运行…」，按钮变「断开提权进程」。任务管理器「详细信息」里应多出一个 **kada.exe**（同一个可执行文件、同一用户名、**没有窗口**）。
5. **提权窗口里注入生效（本档的正题）**：前台保持管理员记事本 → ① 触发 Text 动作 → 文字出现在记事本里；② 触发 Keys 动作（如 `Keys: Ctrl+S`）→ 生效；③ Mouse 动作 → 光标移动 / 点击落在提权窗口上。三种都成功才算这条过。
6. **「转大小写」的边界（如实说那条）**：在管理员记事本里选中一段文字 → 触发「转大小写」动作 → **预期没有变化**（复制出来的剪贴板内容普通权限读得到，但贴回去时提权目标读不到普通权限进程写的剪贴板）。把设置页「文本注入」改成**逐字直发** → 再触发一次 → 这次应能变大小写。这是**已知边界**，不是失败（见 §4.7 边界那条）。
7. **失败可见（把提权进程干掉）**：任务管理器结束那个提权 kada.exe → 回管理员记事本按快捷键 → 这次注入没生效，且「消息」页应出现一条「提权通道出错」的提示（**60 秒冷却**：期间连按不刷屏）；重进设置页（或点「重新检测」那类刷新动作）→ 结论区应回到「开关已打开，但提权进程没在运行」，按钮回到「启动提权进程」。
8. **关开关 = 完全回到现状**：关掉细开关 → 提权进程**自行退出**（任务管理器里那个 kada.exe 消失，不必手动杀）；此时在管理员记事本里按快捷键仍是没反应（同第 3 步），且**不再报提示**（同一次运行里「开关没开」只报一次，属预期）。
9. **不留孤儿**：重新打开开关并点「启动提权进程」→ 从托盘**退出 Kada** → 提权进程应随之消失。再做一遍，这次用任务管理器**强杀** Kada（模拟崩溃）→ 提权进程同样应消失（父进程守望）。两遍都不该留下能在系统里往提权窗口注入的进程。
10. **代理模式是安静的**（可选，看它到底干了什么）：`taskkill /IM kada.exe /F` 后 `cargo build -p kada`，再开一个终端跑 `target\debug\kada.exe --kada-agent`（不带父进程 pid = 手工运行、不守望）→ 应**不出现任何窗口**、不新增托盘图标、不碰配置文件（`%APPDATA%\com.kada\config.json` 的修改时间不变），只在后台等客户端，`Ctrl+C` 即退出。**期间别在 Kada 里点「启动提权进程」**——通道名被它占着，新拉的提权进程会建不起通道（这正是 `FIRST_PIPE_INSTANCE` 的预期行为，只是看起来像启动失败）。
11. **老配置兼容**：手工把 `config.json` 的 `settings` 里 `elevated_inject` 删掉 → 重载配置 → 卡片开关显示**未勾选**（`#[serde(default)]` 取 false），不报错、不弹 UAC。

**判失败**：

- 打开开关、也连上了提权进程，Text / Keys 动作在提权窗口里**仍不生效**（本档的正题没做成）。
- **没打开开关时行为变了**（比如不注入、报错、变慢）——本档只增能力，关着时必须与现在一模一样。
- 该报提示时一声不响（用户看到的仍然只是「按了没反应」），或反过来连按刷屏不停。
- 关掉开关 / 退出 Kada / 强杀 Kada 之后，提权进程**还留在任务管理器里**（能往提权窗口注入的孤儿进程）。
- 点「启动提权进程」不弹 UAC 就说「已连接」（说明连上了一个不是提权运行的对端——客户端的提权校验失效）。
- UAC 里点了「否」之后界面卡住或崩掉（应显示「已取消提权（UAC 授权被拒绝）」这类错误串）。
- 手工跑 `--kada-agent` 时冒出窗口、托盘图标或改了配置文件。
- 删掉 `elevated_inject` 的老配置报错打不开，或开关默认变成勾上（**默认必须是关**）。

**为什么只能人工**：这套东西的核心是**两个不同完整性级别的进程**之间的约定——UAC 授权框只能人点（自动化点不了也不该点），「提权窗口里注入到底进没进去」只有在真的管理员窗口里打字才知道，而「进程会不会留下孤儿」要在任务管理器里看着它消失/残留。不需要 UAC 的那一段（管道 DACL、双向身份校验、行协议往返、分片、坏 op 整批拒、断开即退）**已由探针自动化覆盖**（`cargo run -p kada-hook --example elevated_probe`，本机全过），所以这里只列它盖不到的部分。

**探针备忘**：`elevated_probe` 是这条链路的核对入口——它在本进程里起一个「代理」（同一个 exe、非提权）来验协议与信任边界，所以**它连着的那一段不是真提权那段**；真提权那段（UAC + 往提权窗口注入）只能按上面第 4~9 步人工走。`verified` 与 `unverified` 的分界就在「对端是不是由 UAC 拉起来的提权进程」。

## 32. 动作分组与拖拽插入线 ⬜ **待真人复跑**（浏览器演示模式已验结构与几何，真实鼠标手感未验）

**要验的**：新增「＋ 添加分组」入口；分组的新建 / 命名 / 收起 / 删除；把动作拖进分组、从分组拖出；拖出条件判断 / 并行执行时插入线落在**两个动作之间**；把容器拖进自己的分支被拒绝。

**步骤**：

1. 新建一条快捷键，点动作页脚的「＋ 添加分组」：应出现一个展开的空分组卡片（▣、淡灰蓝虚线框），标题行可直接输入「分组名称」。
2. 给分组命名（如「收尾清理」）→ 点脊柱圆点收起：标题应显示「收尾清理 · 0 个动作」；再点展开。
3. 把上面已有的一个动作拖进分组：拖到空分组泳道上时整块泳道出现强调色描边，松手后动作出现在组内最后。
4. 把组内动作往外拖：指针移到分组卡片**上方的空隙**时，插入线应出现在「上一个动作卡片底边」与「分组卡片顶边」之间的正中间（不是压在任一卡片的上/下边缘上），松手后动作落在分组前面。
5. 展开一个条件判断 / 并行执行，把其中一条分支成员拖到容器的**头部或卡片外**：插入线同样应落在外层相邻两个动作之间，而不是容器卡片边缘。
6. 把分组（或条件判断 / 并行执行）拖到自己的分支泳道里：应显示红色禁止线 / 红色虚线框，松手后结构完全不变（不能把容器塞进自己肚子里）。
7. 保存后退出重进：分组与成员结构、名称应完整回显；触发这条快捷键，执行记录/流水线里分组作为一层容器、成员挂在它下面，执行顺序与摊平一致。

**判据（不通过的样子）**：

- 拖到两张卡片的缝隙里没有任何指示（旧实现的漏判），或指示线画在卡片内部、跟着卡片边缘走而不是待在空隙中央。
- 拖出分组 / if / 并行时线仍然贴在容器卡片的上下边缘。
- 分组拖进自己的分支后应用卡死、保存报错或配置变成循环结构。
- 分组重进后名称丢失 / 成员顺序被打乱 / 被当成并行执行。

**为什么只能人工**：插入线的位置、过渡动画与真实拖拽手感只能在壳内窗口用真鼠标感受；演示模式的几何位置已用合成 PointerEvent 量过（见 `docs/变更归档.md` V0.97），但 `pointerdown/move/up` 的时序与真实指针设备不同。

**步骤**：

1. 设置 → 外观与提示 → 界面主题 → 选「像素 CRT 深色」（首次安装 / 清掉 `localStorage` 时**默认已是这一档**）。应立刻切换：底色是简约深色那种黑灰（`#111318` / 面板 `#191d24`），文字近白、外圈有一层**能看出来的余晖**（近圈收边 + 远圈摊开，但笔画本身不能被糊粗），全站直角、卡片有 4px 无模糊硬影，左栏品牌字变为四色 Kada + 星芒；**扫描线只应出现在文字与图标上（4px 周期，每条为 1px 实亮 + 1px 约 2/3 强度余晖，呈明显的拉丝 / 拖影感），空背景几乎看不到横线**——普通字、灰字、主按钮里的纯白字都应能看到拉丝，不应只有部分文字有；能看到很轻的闪烁与自上而下扫过的亮带；**不应出现荧光绿**。**打包版（WebView2）与浏览器里的观感应基本一致，若打包版仍明显更淡，记一条失败。**
2. 再选「像素 CRT 浅色」：底色应变成浅色主题的白 / 浅灰（`#f2f3f5` / 面板 `#ffffff`），文字深灰、外圈同样有余晖（比深色档更收敛，不能把 12px 字糊成灰团），扫描线同样只落在深色文字与图标上（白面板与浅灰底不变），圆角 / 字体 / 扫描线结构保持不变；主按钮应是强调色实底白字，编辑页「保存」在无改动时仍是透明描边的置灰态（不能是实底色）。
3. 依次打开：快捷键列表 / 一条条目的详情与动作流程图 / 消息（执行记录 + 冲突）/ 设置（八张卡片）/ 帮助长文。**两档各看一遍**：12px 像素字是否清楚、笔画有没有被辉光糊粗，行是否被截断、列表与卡片是否横向溢出、滚动条是否可用。
4. 触发一条快捷键看右下角气泡；按住切层键看底部状态条；打开快捷键提示框。三者都应为当前 CRT 档的配色，**窗口透明边内不能出现实心矩形**；提示框的扫描线只在面板范围内。
5. 在四档之间来回切（像素 CRT 深色 → 像素 CRT 浅色 → 简约 深色 → 简约 浅色）：字体、圆角、投影、图标、品牌字应各自恢复 / 切换，不残留 `data-crt` 带来的浅色或深色残留（切回简约两档后不能还是像素字体或方角）。
6. 在 Windows 设置里开启「减少动态效果」（或关闭系统动画）后重启 Kada：主界面的闪烁与扫过的亮带应停止、字标星芒停止呼吸，只留静止的发光扫描线（两档都一样）。
7. 用鼠标正常操作：点导航、点列表行、输入、下拉、拖动动作卡片、滚动提示框，确认扫描线不挡点击（预期完全无感）。
8. 两档 CRT 下各打开一次**原生下拉**（设置页「界面主题」、动作卡片标题里的类型名、改键的原键下拉）：展开列表应是像素字体 + 方角 + 4px 无模糊硬影，面板上有极淡的每 4px 一条的横向扫描线，悬停项是强调色淡底；下拉打开时控件本身不应被选项配色反灌。切回简约两档后，展开列表应恢复系统原生样式（这套皮肤只在 CRT 两档生效）。

**判据（不通过的样子）**：

- 12px 像素字明显发糊、笔画被辉光加粗、行高挤压导致文字上下被切，或中文缺字回退成系统字体（尤其生僻字）。
- 两档里仍出现荧光绿 / 绿色底（类型色里语义性的绿除外），或浅色档不是白底、深色档不是简约深色那种黑灰。
- 主按钮不是强调色实底白字，或「保存」禁用态是实底色。
- 气泡 / 状态条 / 提示框出现实心深色矩形，或投影被窗口边裁出直边。
- 切回简约两档后仍残留方角、像素字体或扫描线；或在 CRT 两档之间切换时浅色 / 深色属性串档。
- 扫描线所在位置点不到按钮 / 行 / 输入框。
- 扫描线出现在空背景上（不发光的地方不该有扫描线），或文字 / 图标上反而看不到；闪烁与扫过的亮带完全看不到，或开启「减少动态效果」后仍有闪烁 / 亮带 / 星芒呼吸。

**为什么只能人工**：字体栅格化与扫描线密度是屏幕观感，浏览器运行时检查只能证明规则生效、证明不了「好看且可读」；浮窗在壳内是独立透明窗口，尺寸与投影裁切只有真机才能确认。

## 34. 罗技 HID++ 解锁侧键（档位 C，7.1-㊿） ⬜ **待真人复跑**（探针已在真机验到协议层：读到 `divert=true`、`--unlock` 后回读 `false` 且进程退出后保持；**应用内按钮、真按侧键、代理重启后的保持没跑**）

**要验的**：设置页「输入层环境」卡片里的「查看罗技设备 / 解锁侧键」两个按钮；解锁后**不退出 Options+** 也能用侧键触发 Kada 快捷键；Kada 退出后侧键仍是系统原生行为（证明没有接管事件流）；代理重启 / 设备重连后保持线程会把 divert 再关掉；通道打不开时界面给指引而不是假成功。规格见 `需求设计说明书.md` §4.8。

**前置**：Windows + 罗技鼠标（接收器或直连）+ Logi Options+ 在运行且侧键被它 divert（指纹：**中键能用、侧键不能用**）；配置里有一条用侧键作触发键的快捷键（如 `MouseBack`）。

**步骤**：

1. 退出正在运行的 Kada（两个实例会抢同一套全局钩子），再跑只读探针看基线：`cargo run -p kada-hook --example hidpp_probe`。应列出罗技设备，**中键 `divert=false`、两个侧键 `divert=true`**。
2. 启动应用（debug 版从终端启动才能看到 `eprintln!`），打开 设置 → 输入层环境，点「查看罗技设备」。应列出同一台设备与三个鼠标键的状态（两个侧键显示「被厂商软件接管」），而不是空白或报错。
3. 点「解锁侧键」。结论区应写「已解锁：后退侧键、前进侧键」+「本次运行期间会保持解锁」；消息中心应多一条「输入层 · 罗技 HID++」记录（不弹窗）。再点「查看罗技设备」，三个键都应显示「标准报文」，并出现「本次运行期间保持解锁中」。
4. **不退出 Options+**，按一下侧键：Kada 那条快捷键应触发（这是本项的核心，修的就是它）。同时在浏览器里按侧键，后退 / 前进仍应正常工作。
5. 重启 Options+（退出它再打开，或直接重启整台机器后重新点一次解锁）：等 15 秒左右点「查看罗技设备」，侧键应**又被关回标准报文**（保持线程在 10 秒巡检里发现代理反写并重关）；若代理没有反写，这一步也算通过（探针保持 `divert=false` 即可）。
6. 退出 Kada（托盘 → 退出），再跑探针：侧键仍应是 `divert=false`（关机重启后可能被代理设回，属正常）。此时按侧键，浏览器后退 / 前进照常——**不能出现「侧键彻底没反应」**（那说明我们接管了事件流或写坏了设备配置）。
7. 失败路径（可选）：把 Options+ 关掉后再点「解锁侧键」不应报错（通道仍可打开，键本来就没被 divert）；若机器上装的是独占控制接口的软件，应显示「解锁失败 + 去厂商软件让位」的指引，而不是「已解锁」。

**判据（不通过的样子）**：

- 点「解锁侧键」显示成功，但 Options+ 仍在跑时按侧键**不触发** Kada 快捷键。
- 解锁后「查看罗技设备」仍显示侧键「被厂商软件接管」。
- Kada 退出后侧键彻底没反应（原生后退 / 前进也没了）。
- 通道打不开 / 设备不应答却显示「已解锁」或「本来就不需要解锁」。
- 设置页出现「保持解锁」字样，但 15 秒后代理反写、侧键重新失效（保持线程没生效）。
- 中键或手势键的行为被改变（本项只许动中键 / 后退 / 前进三个键，且中键本来就该是标准报文）。

**为什么只能人工**：探针只能证明「协议写入生效、回读正确」，证明不了「真按物理侧键后 Windows 产生 XBUTTON、钩子收得到、快捷键触发」；代理重启 / 设备重连时的反写与竞态也只有真机能看到。

## 35. macOS 安全输入（Secure Input）提示（7.1-㊸） ⬜ **待验证（需要一台 Mac）**（Carbon FFI 已随 darwin 交叉检查编译通过；`IsSecureEventInputEnabled` 的真机行为、翻转提示没跑过）

**要验的**：`需求设计说明书.md` §4.3 那条——macOS 进入「安全输入」场景（快捷键全失效）时，Kada 在约 2 秒内给一条「系统『安全输入』已开启：快捷键此刻全部失效」的消息（不弹窗）；退出该场景后约 2 秒内再给一条「已关闭：快捷键恢复」；快捷键在两个状态下确实分别失效 / 恢复。开发机是 Windows，这条只能真机验。

**步骤**：

1. 真机跑 debug 版 Kada（能看 stderr），配置一条简单快捷键（如 `Ctrl+Alt+K` 弹气泡）。
2. 正常按快捷键应触发。
3. 制造「安全输入」场景：打开终端运行 `sudo -k` 后输密码（或打开系统「用户与群组」等需要鉴权的界面输密码）。输入密码的当下，消息中心应在约 2 秒内出现「已开启」一条；此时按快捷键应**不触发**（系统关掉了所有事件 tap）。
4. 退出密码场景（密码输完 / 取消鉴权）：约 2 秒内应出现「已关闭：快捷键恢复」一条，快捷键恢复触发。
5. 启动 Kada **之前**先进入一个持续的安全输入场景（如开着鉴权框）再启动 Kada：约 2 秒内应出现「已开启」（初始态按 false 起，第一拍就会报）。
6. 长时间停在安全输入场景内：不应重复刷「已开启」（只报翻转）。

**判据（不通过的样子）**：

- 进安全输入场景没有任何提示，快捷键失效像「Kada 坏了」（这条功能就没起作用）。
- 每 2 秒重复刷同一条提示（没按「只报翻转」）。
- 退出场景后「已关闭」不来，快捷键也不恢复（更严重：状态机卡死）。
- 消息弹了但快捷键在正常状态下也不触发（提示误报——`IsSecureEventInputEnabled` 被读错位）。

**为什么只能人工**：安全输入是系统全局状态，只在本机无 Mac 时无法构造；「输密码 → 提示 → 退出 → 恢复」的闭环要真人操作，darwin 交叉检查只能证明 FFI 签名与链接名编译通过。

## 36. Linux 热插拔（7.1-㉜） ⬜ **待验证（需要 Linux 真机）**（Linux 交叉检查 + 单测已过；真机拔插没跑）

- 拔掉设备后修饰键状态卡住（快捷键按「Ctrl 还按着」误判）。

**为什么只能人工**：需要真实热插拔与 `/dev/input` 权限；交叉检查只能证明代码编译得过，单测只能证明目录比对只认 `eventN`。

## 37. macOS 媒体键（7.1-㊹） ⬜ **待验证（需要一台 Mac）**（darwin 交叉检查 + `parse_media` 单测已过；真机触发 / 注入没跑）

**要验的**：`需求设计说明书.md` §4.3——播放 / 上一曲 / 下一曲 / 音量 / 静音能当触发键（快捷键、改键来源与目标、动作里的按键都算），绑了才吞、没绑原样放行（原生功能不受影响），自己注入的事件不回路。

**前置**：Mac 已按 §15 授好「辅助功能」权限；debug 版从终端启动（看 `eprintln!`）；配置四条：① `MediaPlayPause` 触发一个明显动作（如 `Action::Keys` 发 `F9`）；② 改键 `VolumeUp → VolumeDown`；③ 改键 `VolumeMute → A`；④ 动作 `Action::Keys` 里含 `MediaNext`。

**步骤**：

1. 按播放 / 暂停键：应触发你绑的动作，且**系统音乐不跟着暂停**（吞键生效）。
2. 按音量 +：音量应**减**一格（改键注入生效），不再增加。
3. 按静音：应打出一个 `A`，系统**不应静音**。
4. 触发配置 ④（用任意快捷键）：播放器应切到下一曲（注入生效），且**不回路**（不再触发 ④ 自己）。
5. 临时删掉播放键那条配置并保存：再按播放 / 暂停，音乐正常暂停 / 播放（未绑定原样放行）。
6. 长按音量 +：应连续加减（自动重复按 `data1` bit0 认，不能只动一格）。
7. 睡眠唤醒后重复第 1 步：媒体 tap 应跟着主 tap 一起恢复（看门狗重装）。

**判据（不通过的样子）**：

- 绑了媒体键但按下去毫无反应（tap 没建起来 / `data1` 解析错）；终端应有「媒体键 tap 创建失败」一行。
- 绑了媒体键，系统原生功能**也**发生（吞键没生效，返回了 event 而不是 null）。
- 注入的媒体键不生效，或生效后无限回路（注入识别没放行）。
- 未绑定的媒体键失灵（把不该吞的也吞了）。
- 长按只触发一次（自动重复位读错）。

**为什么只能人工**：媒体键是系统级 `NX_SYSDEFINED` 事件，Windows 开发机构造不出来；darwin 交叉检查只能证明 FFI 签名与 `parse_media` 编译 / 单测通过。

## 38. 看门狗半边失效：Raw Input 键盘旁路作第二观察者（7.1-㊵ 余项补齐） ⬜ **待真人复跑**（单测已过，真机半边失效没跑）

**要验的**：`需求设计说明书.md` §4.1 / `架构设计.md` §3.15——**鼠标持续移动**时，键盘钩子被摘也能被判出来并自愈（旧口径这一拍归因不出来）。旁路证据来自已有的键盘 Raw Input 消息窗口（设备识别那条），不是新装的东西。

**前置**：debug 版从终端启动（`eprintln!` 里能看到「看门狗重建输入钩子（…）」）；配置里至少一条鼠标键触发（鼠标钩子得装着，`config_uses_mouse`）；准备一个**短时间卡死钩子回调**的办法：临时把 `keyboard_proc` 入口塞一句 `std::thread::sleep(Duration::from_millis(600))` 重编（验完撤掉）——`LowLevelHooksTimeout` 默认 300ms，超时会被系统静默摘钩。

**步骤**：

1. 改完上面的 sleep 重编启动，**一边持续快速晃动鼠标、一边打几个字**：让键盘回调超时被摘、且此后系统最后输入一直是鼠标。
2. 观察终端：应在 1~2 秒内出现「看门狗重建输入钩子（**键盘钩子回调超时被系统摘除**）」。
3. 停止晃动鼠标、正常打字：快捷键 / 改键 / 热串全部照常（自愈完成）。
4. 反证「注入不喂活心跳」：只让看门狗对着**我们自己的注入**跑（如把钩子手动弄失效后用定时动作发按键）——旁路心跳不该被刷新，仍应判出失效（若判不出来，说明 `note_raw_input` 里那道 `hDevice` 判空被绕过了）。
5. 旁路缺席时的回落（可选）：临时让 `install_raw_input` 失败（改窗口类名 / 直接 return），重复第 1 步——**这一拍不该再判出**（老口径的残余，属预期，不是失败）。

**判失败**：

- 鼠标持续移动、键盘钩子确实被摘，但终端一声不吭 → 旁路心跳没写进 / 没参与判定（`LAST_RAW_KEY_TICK` 一直是 0 或判据没接上）。
- 没有失效却反复重装（打字时每 1~2 秒一次）→ 判据把正常时序当失效（旁路 vs 钩子心跳的先后搞反了，或注入事件在刷旁路心跳）。
- 自愈后快捷键双触发（钩子被处理两遍）→ 重装没先卸旧。

**为什么只能人工**：「回调超时被系统摘除」无法在测试里稳定构造（要真的让回调超时）；单测只覆盖纯函数判据（`watchdog_uses_raw_input_bypass_as_keyboard_observer`），「WM_INPUT 真的在物理按键时刷新、注入时不刷新」只有真机能证。

## 39. Kada' 鼠标手势试验台的真手势体验（`kada-prime/`，独立工具） ⬜ **待真人复跑**（单测已过，真手势未跑）

**要验的**：`docs/鼠标手势与滚轮快捷键规划.md` §4 / §14——「按住右键 → 画轨迹 → 命中执行 / 未命中回放右键」这条链**只做过代码级验证**（9 条单测 + 钩子安装成功），**真手势一次都没跑过**（开发时输入桌面处于 `Screen-saver`，`GetCursorPos` 返回拒绝访问，脚本合成事件进不来）。手感（起手距离、方向段长、8 方向认不认得顺手）只能真人试。

**前置**：

```powershell
cd kada-prime
cargo build --release
New-Item -ItemType Directory -Force dist
Copy-Item target\release\kada-prime.exe "dist\Kada Prime.exe" -Force
Start-Process "dist\Kada Prime.exe"
```

启动后：托盘出现图标、首次运行生成 `dist/config.json`（8 条默认手势）与 `dist/kada-prime.log`。**左键或右键单击托盘图标**开菜单（右键会被手势钩子吞掉再回放，左键更稳）。

**步骤**（每条做完在 `dist/kada-prime.log` 里能对上对应行）：

1. **命中**：按住右键画 `↓` 再 `→`（约 60~100 px 即可）→ 应触发「复制」（Ctrl+C）。轨迹层应显示橙色折线与方向串，抬起后显示「复制 DL」。
2. **未命中回放**：按住右键画一个**没配过**的方向（例如 `→` 再 `↓`，即 `RD`）→ 应看到「未配置：RD」，**并且右键菜单照常弹出**（这是与 MouseInc 相反的一条：MouseInc 默认什么都不做）。
3. **右键单击**：原地点一下右键（不动）→ 右键菜单正常弹出，延迟应在 30 ms 内（肉眼几乎无感）。
4. **单击延迟**：连续快速右击 20 次，菜单每次都要出、不卡、不吞。
5. **滚轮切换**：按住右键不放，滚轮上/下 → 触发 `Ctrl+Tab` / `Ctrl+Shift+Tab`（切标签页）；滚完松右键**不应**弹出右键菜单（滚轮被手势消费掉了）。
6. **边缘滚轮**：鼠标贴到屏幕左边缘滚动 → 触发音量 +/−（托盘可关）。
7. **触发角**（默认关，需在托盘里开）：光标移到屏幕左上角 → 弹「左上角」气泡；离开再进 → 再弹一次。
8. **轨迹层不抢前台**：画手势的全过程中，**当前窗口焦点不能变**、不能弹出 Kada 自己的窗口；轨迹线不应遮住点击目标（能穿透）。
9. **配置热加载**：托盘「编辑配置」→ 记事本里把 `settings.start_distance` 改成 `50`、把某条 `pattern` 改掉 → 保存 → 托盘「重新加载配置」→ 新参数立即生效（画短一点应该不再触发）。
10. **开关**：托盘关掉「启用手势」→ 右键行为完全回到系统（不吞、不回放）；重新打开 → 恢复。
11. **退出**：托盘「退出 Kada'」→ 进程结束、`dist/kada-prime.log` 末尾出现「=== Kada' 退出 ===」；再启动时托盘图标正常回来。

**判失败**：

- 画手势时**右键菜单还是弹出来了**（说明右键按下没被吞，或吞了但抬起没吞）→ 吞键配对断了。
- 未命中时**右键菜单不弹**（吞了没回放）→ 回放路径断了，这是最严重的一条（用户右键彻底失灵）。
- 轨迹层出现后**抢走了前台**（当前窗口失焦）→ 浮窗没设 `WS_EX_NOACTIVATE`。
- 命中的是**另一个手势**（方向串认偏）→ 方向量化 / 段长阈值要调（`settings.min_segment`、`start_distance`）。
- 手势执行后**右键一直处于按下状态**（后续左键点击变成右键拖拽）→ 按下-抬起配对漏了。
- 画手势时明显卡顿（输入延迟变高）→ 钩子回调里做了耗时操作。

**为什么只能人工**：整条链依赖**真实鼠标输入**（合成事件带 `LLMHF_INJECTED` 会被自己的钩子放行，除非用 `KADA_PRIME_SELFTEST=1` 的自测开关，但那条也只覆盖识别，不覆盖回放与浮层）。

## 40. 鼠标手势 V1（Windows）+ 新功能总闸（7.1-MG） ⬜ **待真人复跑**（单测 + 构建已过；2026-10-21 首次真机尝试暴露「采集出口被取走」故障，已修，见 V1.29，真手势仍未复跑）

**要验的**：`需求设计说明书.md` §5.9 —— 按住右键画轨迹 → 方向串匹配 → 执行动作；**没命中要把右键补回来**；设置页「实验功能」的总闸关掉后新功能一律不可用（入口隐藏 + 行为不生效，配置保留）。

1. **命中**：按住右键向下画一段（≥ 起手距离 22px）再松手 → 应触发「复制」（Ctrl+C），右下角出触发气泡（气泡上写「手势 D」），「消息」页的执行记录里有一条 `trigger = 手势 D`。

4. **没配动作**：把那条 `D` 手势的动作改成「不执行」→ 再画 `D` → **不执行任何动作、且右键菜单照常弹出**（半条配置不能把右键吞掉）。
5. **总闸关掉**：设置页「实验功能」→ 关掉「新功能总开关」→ ① 「快捷键」页里**「鼠标操作」那一类整个消失**（列表里的行、模式菜单里的项、「＋ 新增」里的入口都没有了）；② 右键行为**完全回到系统**（单击立即弹菜单、无任何延迟、不触发任何动作）；③ 重新打开 → 「鼠标操作」那一类回来、行为恢复（**配置没丢**）。

9. **与鼠标录制的关系**：开着手势时在「鼠标操作录制」里点右键 → **录不到右键**（右键归手势，属已知取舍，不是故障）。

- 画手势时**右键菜单还是弹出来**（菜单在画的过程中就弹了）→ 右键按下没被吞住。

**步骤**：

1. **语言切换**：设置页「外观与提示」→「界面语言」→ **English** → 整页 reload；静态文案（导航 / 卡片标题 / 按钮）与动态文案（列表行、编辑页页签、气泡、执行记录里的前端摘要）都应变成英文，**不夹中文**。切回「中文」→ 全部回中文；选「跟随系统」→ 英文系统显示英文、中文系统显示中文。

- English 下刷新后**又变回中文**（语言没写进 `localStorage`，或 `localizeStaticDom` 太早跑）。

## 42. 滚轮快捷键（`WheelUp`/`WheelDown`，7.2-MG 余项①） ⬜ **待真人复跑**（单测 + 构建已过；真机滚轮没跑）

**要验的**：`需求设计说明书.md` §5.10 —— 滚轮当离散键：一格 = 一次按下+抬起；绑了才接管，没绑滚动行为完全不变；高精度滚轮累积到 120 才算一格。

**前置**：Windows 真机；一条普通鼠标（再准备触控板或高精度滚轮鼠标更好）。

**步骤**：

1. **没绑时不变**：配置里没有任何 `WheelUp`/`WheelDown` 触发 → 在网页 / 资源管理器里滚动 → 与平时完全一样（不该有任何延迟或丢格）。
2. **绑滚轮触发**：新增快捷键 → 录入组合键 → **向上滚一格** → 触发区应填 `WheelUp`（向下则是 `WheelDown`）；动作设「按键组合 `Ctrl+C`」并保存。
3. **命中即吞**：在任意程序里向上滚一格 → 执行动作；**页面 / 列表不应跟着滚动**（这一格被吞掉，属预期）。
4. **条件 / 层不成立照常滚**：给该快捷键加 `when`（前台应用 = `notepad`）→ 在别的程序里向上滚 → 不执行动作、页面照常滚动。
5. **带修饰**：绑 `Ctrl+WheelUp` → 按住 Ctrl 滚一格触发；不按 Ctrl 滚时页面照常走（不误触发）。
6. **高精度滚轮 / 触控板**：用触控板或高精度滚轮连续慢滚 → 绑定动作**不是每一丝滚动都触发**，而是在累积约 120（一格）时触发一次；中途反向滚不应把两个方向的残余凑成一格。
7. **改键到滚轮**：新增改键 `F1 → WheelDown` → 在记事本里按 F1 → 文本向下滚一格（`WheelDown` 的按下滚、抬起不滚，不能滚两格）。
8. **序列**：录入序列 `WheelUp` + `A` → 先向上滚一格再按 A 能触发；只滚不按 A 等超时后，滚轮本身照常滚（被吞的一格不补——滚轮没有「补回」语义，属已知边界）。
9. **总闸 / 暂停**：应用暂停（`settings.paused`）或总闸关着时绑定的滚轮快捷键不触发（行为与键盘快捷键一致）。
10. **自动化**：`cargo test --workspace` 全绿（含 `wheel_is_a_mouse_trigger_but_only_when_bound` / `wheel_keys_scroll_one_notch_each`）。

**判失败**：

- 没绑滚轮时滚动**变慢 / 丢格 / 触发别的动作** → `set_wheel_enabled` 没推、或钩子层无条件处理。
- 绑了之后**页面还在滚** → 这一格没被吞（`Action::Block` 没生效）。
- 绑了之后**所有滚动都不能用**（不管方向 / 前台）→ 闸门没按配置走，吞得太宽。
- 触控板**每一丝滚动都触发一次** → 120 累积没做或阈值不对。
- 改键到滚轮**一次滚两格** → 抬起也被当成滚动（`send_key` 的 up 分支没排除）。
- 向上滚录成 `WheelDown`（或反之）→ `deltaY` 符号方向判反。

**为什么只能人工**：滚轮事件只能在真实输入设备上产生（合成事件的 `LLMHF_INJECTED` 被放行），且「吞掉一格 vs 页面照常滚」的观感只能肉眼确认。

## 附. 更新端到端（发版时才做） ⬜ 未验证



这条不属于上面那批可靠性改动，但同样是「只有真人能确认」的验收项，一并记在这里：客户端更新链路（启动静默检查 / 手动检查 / 下载安装 / 签名校验）。

**状态（2026-10-21 更正）**：**发布链路已端到端跑通两轮**——`v1.0.0` 与 `v1.1.0` 均于 2026-10-18 由 CI 构建并 Publish，Assets 齐全（Windows `x64-setup.exe` + `x64-portable.zip` / `x64-portable.exe`、Linux `amd64.deb` + `amd64.AppImage`、macOS `universal.dmg`、`latest.json`、各平台 `.sig`）。**仍未验的是客户端侧**：启动静默检查 / 手动下载与安装 / 自动更新空闲安装 / 便携版原位替换（§附.2 第 3~10 步），以及 Linux 真机装包（§附.3）、macOS 签名 + 公证。**自动化能覆盖的那一半已补**：`scripts/verify-release.mjs` 会核对版本号 / 签名 key id / 签名里的版本号 / 更新清单与产物的一致性（`node scripts/verify-release.mjs` 本地可跑），并抓到过一次「老 CLI 打出的签名没有版本号、客户端会全部拒装」的静默故障。下面这些是它管不到、必须真人做的。

### 附.1 产物自检（发版前后各跑一次，两分钟）

1. 在仓库根跑 `node scripts/verify-release.mjs`（打完包才有产物可查）。
   - 预期：打印每个安装包一行 `✓`，末行 `发布产物一致性校验通过。`。
   - 判失败：任何 `✗`。最常见的两条是「签名 key id ≠ 内嵌公钥」（私钥换了 / 公钥没同步进 `tauri.conf.json`）与「trusted comment 里没有 version: 字段」（Tauri CLI 太老）。
2. 动过 Tauri CLI 版本、版本号、或改了打包 targets 之后，**必须重跑一次**——这条不变量平时没人替你盯着。

### 附.2 真机发一次 Release 并验收（Windows）

发版步骤（打 tag、Secrets、draft 发布、`requireSignedVersion`）见 `.github/workflows/release.yml` 顶部注释，这里只写**验收判据**：

1. 发一个 `v1.0.0`（tag 推上去后由 CI 构建、签名、生成 `latest.json`、产出 **draft** Release；流水线三个平台的 job 串行跑完），确认三个 job 的最后一步（Verify release artifacts）都是绿的再 **Publish**（`releases/latest` 只解析已发布的 Release）。
2. Publish 后确认 ihomy 镜像已同步：`curl -s https://ihomy.top/files/kada/updates/latest.json` 应返回 `"version": "1.0.0"`，且各平台 `url` 都指向 `ihomy.top/files/kada/updates/...`。没同步就 `sudo -u ihomy /usr/local/bin/kada-mirror` 手动跑一次（见 `scripts/ihomy-mirror/README.md`）；**镜像没就位之前，默认源的新客户端会检查失败**。
3. 在装着旧版（0.1.0）的机器上启动 Kada，**等 8 秒**（启动检查是延迟 8 秒 + 只在发现新版本时弹一次气泡）；设置页确认「更新源」是「ihomy 镜像（默认）」。
4. 托盘右键 →「检查更新」（或设置页按钮）：发现新版本时先问「现在下载吗？」（**下载与安装是两步**），点「下载」后状态走 `downloading`（带百分比）→ `ready`；设置页此时**只出现「安装」按钮**（`available` 时只出现「下载」）。点「安装」→ 应用退出、安装器静默装完自动重启（`installMode: quiet` = `/S /R`，**没有进度窗**，属预期）。
5. 安装后确认版本号已变（「安装」在 Windows 上会**退出应用**并自动拉起新版，属预期）。
6. 便携版：下载 `Kada_1.0.0_x64-portable.zip` 解压直接跑 `kada.exe`，能起窗口、托盘常驻、配置还是原来那份（配置在 `%APPDATA%\com.kada\`，与 exe 位置无关）。**形态不交叉**（§5.5）：便携版读清单的 `windows-x86_64-portable` 条目（`Kada_1.0.0_x64-portable.exe`，带 `.sig`），设置页「安装」做的是**原位替换**——程序目录出现 `kada.exe.old-1.0.0`、新 exe 就位、进程按原参数重启（残留旧文件下次启动自动清），且 `%LOCALAPPDATA%\Kada` **不应**多出安装版。反向确认：安装版（`%LOCALAPPDATA%\Kada\kada.exe`）仍走 NSIS 装回原目录。
7. **自动更新（勾选）**：设置页勾「自动更新」→ 发现新版本即自动下载（不必点按钮；勾选时若已发现版本也会立刻开下）。安装时机：**空闲 10 分钟**（`kada_hook::idle_seconds()` ≥ `AUTO_INSTALL_IDLE_SECS`）自动装；免安装版另在**应用下次启动约 30 秒后**装。验空闲最省事是勾上后离开键鼠 10 分钟（或临时把 `AUTO_INSTALL_IDLE_SECS` 改小重编，验完改回）；验启动则是便携版下载完直接重启应用，30 秒内应看到自动替换 + 重启。
8. **不勾自动更新**：只有手动两步（`available` 时「下载」、`ready` 时「安装」）；下载完重启应用，「安装」按钮应仍在（`pending.json` 恢复，不丢下载结果）。改动设置里的「自动更新」只看配置，不影响已有的 `ready`。
9. **形态不匹配的包会被丢弃**：把 `%APPDATA%\com.kada\updates\pending.json` 里的 `kind` 改成另一种形态后重启，状态应回到 `idle`（不安装、不崩），下次检查重新走。已知边界：Linux 的 `idle_seconds()` 恒 `None`，**自动安装不会触发**（只能手动）；macOS 用 `CGEventSourceSecondsSinceLastEventType`，能自动。
10. 换源：设置页切到「GitHub Releases」→「检查更新」，能直连 GitHub 的机器上应同样发现新版本；切回 ihomy 后**下一次检查立即按新源走**（后端每次检查重读设置，不需要重启）。每日复查（启动后每 24 小时一次）只能挂机观察，或把系统时间往后调一天看托盘是否弹「发现新版本」。
11. 反向用例：若客户端**拒绝安装**，优先怀疑三处——① 内嵌公钥与签名私钥不匹配（客户端拿内嵌公钥验安装包签名，验不过直接拒装，是设计使然）；② 签名里没有版本号（`MissingSignedVersion`，见 §附.1 第 1 步；便携更新包靠 `tauri signer sign --app-version` 写入）；③ 签名版本与清单版本对不上（`SignedVersionMismatch`，多半是三处版本号只改了两处）。

### 附.3 Linux 装包与更新（需要一台 Linux，本机验不到）

1. 装 deb：`sudo apt install ./kada_1.0.0_amd64.deb`；装完按 `需求设计说明书.md` §4.2 配 `input` 组与 udev 规则（装包**不会**自动给钩子权限）。
2. AppImage：`chmod +x` 后直接跑；需要 FUSE 时装 `libfuse2` 或用 AppImageLauncher。
3. 更新：应用内「检查更新」默认读 ihomy 镜像的 `latest.json`（需先在设置页确认更新源是「ihomy 镜像」），应能看到新版本，下载后**弹管理员密码**（deb 走 `pkexec`），装完应用**自己重启**（这条 2026-10-10 才补上——以前装完仍跑旧二进制）。
4. 判失败：更新后版本没变 → 多半是重启那条没生效（`app.restart()`）；列表里根本没有这个平台 → 看 `latest.json` 里有没有 `linux-x86_64` 条目（流水线那个 Ubuntu job 可能没跑成）。

### 附.4 macOS 包（本机没有 Mac，只能靠 CI 出）

macOS 的 `.app` / `.dmg` **不可能在 Windows 上产出**：链接要 macOS SDK 与 `ld`（`cargo check --target aarch64-apple-darwin` 能过是因为 check 不链接），Tauri 的 `.app` / `.dmg` 打包也只有 macOS 上那份 CLI 会做。所以这一平台在 `release.yml` 的矩阵里（`macos-latest` + `--target universal-apple-darwin --bundles dmg`），**产物只能从 CI 拿**。

1. 出一份包：推一个 `v*` tag（或手动触发 Release 流水线），等 macOS 那个 job 跑完，从 draft Release 的 Assets 取 `Kada_<版本>_universal.dmg`。
2. 装：拖进「应用程序」。
3. **首次打开会被 Gatekeeper 拦**（本项目没有 Apple 开发者证书，产物未签名 / 未公证）：右键「打开」→ 再次确认，或 `xattr -dr com.apple.quarantine /Applications/Kada.app`。
4. 用：第一次进要按 §15 授「辅助功能」权限（输入层才起得来）。
5. 判失败：应用起来但按键完全没反应 → 权限没授（消息中心会有指引）；`.dmg` 打不开 / 拖不进 → 下载损坏，重下一次看 md5。

## 目前做不到的验证（不必尝试）

- **「回调超时被系统摘除」**：需要钩子回调真的卡住超过 `LowLevelHooksTimeout`（约 300ms）才会被系统摘掉，人为触发不了。这条路径的判据（心跳停摆）由单测 `watchdog_spots_hook_that_stopped_receiving_events` 覆盖，重装动作由冒烟测试走 `request_reinstall()` 走同一条代码路径。
- **macOS 全链路**：开发机是 Windows，对 macOS 只能做类型级验证（`cargo check --target aarch64-apple-darwin`，且只覆盖 `kada-hook` / `kada-core` / `kada-actions`；Tauri 壳因 `ring` 要真 clang 而无法交叉检查）。链接期符号、运行时权限、真实系统行为（注入识别、AX 查询、唤醒自愈）都只能靠真机或 CI 的 macos job——见 §15。
- **Linux 侧杀进程树（真机手动）**：本机是 Windows，§6 那套手动流程是 Windows 形态（`cmd /C` → `powershell` 孙进程）。Linux / macOS 侧已随 7.1-㊴ 落地（spawn 时 `process_group(0)` + `kill(-pgid)`），由单测 `timeout_kills_whole_process_tree` 的 unix 分支覆盖——断言**孙进程**建不出标记文件（该形状只有真的杀到组才会过），CI 的 ubuntu / macos job 每次都跑；本机想复跑可开个 Linux 容器（如 `rust:latest`）里 `cargo test -p kada-actions`。真机手动仅在有 Linux 机器时补做。
- **「键盘钩子单独被摘、鼠标钩子还活着」在旁路缺席时**：Raw Input 键盘旁路在时已能判（§38）；建窗 / 注册失败时回落到 `GetLastInputInfo` 的归因口径，鼠标持续移动那一拍探不到——这是**旁路缺席时的**残余，不是普遍天花板。

# 底层输入能力 · 分档规划（提权伴随进程 / HID++ 解锁 / 内核驱动取舍）

> **结论先行**：三平台现在站的层不一样——**Linux 已经在最底层**（evdev + `EVIOCGRAB` 抓取 + uinput 虚拟设备注入），Windows / macOS 还在用户态钩子层。而「再往下走」的真实缺口只有两个：**厂商软件把按键 divert 走**（本机实证：Logi Options+ 拿走了 MX Anywhere 3 的侧键，退出即恢复触发）与**往提权窗口注入**（UIPI）。这两件事**都不需要内核驱动**：前者唯一的路是自己当 HID++ 客户端（纯用户态、零签名成本），后者是「可选的高权限伴随进程」。内核过滤驱动 / 虚拟 HID 设备（对应 7.2-㉑）的收益（游戏原始输入、安全桌面的一部分）不在当前痛点上，代价却是签发常态化 + 内核责任 + 杀软观感 + CI / 发布流程重构，**建议评估后不做、留门**。总原则：**深档位一律可选、可退化——只增加能力，永不做必需依赖**。
>
> 状态：规划完成（2026-10-16），**未实现**。本文只回答「怎么在保住轻盈的前提下尽量往下走」，不含产品代码改动。

## 1. 诉求与边界

- **诉求**：不牺牲「轻快」定位与现有功能的前提下，尽量把输入层做得更靠下。
- **轻盈五条不变量**（任何深档位都必须满足；实现时同步写进 `人工验证清单.md` 的验收口径）：
  1. **只增能力，不做依赖**：没装 / 被策略禁 / 启动失败三种情况下，功能必须退化成当前版本（用户态钩子），而不是变慢、按键变哑或崩——与「吞键铁律」同级。
  2. **默认体积与常驻不增**：深档位是可选组件，主程序不打包；不新增常驻线程。
  3. **不进启动路径**：所有探测（驱动组件在不在、HID++ 通道能不能开）懒执行 + 带超时，不许破坏「冷启动零 WebView」。
  4. **事件驱动而非轮询**：设备变化走 `WM_DEVICECHANGE` / `RegisterDeviceNotification`，不新起看门狗线程。
  5. **失败可见**：一律「维持现状 + 消息中心一条提示」，不许静默。
- **边界**：不碰反作弊对抗；不为单家厂商设备改核心模型（`Key` / `Trigger` 不动，见 `docs/触摸板手势可行性调研.md` §3 的同类结论）；签名驱动不做默认分发。

## 2. 现状：三平台各站在哪一层

| 平台 | 抓取层 | 注入层 | 这一层看不到什么 |
|------|--------|--------|------------------|
| Windows | `WH_KEYBOARD_LL` + `WH_MOUSE_LL`（用户会话、非提权进程；鼠标钩子按需挂：`config_uses_mouse` → `set_mouse_enabled`） | `SendInput`（`simulate`） | 安全桌面（UAC 提示、锁屏、登录）；提权窗口（UIPI 挡注入）；win32k / shell 保留的组合键；被设备固件 divert 的按键 |
| macOS | 会话级 `CGEventTap` | `CGEventPost` | 提权进程；安全输入（Secure Input——终端里输密码时系统关掉所有事件 tap） |
| Linux | **已在最底层**：evdev + `EVIOCGRAB` 独占抓取（键盘与真鼠标） | uinput 虚拟设备（系统眼里是一台真键盘 / 鼠标） | 触摸板 / 指点杆（有意不抓，见 §4.2）、热插拔（需重启应用） |

- 补一条容易误解的：**`Raw Input`（`WM_INPUT`）不是「更底层」而是「更晚」**——它只能观察不能拦，而且被低层钩子吞掉的键它同样看不到。Kada 只用它做设备识别（7.1-㊷）。
- 「Linux 已经在最底层」这件事反过来解释了为什么 Windows / macOS 的限制在 Linux 上不存在：提权窗口、游戏原始输入在 Linux 都照常（注入出去的是真实虚拟设备事件）。

## 3. 两个真实缺口（决定该不该再往下）

### 3.1 厂商软件把按键 divert 走

- **机制**：罗技这类设备支持把某个按键**转交（divert）**给代理——代理经 HID++ 设置后，设备固件不再把该按键放进标准 HID 报文，改用 HID++ 通知只发给代理。Windows 输入栈里从来没有这次按下，**低层钩子拿不到，内核过滤驱动同样拿不到**（事件在到达系统之前就不存在了）。
- **本机实证（2026-10-16）**：Logi Options+ 运行中，MX Anywhere 3 的侧键无法触发 Kada 快捷键，浏览器后退 / 前进照常（那是代理自己执行的）；**退出 Options+ 后立即恢复触发**。旁证：接收器 HID++ 缓存里有 `0x1B04`（`REPROG_CONTROLS_V4`，可编程控件 / divert 特性）的查询并且设备回了索引；代理的指派表里侧键是它自己的系统动作（`WIN_BACK` / `WIN_FORWARD`），而**中键是直通**（`{"mouse":{"action":"BUTTON","hidUsage":3}}`）——「中键能用、侧键不能用」是这类接管的指纹。
- **Kada 侧同时已验通，排除自身 bug**：配置确实存进了触发键（`MouseForward`，启用中）；匹配逻辑对裸鼠标键必命中（`matches` 的 mods 空集恒为超集）；按需挂钩子实测会真的重装（诊断探针跑 `set_mouse_enabled(false→true→false→true)`，`reinstall_count` 递增）。
- **处置**：只有两条路——自己当 HID++ 客户端把 divert 关掉（档位 C），或让用户在厂商软件里让位（档位 A 给出指引）。

### 3.2 往提权窗口注入（UIPI）

- 这**不是抓取层问题**：钩子看得见按键，但注入进不去提权窗口。处置见档位 B。

**结论**：内核驱动能补的两类收益（游戏原始输入、安全桌面的一部分）都不在这两条缺口里。所以「尽量在底层」的正确解是分档补齐这两件事，而不是往内核钻。

## 4. 四个档位

### 档位 A：环境诊断与能力口径（零底层改动）

- **做什么**：识别已知的接管者（进程名 / 注册表里的 Logi Options+、G HUB、Razer Synapse 等）与内存完整性（HVCI）状态，接到现有 `platform_caps()` / `get_conflicts` 第④段那套「平台能力缺失 = 软冲突、不拦保存」的口径上，在快捷键页 / 帮助页给出**能照做**的指引。
- **为什么先做**：这类「按了没反应」的问题里，这是唯一能做且立刻见效的事；同时它是 B / C 的入口（用户得先知道发生了什么事）。
- **成本**：低（读进程名 / 注册表 + 一段文案）。风险：误报，需可关闭。

### 档位 B：提权伴随进程（Windows；补 UIPI）

- **做什么**：一个**可选、按需启动**的提权辅助进程，只负责**注入**（Text / Keys / Mouse），抓取仍在现有用户态钩子；IPC 走命名管道；设置里一个开关（「提权窗口也生效」），首次一次 UAC 拉起，平时不运行。
- **边界（界面必须说清）**：安全桌面（UAC 提示、锁屏、登录界面）仍然看不到也注入不进去——本档只补「提权窗口里的注入」。
- **为什么不是内核**：签署与分发成本为零（安装包本来就要 UAC），失败退化为现状，符合第 1 条不变量。
- **待定**：每次 UAC 拉起 vs Windows 服务 / 计划任务（后两者免每次弹窗但更重、卸载残留风险高）。

### 档位 C：HID++ 解锁侧键（Windows 专属、按需）

- **做什么**：**只调 `setCidReporting(cid, divert=false)` 把按键交回标准 HID 报文**，让现成的钩子链直接看见它。**不接管事件流**——这是本档最关键的取舍：延迟与现在完全一致，Kada 退出也不影响按键（接管式的做法会多绕一圈、还得处理退出复位）。
- **触发时机**：配置里用到了鼠标键 + 检测到罗技代理 + 设备支持 `REPROG_CONTROLS_V4` 时才提示并给「一键解锁」；设备重连或代理重启后 divert 会被设回，需事件驱动重试。
- **参照实现**：Linux 上的 logiops / Solaar 就是用户态 HID++ 客户端（含控件表），规模可估。
- **风险**：控件通道可能被代理独占打开（打不开就退化为档位 A 的指引）；控件 ID 按型号不同，要维护一张表；只覆盖罗技自家设备。
- **通道实测（2026-10-16，logioptionsplus_agent 运行中）**：接收器 `MI_02` 的三个 HID collection，**独占打开失败（WinError 32 = 代理占着）但共享打开（`FILE_SHARE_READ|FILE_SHARE_WRITE`）成功**——通道是共享模型，第三方可与代理并存，**打开这一步不构成障碍**；短报告（7 字节）`WriteFile` 也被接受。协议层握手（`GetFeature` 的回包）在临时 ctypes 探针里未拿到（裸 ctypes 的重叠 IO 不可靠，脚本本身还段错误了）——这属于工程细节，实现时应走 `hidapi`（它管报告尺寸与重叠 IO），不构成新的可行性疑问。剩余真正的未知只剩：与代理**并发发命令**的仲裁行为（谁后写谁生效？会不会互相打断）与设备索引/控件表的整理。
- **成本**：协议 + 设备表，中等偏高；**零签名成本、零常驻**。

### 档位 D：内核过滤驱动 / 虚拟 HID 设备（评估后不做，留门）

- **收益**：游戏的原始输入 / 反作弊场景；安全桌面的一部分；更早的拦截点；虚拟 HID 注入可绕过 UIPI。
- **成本**：EV 代码签名证书 + 微软驱动签名（每版提交、往返以天计）；HVCI / 内存完整性下必须兼容（会封掉传统 hook 写法）；安装卸载与内核残留；蓝屏是产品级事故；输入类内核驱动被 AV / EDR 报毒或被 Smart App Control 拦是常态；CI 与发布流程要从「三平台编译 + 测试」变成「加 WDK、签名、真机或虚拟机加载验证」；三平台一致性破裂（macOS 侧要 System Extension + 审核）。
- **重启条件（写清才叫留门）**：只有出现明确的企业 / 游戏场景需求，且愿意为它单开一条驱动签名与发布通道时才启动；届时形态必须是「**可选**驱动包 + 主程序检测到才启用」，绝不做成必需依赖。

### 4.5 对照表

| 档位 | 解决什么 | 签名 / 分发成本 | 主要风险 | 建议 |
|------|---------|----------------|---------|------|
| A 环境诊断 | 「为什么按了没反应」的可见性 | 无 | 误报 | **先做**（P2） |
| B 提权伴随进程 | 提权窗口里的注入（UIPI） | 无（安装包已有 UAC） | 多进程 + IPC + 权限边界 | **第二做**（归 7.2-㉑a） |

## 5. 落地顺序与分期验收

顺序：**A → B → C（先 spike 再实现）→ D 只留评估结论**。

每期都要在 `docs/人工验证清单.md` 补条目：

- **A**：在装了 Options+ 的机器上给出正确指引；误报可关闭；不影响未装接管软件的机器。
- **B**：在提权窗口（如管理员身份启动的记事本）里触发 Text / Keys 动作成功；未开启开关时行为与现在完全一致；安全桌面的边界说明如实。
- **C**：不退出 Options+ 就能触发侧键；**退出 Kada 后侧键仍按原生行为工作**（证明没有接管事件流）；打不开通道时退化为 A 的指引而不是报错。
- **D**：不适用（不实现）。

现有工具：`crates/kada-hook/examples/mouse_probe.rs`（鼠标侧键分诊探针）就是 C 的可行性 spike 的模板——它已经能自检「按需挂钩子」并回答「事件有没有到得了钩子」，C 只需把「观察事件」换成「打开厂商控制接口、读控件表」。

## 6. 未决问题（落地前必须实测）

1. **厂商控制接口在代理运行时能否打开**（共享 vs 独占）——**已实测（2026-10-16）**：共享打开成功、代理未独占（见 §4 档位 C「通道实测」）；前置已解除，剩余未知是并发命令仲裁与协议握手细节（实现时用 `hidapi`）。
2. 代理执行 `WIN_BACK` / `WIN_FORWARD` 时**是否注入**鼠标事件（决定「放宽防回环、接受厂商注入」这条备选是否存在；即便存在，也要评估其它自动化注入带来的误触）。
3. 提权伴随进程的启动方式（每次 UAC / 服务 / 计划任务）与卸载残留口径。
4. 环境诊断认哪些接管者、如何避免误报。
5. divert 复位策略：Kada 退出时要不要还原；不还原而代理也退出时按键会不会短暂失效。
6. macOS 是否要碰 System Extension（当前结论：不碰，与档位 D 同级）。

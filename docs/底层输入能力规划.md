# 底层输入能力 · 分档规划（提权伴随进程 / HID++ 解锁 / 内核驱动取舍）

> **结论先行**：三平台现在站的层不一样——**Linux 已经在最底层**（evdev + `EVIOCGRAB` 抓取 + uinput 虚拟设备注入），Windows / macOS 还在用户态钩子层。而「再往下走」的真实缺口只有两个：**厂商软件把按键 divert 走**（本机实证：Logi Options+ 拿走了 MX Anywhere 3 的侧键，退出即恢复触发）与**往提权窗口注入**（UIPI）。这两件事**都不需要内核驱动**：前者唯一的路是自己当 HID++ 客户端（纯用户态、零签名成本），后者是「可选的高权限伴随进程」。内核过滤驱动 / 虚拟 HID 设备（对应 7.2-㉑）的收益（游戏原始输入、安全桌面的一部分）不在当前痛点上，代价却是签发常态化 + 内核责任 + 杀软观感 + CI / 发布流程重构，**建议评估后不做、留门**。总原则：**深档位一律可选、可退化——只增加能力，永不做必需依赖**。
>
> 状态：规划完成（2026-10-16）。**档位 A / B / C 已落地**（V0.88 / V0.89 / V1.16，见 `docs/变更归档.md`；功能现状见 `需求设计说明书.md` §4.6 / §4.7 / §4.8，真机验收见 `人工验证清单.md` §30 / §31 / §34）；**D 评估后不做**（留重启条件）。

## 1. 诉求与边界

- **诉求**：不牺牲「轻快」定位与现有功能的前提下，尽量把输入层做得更靠下。
- **轻盈五条不变量**（任何深档位都必须满足；实现时同步写进 `人工验证清单.md` 的验收口径）：
  1. **只增能力，不做依赖**：没装 / 被策略禁 / 启动失败三种情况下，功能必须退化成当前版本（用户态钩子），而不是变慢、按键变哑或崩——与「吞键铁律」同级。
  2. **默认体积与常驻不增**：深档位是可选组件，主程序不打包；不新增常驻线程。
  3. **不进启动路径**：所有探测（驱动组件在不在、HID++ 通道能不能开）懒执行 + 带超时，不许破坏「冷启动零 WebView」。
  4. **事件驱动而非轮询**：设备变化走 `WM_DEVICECHANGE` / `RegisterDeviceNotification`，不新起看门狗线程。
  5. **失败可见**：一律「维持现状 + 消息中心一条提示」，不许静默。
- **边界**：不碰反作弊对抗；不为单家厂商设备改核心模型（`Key` / `Trigger` 不动，见 `docs/触摸板手势可行性调研.md` §3 的同类结论）；签名驱动不做默认分发。

## 2. 现状：三平台各站在哪一层

| 平台 | 抓取层 | 注入层 | 这一层看不到什么 |
|------|--------|--------|------------------|
| Windows | `WH_KEYBOARD_LL` + `WH_MOUSE_LL`（用户会话、非提权进程；鼠标钩子按需挂：`config_uses_mouse` → `set_mouse_enabled`） | `SendInput`（`simulate`）；前台是提权窗口时由提权进程重放（档位 B 已落地） | 安全桌面（UAC 提示、锁屏、登录）；win32k / shell 保留的组合键；被设备固件 divert 的按键（**罗技设备已可由档位 C 解锁**，非罗技仍无解） |
| macOS | 会话级 `CGEventTap` | `CGEventPost` | 提权进程；安全输入（Secure Input——终端里输密码时系统关掉所有事件 tap） |
| Linux | **已在最底层**：evdev + `EVIOCGRAB` 独占抓取（键盘与真鼠标） | uinput 虚拟设备（系统眼里是一台真键盘 / 鼠标） | 触摸板 / 指点杆（有意不抓，见 §4.2）、热插拔（需重启应用） |

- 补一条容易误解的：**`Raw Input`（`WM_INPUT`）不是「更底层」而是「更晚」**——它只能观察不能拦，而且被低层钩子吞掉的键它同样看不到。Kada 只用它做设备识别（7.1-㊷）。
- 「Linux 已经在最底层」这件事反过来解释了为什么 Windows / macOS 的限制在 Linux 上不存在：提权窗口、游戏原始输入在 Linux 都照常（注入出去的是真实虚拟设备事件）。

## 3. 两个真实缺口（决定该不该再往下）

### 3.1 厂商软件把按键 divert 走

- **机制**：罗技这类设备支持把某个按键**转交（divert）**给代理——代理经 HID++ 设置后，设备固件不再把该按键放进标准 HID 报文，改用 HID++ 通知只发给代理。Windows 输入栈里从来没有这次按下，**低层钩子拿不到，内核过滤驱动同样拿不到**（事件在到达系统之前就不存在了）。
- **本机实证（2026-10-16）**：Logi Options+ 运行中，MX Anywhere 3 的侧键无法触发 Kada 快捷键，浏览器后退 / 前进照常（那是代理自己执行的）；**退出 Options+ 后立即恢复触发**。旁证：接收器 HID++ 缓存里有 `0x1B04`（`REPROG_CONTROLS_V4`，可编程控件 / divert 特性）的查询并且设备回了索引；代理的指派表里侧键是它自己的系统动作（`WIN_BACK` / `WIN_FORWARD`），而**中键是直通**（`{"mouse":{"action":"BUTTON","hidUsage":3}}`）——「中键能用、侧键不能用」是这类接管的指纹。
- **Kada 侧同时已验通，排除自身 bug**：配置确实存进了触发键（`MouseForward`，启用中）；匹配逻辑对裸鼠标键必命中（`matches` 的 mods 空集恒为超集）；按需挂钩子实测会真的重装（诊断探针跑 `set_mouse_enabled(false→true→false→true)`，`reinstall_count` 递增）。
- **处置**：只有两条路——自己当 HID++ 客户端把 divert 关掉（档位 C），或让用户在厂商软件里让位（档位 A 给出指引）。

### 3.2 往提权窗口注入（UIPI）

- 这**不是抓取层问题**：钩子看得见按键，但注入进不去提权窗口。处置见档位 B。

**结论**：内核驱动能补的两类收益（游戏原始输入、安全桌面的一部分）都不在这两条缺口里。所以「尽量在底层」的正确解是分档补齐这两件事，而不是往内核钻。

## 4. 四个档位

### 档位 A：环境诊断与能力口径（零底层改动）——**已落地（V0.88）**

- **做什么**：识别已知的接管者（进程名 / 注册表里的 Logi Options+、G HUB、Razer Synapse 等）与内存完整性（HVCI）状态，接到现有 `platform_caps()` / `get_conflicts` 第④段那套「平台能力缺失 = 软冲突、不拦保存」的口径上，在快捷键页 / 帮助页给出**能照做**的指引。
- **为什么先做**：这类「按了没反应」的问题里，这是唯一能做且立刻见效的事；同时它是 B / C 的入口（用户得先知道发生了什么事）。
- **成本**：低（读进程名 / 注册表 + 一段文案）。风险：误报，需可关闭。
- **落地结果（2026-10-16）**：功能规格见 `需求设计说明书.md` §4.6（探测三平台口径、`DIVERTERS` 目录的收录边界、门控与开关、报告的 `supported` 字段），真机验收见 `人工验证清单.md` §30，文件级改动见 `docs/变更归档.md` V0.88。三处**与本文原描述不同**的决策，记在这里备查：
  - **HVCI 只作环境信息、不报成冲突**——原文把「内存完整性状态」列进了探测项，但它拦的是内核驱动、不拦本项目的用户态低层钩子，报成「能力缺失」就是纯误报。故它只进设置页卡片的结论区，不进冲突列表。
  - **只在配置用到鼠标键时才提示**——这类接管拿走的典型是侧键 / 额外键；配置里没用到鼠标键时它不影响任何一条快捷键。这是「误报可关闭」之外的第一道闸（第二道是 `settings.input_env_diag` 总开关，关掉后连探测都不跑；第三道是 `settings.input_env_ignored` 按单个接管者掐提示，「这台机器上它确实不影响我」的用户不必关掉整条诊断）。
  - **目录同时收了 Linux 的 evdev 抢占者**（`keyd` / `input-remapper`）：它们与 Kada 抢同一个 `/dev/input`，症状与 divert 一样（配置没错、就是没反应），归进同一份诊断；macOS 探测落地时未实现、后来已补（libproc 进程表，见 §6 未决 #4）。

### 档位 B：提权伴随进程（Windows；补 UIPI）——**已落地（V0.89，7.1-㉑a）**

- **做什么**：一个**可选、按需启动**的提权辅助进程，只负责**注入**（Text / Keys / Mouse），抓取仍在现有用户态钩子；IPC 走命名管道；设置里一个开关（「提权窗口也生效」），首次一次 UAC 拉起，平时不运行。
- **边界（界面必须说清）**：安全桌面（UAC 提示、锁屏、登录界面）仍然看不到也注入不进去——本档只补「提权窗口里的注入」。
- **为什么不是内核**：签署与分发成本为零（安装包本来就要 UAC），失败退化为现状，符合第 1 条不变量。
- **待定**：每次 UAC 拉起 vs Windows 服务 / 计划任务（后两者免每次弹窗但更重、卸载残留风险高）。
- **落地结果（2026-10-16）**：功能规格见 `需求设计说明书.md` §4.7，机制与信任边界见 `架构设计.md` §3.23，真机验收见 `人工验证清单.md` §31，文件级改动见 `docs/变更归档.md` V0.89。三处**与本文原描述不同**的决策，记在这里备查：
  - **不是独立组件，而是同一个 exe 的另一个模式**（`kada.exe --kada-agent <父进程 pid>`，壳层 `main` 在 Tauri 之前分派）：零打包改动、零卸载残留、版本天然与本体一致（握手行还带版本，升级后残留的旧代理会因版本不符被退回本地注入）。第 104 行那条「启动方式未决」因此有了答案：**不装服务、不建计划任务**，就是 `runas` 拉起的一份同 exe 进程。
  - **UAC 只在设置页点「启动提权进程」时弹**，开关本身不弹——「打开开关」是记一个偏好，「弹出提权授权」是一件要用户当场点头的事，两者不该绑在同一个动作里。启动时先试一次「直接连」（Kada 重启后提权进程可能还在），连不上才弹。
  - **生命周期 = 断开即退**，靠「客户端断开 / 父进程退出」两条边而不是心跳：开关关掉、Kada 退出、Kada 被强杀（父进程守望）都会让提权进程自己走掉。客户端与服务端**双向**识别（版本握手行 + 客户端问候）都是为了这一条不被误触发（校验完掉头就走的对端不该把进程带走）。
  - **能力面刻意窄**：通道上只有按键 / 鼠标 / 文本 / 停顿四类 op，没有「执行命令」这种口子；管道 DACL 只放行本用户 + 双向镜像路径 / 身份校验（提权进程能往任何提权窗口注入，「谁能对它说话」就是这条功能的权限边界）。
  - **一处已知不回补的缺口**：「转大小写」动作要先把剪贴板贴回去，而提权目标读不到普通权限进程刚写进剪贴板的内容（复制出来可以、贴回去不行），所以那条动作在提权窗口里仍不工作——改用「逐字符直发」注入方式即可（见 `需求设计说明书.md` §4.7 边界那条）。

### 档位 C：HID++ 解锁侧键（Windows 专属、按需）——**已落地（V1.16，7.1-㊿）**

- **做什么**：**只调 `setCidReporting(cid, divert=false)` 把按键交回标准 HID 报文**，让现成的钩子链直接看见它。**不接管事件流**——这是本档最关键的取舍：延迟与现在完全一致，Kada 退出也不影响按键（接管式的做法会多绕一圈、还得处理退出复位）。
- **触发时机**：设置页「输入层环境」卡片里的「解锁侧键」按钮（Windows 才有），不自动弹窗、不替用户决定；「查看罗技设备」是只读扫描。
- **参照实现**：Linux 上的 logiops / Solaar 就是用户态 HID++ 客户端（含控件表），规模可估。实现时以 Solaar 的 `REPROG_CONTROLS_V4` 代码为协议参照（功能 0 `getCount` / 1 `getCidInfo` / 2 `getCidReporting` / 3 `setCidReporting`，标志位语义一致）。
- **风险**：控件通道可能被代理独占打开（打不开就退化为档位 A 的指引）；控件 ID 按型号不同，要维护一张表；只覆盖罗技自家设备。
- **通道实测（2026-10-16，logioptionsplus_agent 运行中）**：接收器 `MI_02` 的三个 HID collection，**独占打开失败（WinError 32 = 代理占着）但共享打开（`FILE_SHARE_READ|FILE_SHARE_WRITE`）成功**——通道是共享模型，第三方可与代理并存，**打开这一步不构成障碍**；短报告（7 字节）`WriteFile` 也被接受。
- **成本**：协议 + 设备表，中等偏高；**零签名成本**，常驻代价见下条「落地结果」的保持线程。
- **落地结果（2026-10-20）**：功能规格见 `需求设计说明书.md` §4.8，命令见 §5.3，真机验收见 `人工验证清单.md` §34，文件级改动见 `docs/变更归档.md` V1.16。以下是与本文原描述不同 / 需要备查的决策：
  - **协议层走 `hidapi` 的 `windows-native` 后端**：枚举 HID++ 控制集合（VID `0x046D`、usage page `0xFF00`）、共享打开、重叠 IO 都由它管；不开默认的 C 后端，免得为一个 Windows 专属功能引入 cc 编译步骤。依赖只挂在 Windows 目标上，Linux / macOS 的交叉检查与 CI 不编它。
  - **只动三个 CID（`0x0052` 中键 / `0x0053` 后退 / `0x0056` 前进）**：手势键 `0x00C3` / SmartShift `0x00C4` 等即便可 divert 也不碰——解开它们会破坏用户在 Options+ 里的设置，而 Kada 键模型里也没有对应的键可绑。原描述「控件 ID 按型号不同，要维护一张表」的实际影响因此被压到最小：只认这三个跨型号一致的 CID。
  - **保持策略是轮询，不是事件驱动**（对 §1 第 2 / 4 条不变量的**有意例外**）：代理重启或设备重连把 divert 设回，没有任何系统事件会告诉我们；唯一能发现的办法就是读一次设备。故解锁成功后起一条**只在解锁期间存在**的线程，每 10 秒读一次 `getCidReporting`（不枚举、不写盘），被设回才写；句柄失效才重新枚举（30 秒一次，最多 20 次 ≈ 10 分钟）。休眠设备的超时按「暂时不应答」处理，不当作断开。Kada 退出 / 超过重连上限即线程结束——不装服务、不写配置、不留常驻。
  - **持久 divert 位一并清掉**：`getCidReporting` 若带 bit2（持久 divert），`setCidReporting` 同时置 persist 的 valid 位把它清零；否则设备可能带着旧配置在重连后复活。写完一律回读确认，仍 divert 就逐键报失败。
  - **实测结论（2026-10-20，Options+ 运行中，MX Anywhere 3 + Unifying 接收器）**：`hidpp_probe` 读到侧键 `divert=true`（中键 `false`，与「中键能用侧键不能用」的指纹一致）；`--unlock` 写入后回读 `divert=false`，进程退出 8 秒后再读仍为 `false`（persist 为 false，未污染设备配置）。**未实测**：与代理并发发命令的仲裁（设置后代理没有立刻反写；代理重启 / 设备重连时的竞争行为留给 §34 真机验收）。

### 档位 D：内核过滤驱动 / 虚拟 HID 设备（评估后不做，留门）

- **收益**：游戏的原始输入 / 反作弊场景；安全桌面的一部分；更早的拦截点；虚拟 HID 注入可绕过 UIPI。
- **成本**：EV 代码签名证书 + 微软驱动签名（每版提交、往返以天计）；HVCI / 内存完整性下必须兼容（会封掉传统 hook 写法）；安装卸载与内核残留；蓝屏是产品级事故；输入类内核驱动被 AV / EDR 报毒或被 Smart App Control 拦是常态；CI 与发布流程要从「三平台编译 + 测试」变成「加 WDK、签名、真机或虚拟机加载验证」；三平台一致性破裂（macOS 侧要 System Extension + 审核）。
- **重启条件（写清才叫留门）**：只有出现明确的企业 / 游戏场景需求，且愿意为它单开一条驱动签名与发布通道时才启动；届时形态必须是「**可选**驱动包 + 主程序检测到才启用」，绝不做成必需依赖。

每期都要在 `docs/人工验证清单.md` 补条目：

- **A**：在装了 Options+ 的机器上给出正确指引；误报可关闭；不影响未装接管软件的机器。
- **B**：在提权窗口（如管理员身份启动的记事本）里触发 Text / Keys 动作成功；未开启开关时行为与现在完全一致；安全桌面的边界说明如实。
- **C**：不退出 Options+ 就能触发侧键；**退出 Kada 后侧键仍按原生行为工作**（证明没有接管事件流）；打不开通道时退化为 A 的指引而不是报错。
- **D**：不适用（不实现）。

现有工具：`crates/kada-hook/examples/mouse_probe.rs`（鼠标侧键分诊探针）就是 C 的可行性 spike 的模板——它已经能自检「按需挂钩子」并回答「事件有没有到得了钩子」，C 只需把「观察事件」换成「打开厂商控制接口、读控件表」。

## 6. 未决问题（落地前必须实测）

1. **厂商控制接口在代理运行时能否打开**（共享 vs 独占）——**已解决（2026-10-16 / 10-20）**：共享打开成功、代理未独占（见档位 C「通道实测」）；协议握手已由 `hidapi` 实现并在真机跑通（`hidpp_probe` 读到了功能索引与 divert 状态、写入后回读确认）。**剩余未知只有并发命令仲裁**：设置后代理没有立刻反写，但代理重启 / 设备重连时谁后写谁生效没有专门实测（真机验收见 `人工验证清单.md` §34）。
2. 代理执行 `WIN_BACK` / `WIN_FORWARD` 时**是否注入**鼠标事件（决定「放宽防回环、接受厂商注入」这条备选是否存在；即便存在，也要评估其它自动化注入带来的误触）。
3. 提权伴随进程的启动方式（每次 UAC / 服务 / 计划任务）与卸载残留口径——**已定（2026-10-16，随档位 B 落地）**：**不装服务、不建计划任务**，就是 `runas` 拉起的一份「同一个 exe 的代理模式」进程（`--kada-agent`）；UAC 只在设置页点「启动提权进程」时弹一次；客户端断开或父进程退出即自行退出，故无卸载残留（见档位 B「落地结果」）。
4. 环境诊断认哪些接管者、如何避免误报——**已给口径（2026-10-16，随档位 A 落地）**：目录只收「真会抢按键」的两类（把按键 divert 给自己的罗技系 HID++ 客户端与各厂商驱动级改键软件、独占抓取输入设备的 Linux 改键守护进程），纯应用层改键 / 注入工具不入列；加条目前先确认真有 divert / 独占行为。误报用两道闸挡：**只在配置用到鼠标键时才提示**（影响面）+ `settings.input_env_diag` 总开关（关掉连探测都不跑）。**已知边界**：靠进程名片段反查，改名 / 自研代理认不出来（事件侧查不出是谁干的，见 §3.1）；另有别名的 Python 入口（`solaar` 的某些发行方式）可能漏认——宁可漏报不误报。macOS 探测**已补（2026-10-20，libproc：`proc_listallpids` + `proc_pidpath` 取基名，拿不到路径退 `proc_name` 内核短名）**；三平台进程探测至此都齐了。
5. divert 复位策略：Kada 退出时要不要还原；不还原而代理也退出时按键会不会短暂失效——**已定（2026-10-20，随档位 C 落地）**：**不还原**。为什么：① 关掉 divert 就是「让按键回到设备默认的标准报文」，这本来就是代理介入前的状态，Kada 退出后按键仍按原生行为工作（§34 要验的就是这一条）；② 想还原也没有可靠的值可写——代理原本的 divert / 持久标志随型号与配置而变，猜一个写回去可能把用户的厂商设置改坏；③ 代理仍在跑时它会按自己的配置处理，不需要我们操心。唯一的副作用是「代理退出 + Kada 也退出」之后侧键仍按标准报文工作（通常是用户想要的），不构成失效。
6. macOS 是否要碰 System Extension（当前结论：不碰，与档位 D 同级）。

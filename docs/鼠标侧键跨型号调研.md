# 鼠标侧键跨型号识别 · 调研（规划 7.2-㊼）

> **结论先行**：**两个标准侧键（后退 / 前进 = MB4 / MB5）跨型号、跨平台都一致，不需要也不该扩展**；超出这两个的「额外侧键」没有统一编号——各厂商靠驱动软件把它们重映射成键盘 / 媒体键，或上报成厂商私有 HID 用法，Windows 低层鼠标钩子根本看不到。因此**不做 `Mouse4..MouseN` 这类键模型**；需要第 3+ 个侧键的用户，用厂商软件把它重映射成 F13–F24 之类的冷门键再在 Kada 绑定（三平台通用、Kada 零改动）。本项**暂不立项（wontfix 级）**。
>
> 状态：调研完成（2026-10-15），**不产生代码改动**。

## 1. 问题

规划 7.2-㊼ 问的是两件事：① 不同型号鼠标的侧键是不是同一个东西（能不能跨型号识别）；② 现在只认标准两个侧键（`MouseBack` / `MouseForward`），要不要扩到游戏鼠标那种 3+ 侧键。本文回答这两点并给结论。

## 2. 标准侧键：跨型号一致（有事实标准）

**物理排布、品牌、外形都不影响**——只要鼠标把侧键报成「后退 / 前进」，三种系统给的都是同一套逻辑键（Kada 三平台各自映射到 `MouseBack` / `MouseForward`，中键同理）：

| 逻辑键 | Windows 低层钩子（§4.1） | macOS `CGEventTap`（§4.3） | Linux evdev（§4.2） |
|--------|------------------------|---------------------------|---------------------|
| 中键 MB3 | `WM_MBUTTONDOWN/UP` | `buttonNumber = 2` | `BTN_MIDDLE`（0x112） |
| 后退 MB4 | `WM_XBUTTONDOWN/UP`，`mouseData` 高 16 位 = **1**（XBUTTON1） | `buttonNumber = 3` | `BTN_SIDE`（0x113） |
| 前进 MB5 | `WM_XBUTTONDOWN/UP`，`mouseData` 高 16 位 = **2**（XBUTTON2） | `buttonNumber = 4` | `BTN_EXTRA`（0x114） |

- **Windows**：Win32 的鼠标按钮模型只有 **5 个**（左 / 右 / 中 / XBUTTON1 / XBUTTON2），`WM_XBUTTONDOWN` 的高位字标准值只有 1 和 2。
- **macOS**：`NSEvent` / `CGEvent` 的 `otherMouse` 用 `buttonNumber` 区分，2 = 中键、3 = 后退、4 = 前进是事实约定（Kada 现在就是这么映射的）。
- **Linux**：标准就是 `BTN_SIDE` / `BTN_EXTRA`；不同桌面 / 型号的物理位置可能反着（有的把「前进」放前面），可在系统或厂商软件里对调。
- **反例（重要）**：有些廉价鼠标 / 某些厂商默认就把侧键**固件级映射成键盘组合**（如后退 = `Alt+Left`），这种 Kada 看到的是键盘组合键、不是 `MouseBack`——按键盘组合绑定即可，与侧键识别无关。

**结论①**：标准两个侧键跨型号、跨平台一致，现有 `MouseBack` / `MouseForward` 就是正确的抽象，**不需要跨型号识别**。

> **补充（2026-10-16 本机实证，别和「跨型号」混为一谈）**：标准侧键也可能「按了没反应」——但那不是型号 / 编号不同，而是**厂商软件把按键 divert 走了**：Logi Options+ 经 HID++ 让设备固件把侧键从标准 HID 报文里摘掉、只发给代理，Windows 输入栈里**根本没有这次按下**，低层钩子（连内核过滤驱动也一样）拿不到。指纹是「中键能用、侧键不能用」（代理把中键设成直通）。这类问题**不是本文的「跨型号识别」能解决的**，处置是 `docs/底层输入能力规划.md` §3.1 / 档位 C（自己当 HID++ 客户端、只把 divert 关掉、不接管事件流），诊断与指引那一半已随 7.1-㊽ 落地。换句话说：**侧键「不统一」是身份问题（本文结论：不扩），侧键「不出现」是厂商接管问题（另走档位 C）**。

## 3. 额外侧键（第 3 个起）：没有统一标准

游戏鼠标常有多达 6~12 个可编程键，但**只有左 / 右 / 中 / 后退 / 前进这 5 个进入系统鼠标模型**，其余按键的上报方式各厂商不同：

- **经厂商驱动软件（Razer Synapse / Logitech G HUB / SteelSeries GG 等）重映射**：额外键在**驱动层**被改成键盘键、媒体键或宏，到 OS 时已经是键盘 / 媒体事件——Kada 看到的是那个**键**，不是鼠标键。
- **上报厂商私有 HID 用法 / 消费类 usage**：这类报文到不了 Windows 的 `WH_MOUSE_LL`——低层鼠标钩子只有那 5 个标准按钮的消息，额外键**根本不会触发 `WM_XBUTTONDOWN`**（除非驱动另做处理）。
- **Linux**：额外键可能落到 `BTN_TASK`（0x117）、`BTN_TRIGGER_HAPPY1..40`（0x2c0..0x2e7）等内核键码，或厂商自定义 `KEY_*`；**编号随型号 / 固件 / 驱动而变**，同一物理位置的键在两块鼠标上未必同一个码。
- **macOS**：HID 层按钮数可以更多，额外键可能以更大的 `buttonNumber` 出现，但**编号与语义不跨型号统一**（同一位置在不同鼠标上可能是 5、6、8……）。

**结论②**：超出 MB4 / MB5 的侧键**没有可移植的身份**。把它扩成 `Mouse4..MouseN` 这类中性键，等于假设「第 N 个额外键在所有型号上同义」——这个假设不成立；在配置跨平台同步（§5.6）的语境下更糟：同一个键码在另一台机器 / 另一个系统上无意义。

## 4. 如果非要支持 3+ 侧键（方案对比）

- **做法 1（推荐，零改动）**：用厂商软件把额外键**重映射成 F13–F24**（键盘玩家几乎不会用、系统也不占用）或某个冷门组合，再在 Kada 里绑定这个键。三平台通用、Kada 一行不用改，且这些键本来就在 `Key::ALL` 里。
- **做法 2（不推荐）**：按平台采集「不透明的原始码」（Linux `BTN_TRIGGER_HAPPY<n>` / macOS `buttonNumber` / Windows 只有 Raw Input HID 才有），配一个「仅本机生效」的标记。代价：配置跨平台同步会失效（别处认不出）、要新增 `Key` 变体 + `PlatformCaps` + 「不跨平台」语义 + UI 说明；收益只在少数多键鼠标用户，**投入产出比很差**。
- **做法 3（最重）**：Windows 读 Raw Input 原始 HID 报文 + 自己做命中/编号——等于重写一段 HID 解析，且额外键的语义依旧不跨型号，不解决根本问题。

## 5. 结论 / 建议

1. **保留现状**：`MouseMiddle` / `MouseBack` / `MouseForward` 三个标准鼠标键（中键 / MB4 / MB5）就是正确答案，**不扩 `Mouse4..MouseN`，不做跨型号识别**。
2. **㊼ 暂不立项（wontfix 级）**，留档备查；真正需要第 3+ 侧键的用户走**做法 1**（厂商软件重映射到 F13–F24 再绑定）。**标准侧键被厂商 divert 的问题不属本项**，另走 `docs/底层输入能力规划.md` 档位 C。
3. 建议在帮助页 / 常见问题里补一句做法 1 的变通（零风险、纯文档；本次只记调研，**未改帮助文案**）。
4. 若将来产品确实要「原生支持超 2 侧键」，只能走做法 2，并**明确不跨平台**——那时再按平台各自实现，不做中性键。

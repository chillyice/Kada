# 触摸板手势 / 模式作触发源 · 可行性调研（规划 7.2-㊻）

> **结论先行**：技术上**能做，但三平台难度差异极大**——Linux 最干净（libinput 直接产出 swipe / pinch / hold 事件），macOS 只能走私有 `MultitouchSupport.framework`，Windows **没有公开的触摸板手势拦截 API**（只能旁路读 Precision Touchpad 的原始 HID 报文、自己实现手势识别，且系统手势仍被 OS 消费）。推荐接法是**把「离散手势」映射成伪 `Key`**（如 `TouchSwipe3Left`），复用现成的触发 / 冲突 / 录入链路，**不动 `Trigger` 模型**；落地顺序建议**先 Linux、再评估 macOS、Windows 暂缓**。
>
> 状态：调研完成（2026-10-15），**未实现**。本文只回答「能不能做、怎么接、代价多大」，不含代码改动。

## 1. 诉求与边界

- **诉求（7.2-㊻）**：把触摸板 / 手势当**触发源**——三指 / 四指滑动、捏合放大缩小等，触发 Kada 的快捷键。
- 先把「触摸板的**模式**」这个词拆成两层，因为只有第二层是本项能碰的：
  1. **驱动 / 系统层的开关**：轻点即点（tap-to-click）、双指滚动方向、手掌误触抑制、打字时禁用触摸板、触控板软按键 vs 三指拖拽……这些是 OS / 驱动 / libinput 的**配置项**，不是能被第三方「拦截」的事件流。改这些应去系统设置，Kada 不该代管。
  2. **手势事件**：三 / 四指滑动、捏合 / 旋转、长按（hold）——这些是可被**读取**的动作，也是本项唯一有意义的落点。
- **边界不变**：**不抓触摸板**这条现行铁律照旧（Linux `EVIOCGRAB` 抓触摸板 = 整个触摸板失灵，见 `需求设计说明书.md` §4.2 / `架构设计.md` §5）。本调研只考虑**被动读取**（不独占设备）。

## 2. 三平台能拿到什么

### 2.1 Linux —— 最可行

- **libinput 直接产出高级手势事件**（`LIBINPUT_EVENT_GESTURE_SWIPE_BEGIN/UPDATE/END`、`GESTURE_PINCH_*`、`GESTURE_HOLD_*`）：swipe = 3 指及以上同向移动（带逻辑中心坐标，方向由调用方解释）；pinch = 2 指及以上距离 / 角度变化（带相对角度与相对初始的 scale 绝对值）；hold = 按停不动（仅 begin / end / cancel 三态，无坐标）。见 libinput 官方 *Gestures* 文档。
- **怎么接进一个普通应用**：用 libinput 的 **path 后端**——自己 `open()` 触摸板的 `/dev/input/eventX`，把它 `libinput_path_add_device()` 进自建的 `libinput_path` 上下文即可拿到手势事件。关键点：**path 后端不 `EVIOCGRAB`**，与合成器 / X 服务各自读同一设备互不冲突（内核允许多方读）。
- **权限**：读 `/dev/input/event*` 需要 `input` 组——Kada 的 Linux 输入层**已经要这个权限**（§4.2），无新增门槛。
- **注意点**：
  - 合成器（GNOME / KDE）自己也绑了三指手势（切工作区、概览等），Kada 读到同一动作时会**与系统手势并存**（一次滑动两个动作），要么让用户在系统设置里让出这几个手势，要么只挑系统默认没占用的（如四指）。
  - 会话切换时合成器可能 `EVIOCREVOKE` 我们打开的 fd → 读循环要能重新 `open`。
  - 多触摸板 / 触摸板 + 触屏的区分、两指触摸板（只报 2 slot）捏合与滑动的歧义——libinput 已文档化，需真机摸清。
- **备选**：绕过 libinput、自己解析 evdev 的 MT 协议 B 多点报文再做识别——可行，但等于重写 libinput 的手势识别，不值。

### 2.2 macOS —— 只能走私有 API，中等风险

- **公开 API 不覆盖全局**：`NSEvent` 的 `.swipe` / `.magnify` / `.rotate` 只投递给**当前前台窗口**，后台常驻的 Kada 收不到；Kada 现有的 `CGEventTap`（§4.3）拿到的是合成后的 `.scrollWheel` 等，**不含**多点手势。
- **私有 `MultitouchSupport.framework`**：`MTDeviceCreateList` / `MTRegisterContactFrameCallback` 可在系统级拿到**原始触点帧**（BetterTouchTool 长期用这套）。代价：**未公开、随时可能变**，要自己在触点上做手势识别；且读原始 HID 需用户在「隐私与安全性」里再授一项 **「输入监控」**（与现有的「辅助功能」独立）。
- **结论**：能做，但建立在未文档化 API 上，且要新增一项权限 + 自己实现识别。维护成本与风险高于 Linux。

### 2.3 Windows —— 无公开手势拦截 API，最贵

- **公开 API 层没有「第三方全局拦触摸板手势」这条路**：Windows Precision Touchpad 的三 / 四指手势由 OS 自己识别并派给**系统动作**（设置里只能选「三指左右 = 切换应用 / 桌面」这类预设），不暴露给普通应用拦截。
- **`WM_GESTURE` / `WM_TOUCH`** 面向触摸屏 / 已注册触摸的窗口，Precision Touchpad **不会**把系统手势转成窗口消息；`Windows.UI.Input.GestureRecognizer` 处理的是触摸 / 笔的 Pointer，不覆盖触摸板。
- **唯一旁路**：把 Precision Touchpad 当作 HID 设备、用 Raw Input 旁路（Kada 的键盘设备识别已是这套机制，`架构设计.md` §3.22）读它的**原始多点报文**（Digitizer / TouchPad usage），然后**自己实现手势识别**。代价与坑：
  - 要解析 HID 报告描述符 + 多点报文（不同厂商 / 固件报文形态不一）——工作量大、兼容性风险高；
  - 即便如此，**系统手势照样被 OS 消费**（除非用户去设置里逐个关掉），「拦得住」做不到；
  - Kada 现有 Raw Input 只订阅了键盘 usage，扩展到触摸板要新开订阅 + 一套报文解析。
- **结论**：投入产出比最差，建议**暂缓**。

### 2.4 对照表

| 平台 | 可用事件 | 接入方式 | 权限 | 系统手势是否仍生效 | 成本 | 风险 |
|------|---------|---------|------|------------------|------|------|
| Linux | swipe / pinch(含旋转) / hold | libinput path 后端（被动读 evdev） | 复用现有 `input` 组 | 是（合成器也绑，需用户让位或选没占用的方向 / 手指数） | 中 | 中（会话切换重开、多设备歧义） |
| macOS | 仅原始触点（需自做识别） | 私有 `MultitouchSupport.framework` | 新增「输入监控」 | 是 | 中高 | 高（私有 API） |
| Windows | 仅原始 HID 多点报文（需自做识别） | Raw Input 旁路 + HID 解析 | 无需新增 | 是 | 高 | 高（报文兼容、OS 仍消费） |

## 3. 与现有模型的接法（建议：伪 `Key`）

现有触发链路完全建立在 `Key` / `KeyEvent{Down,Up}` / `Shortcut{mods,key}` / `Trigger{Combo|Sequence|Chord}` 上（§2）。两种接法：

- **（推荐）把离散手势映射成伪 `Key`**：给 `Key` 增一组 `TouchSwipe3Left/Right/Up/Down`、`TouchSwipe4*`、`TouchPinchIn/Out`（命名待定），钩子层把手势识别结果**当成一次「按下即抬起」的按键**交给决策器（与鼠标中键 / 侧键当年接入一致）。
  - **好处**：`Trigger` / `Shortcut` / 冲突检测 / UI 录入 / 改键 `from`·`to` / `Recorder` **一行都不用改**。
  - **约束**：手势**不进修饰键空间**（同鼠标键），只能是触发键 / 改键目标；`Key::ALL` 与前端 `KEY_OPTIONS` 必须同步（`frontend_key_table_matches_core` 守着）；**连续量不做触发**（捏合比例、双指滚动）——只做**离散化**后的「捏合放大 / 缩小」这类。
- **（不推荐）新增 `Trigger::Gesture`**：要牵动冲突指纹、判重、编辑 UI、`Recorder`、`sanitize` / `merge` / 片段摘取——爆炸半径远大于收益。

配套：`PlatformCaps` 增一条「触摸板手势」能力项（见 §3 冲突检测的 `platform` 标注）——配置里写了手势触发，但在不支持 / 未授权的平台**如实标成「当前平台用不了」**，而不是静默失效。

## 4. 成本 / 风险与落地建议

- **建议分阶段**：
  1. **先 Linux**：libinput path 后端拿 swipe / pinch / hold，映射伪 `Key`，打通「触发 → 冲突 → 录入 → 保存」整条链路。这是唯一能把坑摸清、又不用碰私有 API 的平台。
  2. **再评估 macOS**：私有 `MultitouchSupport.framework` + 自做识别 + 「输入监控」权限——先做**一次性真机 spike**（能否稳定拿到触点帧、是否影响现有 `CGEventTap`）再决定是否上。
  3. **Windows 暂缓**：除非产品明确需要，且接受「自己解析 HID + 系统手势仍生效」。
- **共同风险**：与系统手势**双动作**（用户需在系统设置让位）；伪键与真实键盘 / 鼠标键的键名冲突；`Key` 增键后前端表与 `Key::ALL` 必须同步（已有测试守）。
- **值不值得**：定位上属**极客向**能力，受众窄（有此诉求的用户多半已在用 BetterTouchTool / 系统手势）。建议排在 7.2 里较后，且**先出 Linux 版验证手感**再决定铺开。

## 5. 未决问题（落地前需真机验证）

1. **Linux**：path 后端与合成器自带手势**能否并存**（双动作是否必然）、`EVIOCREVOKE` 后重开是否稳定、两指触摸板的歧义实际表现。
2. **macOS**：`MultitouchSupport` 在当前系统版本是否仍可用、「输入监控」授权粒度、与现有 `CGEventTap` 是否互斥。
3. **手势离散化口径**：swipe 方向判定（阈值 / 主方向）、pinch 到「放大 / 缩小」的阈值、是否要「双击手势」这类组合——均属手感调参，需真机打磨。

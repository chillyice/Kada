# Kada 竞品分析与优化规划

> 本文档从「极客 / 键盘玩家」视角，把 Kada 放到主流开源快捷键 / 改键 / 自动化软件里做横向对比，找出差距与短板，并给出分阶段的优化改进路线图。
> 定位：**规划文档，不是需求文档**。落地到实现时，功能细节同步进 `docs/需求设计说明书.md`，实现归档进 `docs/变更归档.md`。
> 竞品事实核实于 2026-09-22（GitHub API + 官方文档站），stars 为量级参考，会随时间变动。

---

## 0. 摘要（先说结论）

Kada 当前的差异化是**跨平台 + 图形化配置 + 宏录制 + 消息中心**，这在「纯配置文件 / 纯脚本」为主的开源赛道里是稀缺的——绝大多数改键工具（Kanata/keyd/KMonad/xremap）没有配置界面，绝大多数自动化工具（AHK/AutoKey/Hammerspoon）要写脚本。Kada 的上手门槛天然更低。

但对比竞品，Kada 缺的是**键盘玩家公认的「标准能力」**，按价值排序：

1. **同键长按/短按不同义（tap-hold）与多层（layers）** —— 竞品标准能力，改键赛道的灵魂。
2. **文本扩展（hotstrings，输缩写自动展开）** —— 竞品标准能力，Kada 已有全部底层可低成本补上。
3. **应用/窗口/设备维度的条件触发** —— 竞品标准能力，Kada 的条件系统还停留在「路径/变量」。
4. **键序列 / leader key / 和弦** —— 极客刚需（Vim 风格）。
5. **高级修饰（oneshot/sticky/multi-tap）** —— 改键进阶能力。
6. **鼠标键作为触发与模拟目标** —— 竞品普遍支持。
7. **键模型残缺**：无媒体键、F13-F24、NumPad 区 —— 纯遗漏，成本最低、应最先补。
8. **脚本化扩展、配置分享生态** —— 中长期差异化方向。

建议的落地顺序：**先补键模型（P0，零风险）→ 上文本扩展（P1，性价比最高）→ 做 tap-hold/layers（P1，改键灵魂）→ 加上下文条件（P1）→ 再做键序列/鼠标/脚本/生态（P2/P3）**。

## 1. 分析视角与定位

- **我是谁**：长期折腾机械键盘、用 QMK 分层、写 AHK 脚本、把 CapsLock 改成 `tap=Esc / hold=Ctrl` 的那类用户。对快捷键工具的三个核心诉求：**低延迟、一 key 多用、上下文自适应**。
- **Kada 定位**（据 `AGENTS.md` / `需求设计说明书.md`）：轻快跨平台快捷键 / 改键 / 宏工具，托盘常驻，JSON 配置落盘可同步。**它不是 AHK（图灵完备脚本），也不是 Kanata（硬核改键引擎），而是「图形化、跨平台、带条件与变量的宏/改键工具」**。
- 本规划的所有建议，都以「守住这条定位」为前提——不去抢 AHK 的脚本生态，也不去抢 Kanata 的纯配置文件硬核分层，而是把竞品的**标准能力**用 Kada 的**图形化 + 跨平台**方式重新表达。

## 3. 分维度差距分析

### 3.1 键模型完整性 —— 纯遗漏，成本最低

**Kada 现状**（`kada-core/src/lib.rs`）：字母/数字/F1-F12/标点/功能键/方向键/编辑键，**没有**媒体键、F13-F24、NumPad 数字区、NumLock、鼠标键。

**竞品**：AHK/Karabiner/Kanata 支持媒体键（音量/播放/上一曲）、F13-F24、鼠标键（侧键 MB4/MB5 常被拿来改键）、NumPad 区独立映射（NumLock 状态区分）。

**差距**：这是纯枚举遗漏，补齐不涉及架构。媒体键是很多人「给 CapsLock/侧键绑音量」的直接诉求；NumPad 缺失导致无法把方向键改到小键盘。

### 3.2 触发方式 —— 只有「修饰键 + 单主键」

**Kada 现状**：`Shortcut { mods, key }`，触发只能是「若干修饰键 + 一个主键」。匹配是「超集宽松规则」（`Ctrl+Shift+K` 也命中 `Ctrl+K`）。

**竞品标准能力**：
- **键序列 / leader**：Kanata leader、xremap 键序列（`C-x C-c`）、skhd modal。先按一个 leader 键，再按序列，可无限扩展，且不需要同时按住修饰键。
- **和弦 / 同时按键**：Karabiner `from.simultaneous`、PowerToys chords、Kanata output chords。
- **长按/连击触发**：KMonad multi-tap（单击/长按/双击各不同）。

**差距**：Kada 的触发表达能力是「一次性组合」，无法表达「先按 A 再按 B」的序列，也无法「按一下/长按」区分。这直接限制了热键数量与手感。

### 3.3 改键能力 —— 只有 key→key，缺改键的灵魂

**Kada 现状**：`Remap { from, to }`，单键单向，支持改键优先级高于快捷键。

**竞品标准能力（改键赛道的核心）**：
- **tap-hold（同键长按/短按不同义）**：Kanata tap-hold、keyd `overload(control, esc)`、KMonad、Karabiner `to_if_alone`/`to_if_held_down`。**这是键盘玩家改键的第一诉求**：CapsLock 短按 = Esc、长按 = Ctrl。
- **多层 layers**：Kanata `deflayer`、keyd、KMonad、xremap modmap/keymap、Karabiner profiles。一层装不下时切层，键位翻倍。
- **oneshot / sticky 修饰**：keyd `oneshot(shift)`、Karabiner sticky_modifier。按一下 Shift 临时生效一次。
- **multi-tap**：KMonad 单击/长按/双击三种行为。

**差距**：Kada 的改键停留在「原始键 → 目标键」的一一映射，这是 2000 年代的改键水平。不补 tap-hold 和 layers，在键盘玩家眼里改键功能基本等于没有。

### 3.4 文本扩展（hotstrings）—— 性价比最高的一块空白

**Kada 现状**：有 `Text` 动作（粘贴文本、大小写转换），但必须**先按快捷键**触发。没有「输入 `:addr` 自动展开成完整地址」的常驻文本扩展。

**竞品标准能力**：
- **Espanso**（专注此道）：`matches` 触发词 + `:date` 动态片段 + Forms 表单 + 正则/动态匹配 + 按应用过滤 + Hub 包市场。
- **AHK hotstrings**、**AutoKey phrases**、PowerToys「键→文本」。

**差距与机会**：Kada 已有全局键盘钩子（能监听输入流）+ 剪贴板文本注入（`type_text`），**做文本扩展缺的只是「监听当前输入缓冲 + 缩写匹配 + 回删缩写再注入」这一层**，底层全部就绪，成本远低于从零起步的竞品，是性价比最高的补强项。

### 3.5 上下文感知 —— 条件系统还没到「应用/窗口」维度

**Kada 现状**：`Condition` 有 `Exists/NotExists/IsFile/IsDir/Equals/NotEquals/ModifiedWithin`，覆盖**路径**与**变量**；`If` 动作可递归嵌套。变量系统（`GetFileProps`/`Status`）是竞品中少见的亮点。

**竞品标准能力**：
- **前台应用/窗口条件**：Karabiner `frontmost_application_if`、xremap 应用过滤（正则）、keyd `app.conf`、PowerToys app-specific、skhd app-specific、Espanso `filter_title`。
- **设备维度**：Karabiner `device_if`、keyd `[ids]`、xremap 设备过滤——多键盘场景。
- **输入法/布局**：Karabiner `input_source_if`、`keyboard_type_if`。

**差距**：Kada 的快捷键/改键是**全局**的，无法「同一快捷键在浏览器里开新标签、在 IDE 里调出终端」。这是「上下文自适应」诉求的直接缺口。好消息是 `If`/`Condition` 框架已经搭好，加一个「前台应用是什么」的条件变体是顺势扩展。

### 3.6 脚本化扩展 —— 有固定动作链，无图灵完备

**Kada 现状**：动作链是**封闭的枚举**（Text/Command/Keys/PauseMs/Os/App/If），变量仅 File/Bool/Text。表达能力有边界。

**竞品**：AHK（完整脚本）、AutoKey（Python）、Hammerspoon（Lua）、Kanata `--features cmd`、KMonad command buttons。

**判断**：这**不一定是缺口，而是定位选择**。Kada 的价值恰在「不写脚本也能用」。脚本化放 P3，且建议**嵌入轻量脚本引擎（如 Rhai/Lua）作为一个 `Action::Script` 变体**，而不是推翻现有动作链——把脚本当「高级逃生舱」，普通用户仍用图形化。

### 3.7 鼠标控制 —— 完全空白

**Kada 现状**：只处理键盘事件，无鼠标钩子、无鼠标模拟。

**竞品**：AHK 鼠标热键、Karabiner `mouse_key/mouse_motion_to_scroll`、Kanata 鼠标模拟、AutoKey 鼠标。

**判断**：中价值。键盘玩家最想要的是「鼠标侧键当快捷键/改键目标」和「键盘模拟鼠标移动/滚轮（全键盘操作）」。前者依赖加鼠标钩子，成本中；后者是进阶玩法，放 P3。

### 3.8 生态与分发 —— 无配置分享

**Kada 现状**：有导出/导入 JSON，无分享市场、无社区包。

**竞品**：Espanso Hub、Karabiner complex-modifications 社区站、AHK 脚本库、Hammerspoon Spoons。

**判断**：非核心，但 JSON 可编辑 + 可 git 管理本身就是 Kada 的优势，把它包装成「可分享的配置片段市场」是中长期生态加分项，放 P3。

## 5. 分阶段路线图（含设计建议）

### 阶段一（P0）：补齐硬伤，零架构风险

**目标**：让 Kada 先成为一个「键位齐全、鼠标侧键可用」的工具，消除最显眼的短板。

1. **键模型补全**
   - `kada-core` 的 `Key` 增：`MediaPlayPause / MediaPrev / MediaNext / VolumeMute / VolumeDown / VolumeUp`、`F13..F24`、`Numpad0..9 / NumpadAdd / NumpadSubtract / NumpadMultiply / NumpadDivide / NumpadDecimal / NumpadEnter / NumLock`。
   - 平台映射：Windows `VK_MEDIA_*`/`VK_F13..F24`/`VK_NUMPAD*`，Linux evdev `KEY_PLAYPAUSE` 等。媒体键/NumPad 在 Windows 低层钩子下可拦截。
   - 同步 `key_name` 渲染 + UI 下拉。**风险极低**，纯扩展。

2. **鼠标钩子（触发/改键）**
   - 新增 `WH_MOUSE_LL`（Windows）/ evdev 鼠标设备（Linux，注意抓取与键盘并存），产出统一 `MouseEvent { button, pressed }`，或并入 `RawEvent` 的键集合（把 MB4/MB5 当作 `Key` 成员）。
   - 用途：鼠标侧键/中键/滚轮键可作为 `Shortcut` 主键或 `Remap` 的 from/to。
   - 风险提示：鼠标钩子比键盘钩子更容易误伤（全局点击拦截），需要**只在配置里引用了鼠标键时才安装**，默认不挂。

### 阶段二（P1）：三项「灵魂级」能力

**目标**：把 Kada 从「能用的改键工具」提升为「键盘玩家会认真考虑的工具」。

1. **文本扩展（hotstrings）—— 建议最先做**
   - 在壳层加一个「输入缓冲监听器」：当不在触发快捷键/改键时，把放行的可打印字符累积成最近 N 字符的滑动窗口；命中某个缩写触发词 → 回删该缩写（发 N 次 Backspace）→ 注入展开文本。
   - 配置模型：`TextExpansion { trigger: String, replace: String, mode: Replace|Append, filter: Option<AppFilter> }`，新增 `Config::expansions`。
   - 动态片段：`{date}`/`{time}`/`{clipboard}` 占位符（复用现有 `substitute_vars` 思路）。
   - 体验细节对标 Espanso：长尾触发词要加「触发后缀」（如空格/回车/Tab）避免误触；支持按应用过滤（复用阶段二第 3 项的应用条件）。

2. **tap-hold + 多层 layers —— 改键升级（成本最高的 P1）**
   - 把 `Remap` 从 `{from,to}` 扩展为带行为的改键：
     ```
     Remap {
       from: Key,
       tap: Option<Key>,      // 短按（<阈值，如 200ms）输出
       hold: Option<Key>,     // 长按输出（典型：修饰键）
       tap_timeout_ms: u64,
     }
     ```
   - `layers`：`Config::layers` + `ShortcutItem::layer` / `Remap::layer`，加一个「切层键」（hold 进入某层 / tap 切到某层）。层切换状态机放在改键决策层（`decide` 之前）。
   - 设计要点：tap-hold 判定必须在**按下后延迟到超时**才能决定 tap 还是 hold，这会让「短按」的响应变慢一个阈值（约 200ms）——需要引入「roll 判定」优化（按了别的键立刻判定为 hold），否则手感差。这是本项的主要复杂度来源。
   - UI：改键编辑从两个下拉扩成「短按/长按 + 阈值滑块」，层用可视化列表 + 当前层高亮。

3. **应用/窗口/设备维度条件 —— 顺势扩展**
   - `Condition` 增：
     - `FrontmostApp { app: String }` / `NotFrontmostApp`（按进程名/窗口标题，支持正则或通配）。
     - `WindowTitleContains { text: String }`。
     - `DeviceIs { id: String }`（多键盘，Linux evdev / Windows 设备路径）。
   - 落到 `ShortcutItem`/`Remap` 上加可选 `when: Option<Condition>`（触发前先求值）。
   - 取前台窗口：Windows `GetForegroundWindow` + `GetWindowText`/进程名；Linux 需各桌面环境（X11 可用 `_NET_ACTIVE_WINDOW`，Wayland 较难，先 X11 + 已知 WM 适配，Wayland 标注受限）。

### 阶段三（P2）：极客进阶与生态

1. **键序列 / leader key / 和弦**
   - 触发模型从「单次组合」扩成「可选序列」：`triggers` 支持 `"F9" + "J" + "K"` 这类序列，或引入 `leader` 概念（按 leader 键后进入「等待下一键」态，超时回退）。
   - 需要触发层的「序列状态机」：记录当前进度、超时回退、Esc 取消。与 tap-hold 的层状态机**共享一个统一的「键盘状态机」**，避免两套时序逻辑打架——建议阶段二做 tap-hold 时就预留这一层。

2. **oneshot / sticky / multi-tap**
   - 在改键状态机上加 `oneshot(Shift)`（按一下临时生效一次）、`sticky`（锁住修饰直到再按）、`multi-tap`（单/双/三击不同义）。这些是 tap-hold 状态机的自然延伸，放 P2 成本可控。

3. **配置分享 / 片段市场**
   - 后端：配置片段（单条快捷键/改键/动作组）导出为独立 JSON 片段 + 在线仓库。
   - 前端：内置「片段市场」入口，一键导入。对标 Espanso Hub / Karabiner complex-modifications。技术选型另议（GitHub 仓库 + 静态索引即可起步）。

### 阶段四（P3）：差异化纵深

1. **脚本化扩展**：新增 `Action::Script { lang, code }`，嵌入 Rhai（Rust 生态友好、沙箱化）作为高级逃生舱；普通用户仍走图形化。**不推翻现有动作链**，脚本作为动作链的一个变体。
2. **鼠标模拟**：键盘模拟鼠标移动/点击/滚轮（全键盘操作），对标 Karabiner mouse_key。
3. **既有规划落地**：macOS 输入层、驱动级拦截（Interception）、`type_text` 直发兜底、Linux 热插拔、配置云同步、动作并行、可视化编排 —— 详见 `需求设计说明书.md` 第 7 章，本规划不重复展开。

## 6. 极客视角的期望清单（总结）

作为一个会把 CapsLock 改成 `tap=Esc / hold=Ctrl`、给 F13 绑脚本、在 IDE 里用 leader 键的键盘玩家，我对 Kada 的期望按「最想要」排序：

1. **给我 tap-hold 和 layers**。没有这两样，改键等于没做。我第一件事就是把 CapsLock 变成「短按 Esc / 长按 Ctrl」。
2. **给我文本扩展**。`;sig` 展开成签名、`;addr` 展开成地址，这种高频刚需比任何宏都实用。
3. **同一快捷键在不同应用干不同事**。浏览器里 `Ctrl+Alt+K` 开新标签，IDE 里它调出终端。
4. **键位别缺**。我要把侧键 MB4 改成 Home、把音量键绑到别的键上，现在这些键你都没有。
5. **Vim 风格序列触发**。先按 leader 再按两个键，比同时按三个修饰键舒服得多，热键数量也能翻几倍。
6. **保持你现在的好东西**：图形化界面别丢、配置还是可读可 git 的 JSON、命令结果能统一看到、启动零 WebView 的轻快感别破坏。

一句话：**Kada 已经赢在「易用」和「跨平台」，接下来要赢在「深度」——把键盘玩家公认的 tap-hold/layers/文本扩展补上，你就有了和 Kanata、Espanso 正面竞争的本钱，而且你还比它们多一个它们都没有的图形界面。**

## 7. 落地原则与风险

- **一条主线**：P0/P1 的能力都往「图形化配置」里落，不要求用户手写配置。这是 Kada 对 Kanata/keyd 的护城河。
- **状态机统一**：tap-hold、layers、键序列、oneshot、multi-tap 本质是同一套「键盘时序状态机」，**不要各自实现一套**。建议阶段二做 tap-hold 时就把状态机抽象好，阶段三直接复用，否则后面会堆出一堆互相打架的时序 bug。
- **性能红线**：所有这些都在钩子回调/热路径里跑，必须保持「处理函数直接跑在回调内」的低延迟特性；tap-hold 的 200ms 判定延迟是唯一可接受的新增延迟，其余不得引入队列/线程切换。
- **跨平台一致性**：所有新概念（层、tap-hold、上下文条件）先在 `kada-core` 定义平台无关模型，平台层只做「OS 事件 → 统一模型」的映射，延续现有 `win`/`linux` 双后端对齐策略。
- **风险最高的三处**：① tap-hold 判定延迟与「roll 判定」优化；② 鼠标钩子全局拦截误伤；③ Wayland 下取前台窗口/设备受限。前两处是手感与体验风险，第三处是平台能力边界，均需在对应阶段单独验证。

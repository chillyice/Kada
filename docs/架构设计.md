# Kada 架构设计

> 系统分层、一次按键的完整流转、关键机制与跨平台策略。动架构前重读本文档。

## 1. 分层与模块分域

```
┌──────────────────────────────────────────────────────────┐
│  UI（kada-ui，Vite + TS）                                 │
│  快捷键 / 改键 / 宏录制 —— 通过 Tauri command 读写配置      │
└───────────────────────┬──────────────────────────────────┘
                        │ invoke (get/set_config, set_paused, start/stop_record)
┌───────────────────────▼──────────────────────────────────┐
│  桌面壳（src-tauri，crate `kada`）                        │
│  KadaState / decide / engine（状态机）/ 托盘                │
└──────┬──────────────────────────────────────┬────────────┘
       │ 喂入 Ev                               │ 命中后 spawn → run_actions
┌──────▼────────────────┐  ┌──────────────────▼───────────┐
│ 钩子引擎（kada-hook）  │  │ 动作执行引擎（kada-actions）    │
│ win/linux/simulate    │  │ run_actions/run_os/run_app/  │
│ 监听 + 拦截 + 注入     │  │ run_cmd/Script + CommandResult│
└──────┬────────────────┘  └──────┬───────────────────────┘
       │                          │
       └────────────┬─────────────┘
                    │ 键模型 / 配置模型 / simulate 接口
         ┌──────────▼────────────────┐
         │ 核心逻辑（kada-core）       │
         │ Key/Modifier/Shortcut/    │
         │ Action/Config 解析匹配     │
         └───────────────────────────┘
```

- **kada-core**：零重量纯逻辑，无平台依赖、可独立单测。键模型 + 快捷键解析/匹配 + 配置模型（JSON 序列化）。是跨平台一致性的锚点。自动化动作 schema（`Command`/`Os`/`App`/`If`/`Script`/`Condition`/`Vars`）由 `automation` feature 门控。
- **kada-hook**：平台钩子引擎，把 OS 键盘事件翻译成统一 `KeyEvent`，回调决定 `Action`（`Allow/Block/Replace`），注入由 `simulate` 完成。Windows（`WH_KEYBOARD_LL`）与 Linux（evdev + uinput）两后端，接口对齐。
- **kada-actions**：动作执行引擎（`automation` feature 门控），把「触发 → 执行一串动作」落地逻辑（`run_actions`/`run_os`/`run_app`/`run_cmd`/`run_script`/`transform_case`）从壳迁出，产出 `CommandResult` 供壳进消息中心。依赖 `kada-core`（模型）+ `kada-hook`（模拟注入），不依赖 Tauri、可独立单测。
- **src-tauri（`kada`）**：配置驱动的壳。启动加载 JSON → 钩子接入配置匹配 → 托盘常驻。命令层承载 UI 读写配置。跨平台事件管道用自有 `Ev`，各平台钩子都喂给 `decide`/`Recorder`；命中快捷键后 `fire` spawn 后台线程调 `kada_actions::run_actions`。两个壳内独立模块：`engine.rs`（输入侧时序状态机，见 §3.9/§3.12）、`update.rs`（软件更新，见 §3.14）——都尽量与 Tauri 解耦以便单测。

## 2. 一次按键的旅程（以快捷键为例）

1. OS 键盘事件进入钩子（Windows 低层钩子回调 / Linux evdev 事件循环）。
2. 钩子翻译成 `KeyEvent::Down { key, mods, repeat }`，交给壳注册的 handler。
3. 壳若在录制中 → 事件进 `Recorder` 时间线、放行。否则依次过 tap-hold → 和弦 → 键序列三个状态机（`engine.rs` 的 `Engine::step`）：待凑齐的键先吞掉、被吞键不进 `decide`；**没组成快捷键的按键由状态机原样回放**（见 §3.6 吞键铁律）。
4. 其余事件读配置经 `decide` 判定：
   - 改键命中 → `HookAction::Replace(to)`（吞原键、注入目标键）。
   - 快捷键命中 → 异步 `fire(action)` + `HookAction::Block`。
   - 否则 → `HookAction::Allow`（放行），并继续喂给 `Engine::hotstring` 累积热串缓冲。
5. 钩子按 `Action` 执行：`Allow` 放行 / `Block` 吞掉（登记 `SWALLOWED` 连 keyup 一起吞）/ `Replace` 登记并注入目标键。
6. 注入走 `simulate`：文本用剪贴板 + `Ctrl+V`；组合键全部按下 → 稍停 → 逆序松开。

## 3. 关键机制

### 3.1 幽灵按键防护（吞键 + 改键）

- 决定吞掉的键登记进 `SWALLOWED`；后续该键的 keyup 一并吞掉，避免"吞了 down 却漏了 up"产生幽灵按键。
- `Replace` 维护 `REPLACED_DOWN`（原键 → 目标键）：按住原键期间只注入一次目标键 down，抬起时注入目标键 up，保持"按下-抬起"配对；自动重复不重复注入。
- Windows 注入事件带 `LLKHF_INJECTED` 一律放行，杜绝自我回环；Linux 事件全走 uinput 虚拟键盘，天然无回环。

### 3.2 修饰键状态与方向修正

- Windows：`GetKeyState` 实时读修饰键（事件键自身方向手动修正，避开队列滞后）；Linux：按事件流维护 `MODS_DOWN`（吞键/改键不动真实状态位）。
- 两后端都做"事件键若是修饰键则包含其自身"的方向修正，保证 `Ctrl+Ctrl` 等边缘组合的语义一致。

### 3.3 快捷键匹配（宽松超集规则）

`matches(e, s)` = 主键一致 **且** 事件修饰键 ⊇ 快捷键修饰键。按下 `Ctrl+Shift+K` 也命中 `Ctrl+K`，避免用户多按一个 Shift 就触发失败。改键优先于快捷键（先消耗原生键）。

### 3.4 宏录制器

- 把全局键盘事件转录成 `Action` 时间线：重复 down 折叠；事件间时差 ≥20ms 补 `PauseMs`；组合键合并成一条 `Keys`，键名落盘为可读字符串（`key_name`）。
- 录制中快捷键/改键全暂停（所有事件进时间线并放行）；结束补全仍按住键的 keyup。

### 3.5 文本注入（剪贴板）

`type_text` 用剪贴板 + `Ctrl+V`：对中文等 Unicode 最稳；副作用是短暂占用并恢复剪贴板。目标程序吞粘贴（游戏/终端）的极端场景后续可加 `KEYEVENTF_UNICODE` 直发兜底（两者加开关）。

### 3.6 窗口懒创建（冷启动零 WebView）

启动时不创建任何窗口（`tauri.conf.json` 的 `windows` 为空）：主窗口由 `show_main_window()` 按需建出（托盘菜单「打开」/托盘双击/`show_output` 弹窗三处入口），气泡窗口由 `ensure_toast()` 在首次触发快捷键时建出。二者都是「已存在则复用、不存在才 `WebviewWindowBuilder` 建」。气泡窗口首触发存在「事件早于前端监听器注册」的竞态，靠后端 `KadaState.toast` 暂存载荷 + 前端加载后 `get_toast_payload` 拉取兜底。托盘图标不受影响：`default_window_icon` 取自 `bundle.icon` 而非 `windows` 数组。

### 3.7 快速唤醒（被动双击检测）

`detect_wake` 在事件决策前运行：监听 `Settings::wake_key`（默认 Alt）的两次独立 down（间隔 ≤400ms、非自动重复），命中即唤出主窗口。设计成**被动**（只唤出窗口、不拦截按键），因为唤醒键常是修饰键，拦截会破坏 Alt+Tab / Alt+字母。配套修改：钩子层 `detect_repeat` 对修饰键/CapsLock 永不判重复，保证快速连按的两击都送达 handler。

### 3.8 系统快捷键冲突探测（三层）

`get_conflicts` 返回三类冲突：① 内部冲突（`detect_conflicts`：重复触发键/改键遮蔽/超集重叠）；② 系统快捷键清单（`SYSTEM_SHORTCUTS` 精确匹配，跨平台）；③ Windows `RegisterHotKey` 瞬时试探真实占用（注册成功即注销，错误码 1409=已被占用）。后两层补足「硬编码清单漏报/误报」，让用户录入组合键时即时看到「已被系统/其他应用占用」的警告。

### 3.9 tap-hold 与多层（改键状态机）

- `Remap` 从「原始键 → 目标键」扩展为六种形态：普通改键（`to`）、tap-hold（`tap` 短按 / `hold` 长按，阈值 `tap_timeout_ms` 默认 200ms）、切层键（`hold_layer` 长按进入层、松开退回）、单次修饰（`oneshot`）、粘滞修饰（`sticky`）、tap-dance（`tap2`/`tap3` 双击/三击）。运行时按 `sticky > oneshot > tap-hold > 普通 to` 互斥判定。
- `taphold_step` 在 `decide` 之前运行：按下 `from` 吞掉并进入待定，短按（阈值内松开）按模式输出——普通 tap-hold 输出 `tap`、含 `tap2`/`tap3` 进入 `TapDanceState`（等待窗累计击数、超时由定时器线程提交，事件路径懒判定兜底）、`oneshot` 武装单次修饰、`sticky` 切换粘滞修饰；**roll 判定**=待定期按下其它键立即判 hold，缓解「短按慢一个阈值」的手感损失；`hold` 是修饰键时并入注入修饰集，让「长按 CapsLock=Ctrl 后按 K」命中 `Ctrl+K`。
- **无输出的两条路径都回放原键**（吞键铁律，见 3.6）：短按没设 `tap`、长按到底（未 roll）没设 `hold`——切层键正属后者（层只在 roll 时进入，单独按住再松开等于没用过），若什么都不发，这个键按下去就没有任何反应；有 `hold` 则长按松开时短促输出该键一次。
- 注入修饰统一走「物理注入（`simulate`）+ 后续键 mods 补全」通道，`ModsState` 分三类：`hold`（长按期间、`from` 松开释放）、`sticky`（锁存、再次单击 `from` 解锁）、`oneshot`（武装待释放、下一个非修饰键释放；roll/长按当普通 hold 修饰）。补全 = `hold ∪ sticky ∪ oneshot`。
- 层语义统一「激活层条目优先、基础层条目兜底」（`match_shortcut`/`match_plain_remap`/`find_taphold_rule` 三处共用）；`active_layer` 是运行时态、由切层键 momentary 驱动，非持久化。
- 键序列已把「键盘时序状态机」思路落地为纯逻辑 `SequenceTracker`（见 3.12）；oneshot/sticky/multi-tap 复用同一套 tap-hold 时序状态机（`TapHoldPending` 待定态 + `TapDanceState` 连击等待态 + `ModsState` 注入通道），避免各自实现一套时序逻辑打架。

### 3.10 文本扩展（hotstring 缓冲）

`Engine::hotstring` 在 `decide` 放行的事件上运行：可打印字符（`key_to_char`）累积成最近 N 字符滑动窗口（`MAX_HOTSTRING_BUFFER=64`）；空格/回车/Tab 触发后缀命中时，**吞掉后缀键**并由后台线程回删触发词（发 N 次 Backspace）+ 注入替换文本 + 补回后缀键（后缀若先落盘会与回删并发错位）；方向键/功能键等非可打印键打断缓冲；最长触发词优先（`match_expansion`）。动态片段 `{date}`/`{time}`/`{clipboard}` 由 `resolve_hotstring` 展开，注入失败记入消息中心。

触发词里的**连打同字母**（如 `addr`）曾经永远不命中：钩子用「同键 250ms 内再次 down」判自动重复，把第二次 `d` 当成按住连发从缓冲里丢掉了。自动重复改按「该键已按下且未抬起」（`HELD_KEYS`）判定后修复，同一次修复也恢复了「同键快速连按两次触发同一快捷键」与双击/三击改键的计击。

### 3.11 前台应用/窗口条件

`Condition::matches(vars, frontmost)` 新增 `frontmost: Option<&FrontmostContext>` 参数。前台上下文在触发时（`fire` 异步线程起点）由 `frontmost_context()` 抓取：Windows 用 `GetForegroundWindow` + `GetWindowTextW` + `OpenProcess`/`QueryFullProcessImageNameW` 取标题与进程名；Linux 暂返回 `None`（Wayland 无通用查询协议，X11 可走 `_NET_ACTIVE_WINDOW` 待后续）。无上下文时三类前台条件一律不成立（避免 `NotFrontmostApp` 误判为真）。

### 3.12 键序列 / leader key（时序状态机）

- **触发模型**：`Trigger = Combo(Shortcut) | Sequence(Vec<Shortcut>) | Chord(Vec<Shortcut>)`。序列以空格分隔多步（`"F9 J K"`）、和弦以 `&` 分隔同时按住的键（`"F&J"`）；解析（`Trigger::parse`）与匹配时序（`SequenceTracker`/`ChordTracker`）都收在 `kada-core`，纯逻辑可单测，壳层只负责吞键/回放/注入的落地。
- **`SequenceTracker`（核心）**：`advance` 维护「候选序列 + 已匹配步数」。空候选时命中任一序列首步即建候选（leader 吞掉）；推进时命中下一步的候选前进、任一走完返回 `Complete(下标)`、全断链重置返回 `NoMatch`；共享同一 leader 的多条序列（`"F9 J K"`/`"F9 J L"`）一并建候选自然共存。
- **`sequence_step`（壳层）**：在 `chord_step` 之后、`decide` 之前运行，只处理非重复 Down。`Advance` 吞掉等待下一键、`Complete` 复用 `fire` 触发（序列按键即触发键，不回放）、`NoMatch` 断链；超时（`SequenceState.timeout`，默认 `DEFAULT_SEQUENCE_TIMEOUT_MS=1000`）由**定时器线程**（每 60ms 调 `Engine::tick`）与事件路径的懒判定双路落地——只靠懒判定时，单独按一下 leader 键（之后不按别的键）回放永不发生，用户看到的是该键按了没反应。**断链与超时都把已吞掉的 leader 与中间步按输入顺序回放**（超时那次连当前键一起回放，保证顺序）；`Escape` 不再单独吞掉，按普通断链处理。序列条目按「激活层优先、基础层兜底」收集（`collect_sequence_items`），与 `match_shortcut` 层语义一致。
- **`chord_step`（壳层）**：在 tap-hold 之后、键序列之前运行。成员键按下即吞掉（不吞就漏字符、凑不成和弦）、凑齐所有成员立即触发；**没凑成则原样回放**——成员键全部抬起仍未凑齐就按按下顺序回放，待定期间按下的其它键一并吞掉并排在后面回放（保序），修饰键直接放行（否则 `Ctrl+X` 失效），待定缓冲 ≥16 项立即定论回放。已触发/已回放但物理仍按住的键记入 `settling`，其 keyup 前抑制自动重复，避免重复回放多出字符。
- **与单组合互相独立**：序列字符串本就不被 `Shortcut::parse` 接受，天然被 `match_shortcut` 跳过；`detect_conflicts` 把「序列 leader 遮蔽同层单组合」（如 `"F9 J K"` 吞掉组合 `"F9"`）列为硬冲突。

### 3.13 热路径克制 + 编译期 feature 门控（架构重构）

- **热/非热路径边界**：钩子回调热路径只跑 `detect_wake → Engine::step（tap-hold → 和弦 → 键序列）→ decide → Engine::hotstring`；状态机集中在 `src-tauri/src/engine.rs`（Tauri 无关，注入走 `Inject` trait、动作走 `fire` 回调，因此可单测：假的注入记录器替代 `simulate`，测试里绝不真的发键）；命中快捷键后由 `fire` 用 `std::thread::spawn` 把动作执行丢到后台线程（`kada_actions::run_actions`），回调不等待、不跑动作逻辑。低延迟是关键约束——Windows 低层钩子卡约 300ms 会被系统直接摘除；动作执行、命令/文件 I/O 本就在后台线程，慢一点无碍。
- **动作执行引擎拆出 `kada-actions`**：`run_action`/`run_os`/`run_app`/`run_cmd`/`run_script`/`transform_case` + `CommandResult` 从 `src-tauri` 迁出（约 800 行），壳只保留 `fire`（spawn + commit 回调）与消息中心 `commit_result`。`kada-actions` 不依赖 Tauri，可独立单测。
- **编译期 feature 门控（`automation`）**：`kada-core`/`kada-actions`/`src-tauri` 均 `default = ["automation"]`；关闭后得「基础版」= 改键全形态 / 层 / 键序列 / 文本扩展 / Text·Keys·PauseMs 注入，裁掉 `Command`/`Os`/`App`/`If`/`Condition`/`Vars`/`Script`，体积更小、零运行时分支。编译期分层（打两个包）与运行时解锁（一个包按 license 开关）两可，当前先做编译期。
- **脚本动作（`Action::Script`，逃生舱而非内嵌引擎）**：`{ path, interpreter, show_output, var }`——复用 `run_cmd` 的输出捕获 + 消息中心通道；spawn 前注入环境变量 `KADA_TRIGGER`/`KADA_NAME`/`KADA_VARS`（变量表 JSON），回写走 `{var.exit_code}`。先指向脚本文件（python/node/bash），不嵌 Rhai/Lua；生态起来再补 wasm/动态库。

### 3.14 软件更新（签名校验 + 「安装即退出」）

- **为什么不在输入热路径上**：更新完全是另一条通道（`src-tauri/src/update.rs`），只在启动后延迟触发或用户点按钮时跑，钩子回调里没有任何更新相关代码。
- **信任链**：清单（`latest.json`）与安装包都从 GitHub Releases 取；**清单本身不被签名**，被签名的是安装包，所以客户端拿内嵌公钥（`plugins.updater.pubkey`）验安装包签名后才安装——签不过直接拒绝，绝不执行未签名的安装器。私钥只在本机 `~/.tauri/` 与 CI Secret。
- **三种触发的打扰等级刻意不同**：启动后台检查全静默（只有真发现新版本才弹一次气泡，网络失败/没发过 Release 都不打扰）；手动检查（托盘/设置页）无更新与出错都弹窗、发现新版本先确认；设置页「下载并安装」点击即确认。
- **「安装即退出」塑造了整个设计**：Windows 安装器要求目标进程先退出，Tauri updater 在安装步骤里会结束应用（NSIS 以 `passive` + `/R` 跑，装完自动重启）。因此**启动检查只提示、不自动安装**——自动安装等于替用户决定「现在关掉你正在用的应用」；也意味着安装后的收尾不能由旧进程做（它已经不在了）。
- **状态在后端、进度要节流**：阶段机在 Rust 侧（`idle/checking/up-to-date/available/downloading/installing/error`）经 `update-status` 事件推给前端；下载的 on_chunk 回调极其密集，只在整数百分比变化时发事件，否则会把 IPC 与前端渲染刷爆。
- **权限面**：更新全走 Rust（`UpdaterExt`），前端不直接调 updater，capabilities 里因此不开 `updater:*`——不是漏配，是最小权限。

## 4. 跨平台策略

- 键模型平台无关（`Meta` 承载 macOS ⌘），平台层负责把 OS 键映射成 `Key`（Windows VK 码 / Linux evdev 键码，均 US 布局语义、左右修饰键归一）。
- 钩子引擎按平台模块化（`win`/`linux`），对外统一 `start(handler) -> HookHandle` + `Action` 三态 + `simulate` 接口。
- 非 Windows/Linux 平台（macOS）用占位类型保证壳可编译（`hooks_supported() = false`），托盘与配置界面可用，快捷键/改键/录制暂不可用（M5 待实现）。

## 5. 已知天花板（升级路径）

- 低层钩子拦不住 UAC 提权进程 / 部分游戏 → 驱动级拦截（Interception）。
- Linux 热插拔键盘不在监听列表 → 监听 `/dev/input` 热插拔事件动态增删设备。
- 剪贴板粘贴被目标程序吞 → `KEYEVENTF_UNICODE` 直发兜底。
